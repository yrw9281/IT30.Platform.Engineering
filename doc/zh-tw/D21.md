# Day 21 - 用 Backstage Software Templates 收集服務設定

## 讓開發者選 image，不必先找 YAML

前面已把 `Microservice` 到 Deployment 的欄位關係說清楚，但目前只有 Kubernetes CRD 與手寫的 `todo-api` 範例。要更新 image，開發者還是得知道 Git 設定放在哪裡、哪個環境能改、如何提出變更。

Backstage 可以提供一個入口。本篇先釐清 **Software Catalog** 與 **Software Templates**：前者讓人找到服務與擁有者，後者收集少量輸入並執行設定產生步驟。這不表示 Backstage 會自己理解 CRD，更不表示按下表單就完成部署。

## Catalog 描述服務，CR 描述部署意圖

為 `todo-api` 建立 Catalog `Component` 時，可以記錄服務名稱、負責團隊，以及關聯 Kubernetes 資源的查詢條件。以下是服務紀錄的關鍵設定：

```yaml
apiVersion: backstage.io/v1alpha1
kind: Component
metadata:
  name: todo-api
  annotations:
    backstage.io/kubernetes-namespace: todo
    backstage.io/kubernetes-label-selector: app=todo-api
spec:
  type: service
  lifecycle: experimental
  owner: todo
```

現有 Todo API 的 Deployment 和 Pod 使用 `app: todo-api`，所以這個 selector 可以指向它們；Backstage 的 Kubernetes plugin 仍需安裝、設定叢集連線與讀取權限。Catalog `owner: todo` 是負責團隊的 metadata，**不能拿來當授權判斷**。Catalog `Component` 也不等於 Kubernetes `Microservice` CR；前者供人查找，後者才是 Operator 會讀取的部署意圖。

## Template 先只開放一個受控輸入

第一個 Software Template 鎖定 Todo API 的 Dev 更新，不讓表單任意填 Git repository、branch、Namespace 或服務名稱。使用者只提供 CI 發布的 image digest；表單用格式限制擋下漏字或無效的 SHA-256 字串：

```yaml
parameters:
  - title: Image from the release workflow
    required:
      - digest
    additionalProperties: false
    properties:
      digest:
        title: Image digest (64 lowercase hex characters, without sha256:)
        type: string
        minLength: 64
        maxLength: 64
        pattern: "^[0-9a-f]{64}$"
```

CI 的輸出通常寫成 `sha256:` 加 64 位十六進位字元；這裡只要求填後半段，產生設定時再固定加上 `sha256:`。格式正確不代表這個 digest 真的是 Todo API 的 image，也不代表使用者有權部署。真正採用前，仍要由受信任的檢查確認它與 GHCR package、CI run 及提出者權限的關係；Git PR 是另一道審查邊界。

Template 的 `fetch:template` 步驟會以這個值渲染一份受控的 `Microservice` YAML。服務名稱、Namespace、port 和 image repository 都由模板決定，產物的關鍵欄位是：

```yaml
apiVersion: platform.example.io/v1alpha1
kind: Microservice
metadata:
  name: todo-api
  namespace: todo-dev
spec:
  image: ghcr.io/yrw9281/it30-todo-api@sha256:{{ values.digest }}
  port: 8080
```

這裡的 `{{ values.digest }}` 是 Backstage 渲染模板時才會替換的值，**不是可直接提交 Kubernetes 的 YAML**。`todo-dev` 與目前原生 manifest 使用的 `todo` Namespace 也不同：Dev 設定儲存庫、Namespace、Argo CD Application 和 Operator 尚未建立。來源檔可以做靜態解析與替換檢查，不能據此宣稱 Backstage 表單或叢集部署已通過測試。

## 提交前應在哪裡驗證？

Software Template 的表單 schema 能減少填錯 digest，但 request 也可能由 API 送入；後端應重驗輸入，而不是只相信瀏覽器。模板的固定目標也不會自動完成團隊授權：若有多個團隊或環境，必須以已驗證身分和受控 mapping 限制哪些人能使用哪份模板。不能從可自行編輯的 Catalog owner 欄位推導使用者權限。

本地能確認的是模板 YAML 可解析、digest 欄位有格式限制，以及測試 digest 渲染後 `Microservice.spec` 仍只有現有 CRD 接受的 image、port。這只是靜態檢查；Backstage 尚未安裝，Git PR 和 Kubernetes 都未被這個檢查觸發。
