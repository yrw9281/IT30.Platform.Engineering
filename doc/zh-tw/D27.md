# Day 27 - 用 Gatekeeper 辨識高風險工作負載設定

Day 26 說明 Gatekeeper 可以在 admission 檢查新資源，並透過 audit 盤點既有資源。但「開啟 Gatekeeper」本身不會拒絕任何高風險設定。平台得先說清楚要防的是什麼、命中哪些工作負載，以及遭拒時開發者該如何修正。

這篇看三種 Todo 服務常見的風險：缺少資源限制、使用特權容器、引用未核准的 image。**目前沒有 Rego、`ConstraintTemplate`、`Constraint` 或實際拒絕紀錄**；以下只建立政策設計與預期驗收邊界。

## 一條規則要有可解釋的輸入與結果

| 風險輸入 | 為何要檢查 | 預期回饋與修正方向 |
| --- | --- | --- |
| Container 缺少 CPU／memory `limits` | 單一 workload 可能占用超出預期的資源 | 指出缺少哪個 container／欄位，補上經核准的預算 |
| Container 設定 `securityContext.privileged: true` | 放寬容器的隔離限制 | 指出容器名稱，改用非特權方式；必要例外另行審查 |
| Image 不在核准的 GHCR repository | 來源超出團隊允許範圍 | 指出 image reference，改用受信任 repository 的 digest |

檢查一般 container 時，別漏了 `initContainers`；只擋直接建立的 Pod，也可能漏掉由 Deployment／其他 controller 產出的 Pod。要在哪一層檢查，取決於期望的回饋時間與資源覆蓋範圍，不能只憑一份「Deployment 規則」宣稱整個叢集都受保護。

## 檢查 image 字串不等於驗證來源

比對 GHCR 時，不能只問 image 字串「是否包含」`ghcr.io/yrw9281`；相似的惡意名稱也可能混過。核准清單要明確到 repository 邊界，必要時要求 `@sha256:` 而非可移動的 tag。不過就算字串符合格式，也不能證明 image 由受信任的 CI run 建置、沒有被錯誤推送，或已獲環境核准。這些仍要回到 CI provenance、Git 設定檢查與 PR review。

現有 Todo API 的原生 Deployment 使用 `:0.1.0` tag，且**沒有 CPU／memory limits**，位於 `todo` Namespace。若把「必須用 digest 且具備 limits」的強制規則直接套到它，會先和自己的既有設定衝突。規劃中的 `todo-dev`、Operator 產出的 Deployment 也都還沒有建立。要先盤點實際工作負載、修正平台預設，再考慮從 `dryrun` 切換到 `deny`。

## 例外必須有邊界

Node 層級 agent 或某些維運工作可能有不同需求，但不應在每個團隊的政策裡留下永久通行的「特殊 Namespace」。例外至少要說明誰核准、影響哪些資源與環境、何時檢討；沒有紀錄的放寬，很快就會變成整條規則的漏洞。

若將來實作，驗收要同時包含合規案例、缺欄位案例、一般與 init container、錯誤 image 以及例外範圍。`dryrun` 可以協助發現現有資源會被哪些規則命中；`deny` 才能觀察新請求實際被拒絕。**本篇沒有跑這些測試，也不提供看似可套用但沒有來源的 Rego 片段。**

Admission 管的是資源寫入時的設定；服務執行後能和誰通訊，是另一道邊界。下一篇從流量路徑理解 Istio Sidecar 能做什麼，以及採用它要付出的代價。
