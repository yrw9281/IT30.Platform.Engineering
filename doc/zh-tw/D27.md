# Day 27 - Policy as Code：OPA Gatekeeper 怎麼檢查資源

Day 26 的 RBAC 限制身分能不能建立 `Deployment`，卻不會檢查內容是否少了 memory limit、使用未核准 image，或要求 privileged container。這些規則若只寫在 Wiki，錯誤 YAML 還是能送進 API Server。

Policy as Code 把可接受行為寫成可版本控制、可 review 的規則，並在資源進入叢集前執行。本日說明 Open Policy Agent（OPA）與 OPA Gatekeeper 的 admission 機制。`src/` 沒有 Gatekeeper 安裝檔、Template 或 Constraint，因此所有設定與演練都是**概念範例**，尚未在叢集執行。

## Admission 邊界在檢查什麼

OPA 是通用的 policy engine；OPA Gatekeeper 將它整合成 Kubernetes 的 admission controller。任何使用者或 controller 對 Kubernetes API 提出 create/update request 時，都會經過這條路徑：

```text
User / CI / Argo CD / Operator
             │ Kubernetes API request
             ▼
      API Server admission chain
             │
             ▼
       OPA Gatekeeper webhook
             │ evaluates matching Constraints
             ├── no violation / dryrun -> request continues
             └── deny violation      -> request is rejected
```

Gatekeeper 同時檢查手動 `kubectl apply` 與 Argo CD、Microservice Operator 產生的 child resources。平台預設必須符合自己的 policy，否則 Operator 每次 reconcile 都可能因 admission 拒絕而重試。

## 將規則邏輯與套用範圍拆開

`ConstraintTemplate` 定義 constraint 型別、參數 schema 與 Rego 邏輯；`Constraint` 則是該型別的實例，負責指定 target kinds、`Namespace`、參數與 enforcement action。這個拆法讓同一份規則能依環境套用不同範圍。

以下概念範例日後應新增為 `src/security/gatekeeper/required-labels-template.yaml`：

```yaml
# 規劃片段：ConstraintTemplate 的 API 與參數定義
apiVersion: templates.gatekeeper.sh/v1
kind: ConstraintTemplate
metadata:
  name: k8srequiredlabels
spec:
  crd:
    spec:
      names:
        kind: K8sRequiredLabels
      validation:
        openAPIV3Schema:
          type: object
          properties:
            labels:
              type: array
              items:
                type: string
  targets:
    - target: admission.k8s.gatekeeper.sh
      rego: |
        package k8srequiredlabels

        violation[{"msg": msg}] {
          required := input.parameters.labels[_]
          not input.review.object.metadata.labels[required]
          msg := sprintf("missing required label: %v", [required])
        }
```

套用到 Todo Dev 的概念 Constraint 日後應新增為 `src/security/gatekeeper/todo-deployments-required-labels.yaml`：

```yaml
# 規劃片段：將規則先以 dryrun 套用在 Todo Dev
apiVersion: constraints.gatekeeper.sh/v1beta1
kind: K8sRequiredLabels
metadata:
  name: todo-deployments-must-have-owner
spec:
  enforcementAction: dryrun
  match:
    namespaces:
      - todo-dev
    kinds:
      - apiGroups: ["apps"]
        kinds: ["Deployment"]
  parameters:
    labels:
      - app.kubernetes.io/owner
```

Template 可以重用並測試規則邏輯，Constraint 讓 platform team 不必為 Dev、Staging、Production 複製 Rego。兩者的變更也要走 Git review：把 `Namespace` 範圍從 `todo-dev` 改成 `*`，影響不亞於調整 production firewall。

## Admission 與 audit 看的時間點不同

Admission 只評估新的 create/update request，無法讓已存在的舊 `Deployment` 自動變安全。Gatekeeper audit 會定期掃描既有 resources，將違規記錄到 Constraint status。

```text
Admission
  問：「這次準備寫入的 resource 可不可以進來？」

Audit
  問：「叢集裡已經存在的 resource 有哪些不符合目前規則？」
```

audit 找到遺留違規後，平台仍要決定修正方式：哪些能自動修、哪些交給 owner、哪些因相容性暫時例外。沒有這個盤點就切換 `deny`，很容易中斷既有工作負載。

## 以 `dryrun` 開始，再評估 `deny`

`enforcementAction` 讓規則不必第一天就硬性阻擋：

| 模式 | 對新 request 的行為 | 適合的時機 |
| --- | --- | --- |
| `dryrun` | 記錄 violation，不阻擋 | 盤點既有資源與 false positive |
| `warn` | 允許 request 並提供警告 | 讓開發者在不阻斷流程下看見新規則 |
| `deny` | 拒絕違規 request | 規則、例外與修正路徑已成熟 |

確切可用 action 要依安裝的 Gatekeeper 版本確認。規劃上先在 Todo Dev 使用 `dryrun`，把 false positive 與必要例外記為有到期日的決策，再考慮轉成 `deny`。永久且沒有原因的寬鬆例外，只會讓風險失去可見性。

## Gatekeeper 補上其他邊界

CRD schema 先檢查欄位形狀；IDP API 應在送出時回傳易懂錯誤；config PR 在 merge 前驗證 render；RBAC 決定誰能送 request；Gatekeeper 則在 admission 邊界確保任何來源都不能繞過最低要求。即使多層都檢查 image registry，它們守住的 trust boundary 也不同。

## 後續驗證

Gatekeeper、Template 與 Constraint 尚未安裝，也沒有對應的測試 fixture。完成上述 `src/security/gatekeeper/` 檔案與安裝設定後，應驗證：

```text
預期演練：
1. 在 todo-dev 以 dryrun 建立缺少 owner label 的 Deployment，確認 request 仍可建立但 Constraint audit 記錄 violation。
2. 補上 label 後重新評估，確認 violation 消失。
3. 將同一規則改為 deny，確認違規 request 在 API Server admission 時被拒絕並顯示可讀訊息。
4. 讓 Microservice Operator 產生的 Deployment 經過相同 Constraint，確認平台預設本身符合 policy。
5. 檢查其他 Namespace 不在 match 範圍時不會被意外阻擋。
```

驗收時要能回答哪份 `Constraint`、哪個版本、哪種 enforcement action 對哪些 resources 生效。下一篇會把資源 limits、privileged container 與核准 image registry 寫成具體 Rego 規則。
