# Day 20 - 用 Kopf 將 `Microservice` CRD 建成 Deployment

## 前一日主題回顧

Day 19 定義了 Operator 在 create、update、drift 與失敗時要持續收斂。現在把它落到 `reminder-api`：`Microservice.spec` 只有 image、port、env，卻必須變成 Kubernetes、Argo CD 與 observability 系統都看得懂的一組資源。

這不只是把 YAML 字串拼出來。每個欄位都在交代平台決策：誰擁有資源、Service 怎麼找到 Pod、資源限制由誰提供、OTel 如何使用一致的服務名稱，以及哪些觀察結果才足以回報 `Ready=True`。

## 先寫清楚轉換契約

對同一筆 `reminder-api` CR，Operator 會產生兩個主要 child resources。日後可再擴充 ServiceMonitor、NetworkPolicy 或 HPA，但第一版先避免把所有平台能力硬塞進一個 controller。

| `Microservice.spec` 輸入 | Operator 產出 | 平台保證 |
| --- | --- | --- |
| `image` | Deployment container image | 使用 GitOps 已核准的 digest，不在 Operator 中改寫 tag |
| `port` | named container port 與 Service `targetPort` | Deployment 與 Service 不會因手打 port 漂移 |
| `env` | non-sensitive container env | 不接受明文 secret；名稱和值經 schema 驗證 |
| `metadata.name` | resource name、labels、OTel service name | logs、traces、metrics 使用一致服務識別 |
| CR UID | child resource owner reference | 刪除 CR 時只清理由它擁有的資源 |

這張表也刻意留下幾個「還沒有」：第一版不自動暴露 public Ingress、不替服務建立資料庫、不把 secret value 寫入環境變數。平台的成熟度不在於一次幫所有人做完所有事，而在於每一項自動化都有清楚輸入、輸出與責任。

## `Microservice` 輸入與受管 Deployment

先回看 Day 18 的服務意圖：

```yaml
# 規劃片段：reminder-api 的平台合約
apiVersion: platform.example.io/v1alpha1
kind: Microservice
metadata:
  name: reminder-api
  namespace: todo-dev
spec:
  image: ghcr.io/yrw9281/reminder-api@sha256:******
  port: 8080
  env:
    REMINDER_BATCH_SIZE: "50"
    LOG_LEVEL: Information
```

Operator 的 desired Deployment 要保留服務團隊提供的 image、port 與非敏感設定，同時加入平台擁有的 labels、resource baseline、probe 與 OTel 資源屬性。以下僅是預期結果的關鍵片段；專案尚無對應實作或完整 manifest，不能直接套用：

```yaml
# 規劃片段：Operator 為 reminder-api 產生的 Deployment 核心
apiVersion: apps/v1
kind: Deployment
metadata:
  name: reminder-api
  namespace: todo-dev
  labels:
    app.kubernetes.io/name: reminder-api
    app.kubernetes.io/managed-by: microservice-operator
  ownerReferences:
    - apiVersion: platform.example.io/v1alpha1
      kind: Microservice
      name: reminder-api
      uid: <microservice-uid>
      controller: true
spec:
  replicas: 2
  selector:
    matchLabels:
      app.kubernetes.io/name: reminder-api
  template:
    metadata:
      labels:
        app.kubernetes.io/name: reminder-api
    spec:
      containers:
        - name: app
          image: ghcr.io/yrw9281/reminder-api@sha256:******
          ports:
            - name: http
              containerPort: 8080
          env:
            - name: REMINDER_BATCH_SIZE
              value: "50"
            - name: LOG_LEVEL
              value: Information
            - name: OTEL_SERVICE_NAME
              value: reminder-api
            - name: OTEL_RESOURCE_ATTRIBUTES
              value: service.namespace=todo,deployment.environment.name=dev
          resources:
            requests:
              cpu: 100m
              memory: 128Mi
            limits:
              cpu: 500m
              memory: 512Mi
```

`replicas`、resources、probe 和 OTel 預設是平台目前的選擇，而不是從 CR 直接複製而來。Day 27 的 admission policy 會再守住「任何 workload 都有 resources limit」這條底線，但 Operator 先提供安全預設，能降低服務團隊只為了通過 policy 而隨意填數字的誘因。

實作時，Operator 必須只管理自己擁有的欄位。若平台未來允許其他 controller 注入 sidecar 或 annotation，不能用一個全物件 replace 把對方設定洗掉；這也是 Day 19 提到 server-side apply 與 field ownership 的原因。

## Service 將 Pod 生命週期藏在穩定端點後方

`Deployment` 會替換 Pod，因此 Operator 也要產生一個 selector 與 labels 相符的 ClusterIP Service。這份合約延續 Day 03，而不是重新發明流量骨架。

```yaml
# 規劃片段：Operator 為 reminder-api 產生的 Service
apiVersion: v1
kind: Service
metadata:
  name: reminder-api
  namespace: todo-dev
  labels:
    app.kubernetes.io/name: reminder-api
    app.kubernetes.io/managed-by: microservice-operator
  ownerReferences:
    - apiVersion: platform.example.io/v1alpha1
      kind: Microservice
      name: reminder-api
      uid: <microservice-uid>
      controller: true
spec:
  type: ClusterIP
  selector:
    app.kubernetes.io/name: reminder-api
  ports:
    - name: http
      port: 80
      targetPort: http
```

Service 的存在不表示它一定有可用 endpoints。真正可不可以接收流量，仍由 Pod readiness 和 Deployment availability 決定；這是 Operator status 不能在成功送出 API request 後立刻寫成 Healthy 的原因。

## 從 Deployment observation 寫回 conditions

Operator 建立 resources 後，先將 CR 標成正在處理；只有觀察到目前 generation 對應的 Deployment 已達目標可用狀態時，才可回寫 `Ready=True`。

```yaml
# 規劃片段：Operator 回寫的 Microservice status
status:
  observedGeneration: 7
  managedResources:
    deployment: reminder-api
    service: reminder-api
  conditions:
    - type: Ready
      status: "True"
      reason: DeploymentAvailable
      message: "2 of 2 replicas are available"
      observedGeneration: 7
```

若 image 無法拉取、readiness probe 持續失敗，condition 應維持 `Ready=False`，並帶上可行的 reason/message，例如 `ImagePullBackOff` 或 `DeploymentUnavailable`。若 Operator 判斷錯誤已無法靠既定 retry policy 自行收斂，還要加入 `Stalled=True`；Day 23 的 Argo CD health check 會以這個明確訊號轉成 `Degraded`，避免把需要人處理的錯誤永遠顯示為部署中。

要注意 `Deployment.status.availableReplicas` 只是其中一個訊號。實作時需同時檢查 Deployment 的 observed generation 和 available condition，避免讀到舊 revision 的成功狀態後，就錯把新 image 當成 ready。

## 產生資源後，平台還應保留什麼？

除了 manifests，Operator 應讓日後的人能辨識資源由誰管理：

```text
Microservice/reminder-api
  ├── owner reference -> Deployment/reminder-api
  ├── owner reference -> Service/reminder-api
  ├── label: app.kubernetes.io/managed-by=microservice-operator
  └── status.managedResources: deployment/service names
```

這些小資訊在平常看起來冗餘，發生事故時卻能回答「這個 Deployment 是不是可以手動刪？」「誰會把它補回？」「如果 CR 被刪除，哪些東西會一起消失？」可操作性也是平台合約的一部分。

## 測試與驗證

Operator 與 CRD 尚未實作。未來的驗證不會只比對 YAML 文本，而會檢查資源與狀態的關係：

```text
預期演練：
1. 建立 reminder-api CR，確認只生成同 Namespace、名稱一致且有 owner reference 的 Deployment 與 Service。
2. 確認 Deployment selector、Pod label、Service selector 與 named targetPort 完全相符。
3. 變更 spec.image，確認 Deployment template 更新而 status 先回到 Ready=False。
4. 等待新 revision available，確認 status.observedGeneration 與 Ready condition 同步前進。
5. 以無法拉取的 image 重複測試，確認不會誤回報 Ready=True。
```

完成這些驗收後，開發者才能相信 `Microservice` 不只是一份被儲存的 YAML，而是會可靠展開並誠實回報的服務合約。

叢集端已有把 `Microservice` 收斂成受管資源的責任劃分，但開發者不該手寫 CR、自己開 Git branch。下一篇改看 IDP 後端：它如何接住 Portal 輸入、驗證權限與合約，再安全地把 `reminder-api` 的意圖寫進 GitOps repository。
