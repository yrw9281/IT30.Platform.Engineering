# Day 20 - 從 `Microservice` 到 Deployment：Operator 應建立哪些資源

## 先從現有 Todo API 設定看差異

Day 19 說明 Operator 應如何反覆處理 `Microservice`，但目前還沒有 Kopf 程式。要寫 controller，得先回答一個比較具體的問題：`todo-api` 的 CR 只有 image 和 port，最後的 Deployment、Service、OTel 設定應從哪裡來？

現有 Todo API 的原生 Kubernetes 設定已包含 Deployment、Service、probe 與 OTel 環境變數；它不是 Operator 產物。可以拿它當對照，檢查平台從服務意圖產生資源時，哪些欄位必須由 Operator 統一決定，哪些來自 `Microservice.spec`。

## `Microservice` 的欄位要落在哪裡？

| CR 中的資料 | 預期寫入的 Kubernetes 欄位 | 不能省略的判斷 |
| --- | --- | --- |
| `metadata.name` | Deployment／Service 名稱、受管 label、OTel `service.name` | 同一個服務在不同資源裡要使用一致名稱 |
| `metadata.namespace` | Deployment／Service 所屬 Namespace | 不跨到表單使用者不能操作的 Namespace |
| `metadata.uid` | child resource 的 owner reference | 只清理這筆 CR 擁有的資源 |
| `spec.image` | Deployment container image | 原樣使用已審查的 reference，不在 Operator 內重新挑 tag |
| `spec.port` | container port、Service port／`targetPort` | Service selector 與 Pod labels 要能對上 |
| 規劃中的 `spec.env` | container 的非敏感環境變數 | 現有 CRD 尚未支援，不能先當成可輸入欄位 |

現有 Deployment 使用 `ghcr.io/yrw9281/it30-todo-api:0.1.0`，Service 的 selector 則選取 `app: todo-api` 的 Pod，將 Service port `8080` 轉給 container 的 `http` port。這些是已存在的原生設定，不是「建立 CR 後已自動產生」的畫面。等 GitOps 設定改用 digest，Operator 也應把 CR 中審查過的 digest 原樣帶進 Deployment。

## 平台預設與服務輸入要分開

`replicas`、readiness／liveness probe、CPU／memory requests 和 limits、OTel exporter endpoint 都不是目前 CRD 開放給服務團隊的欄位。Operator 必須有自己受審查的預設值，否則只憑 image 與 port 無法產生可維護的工作負載。

以現有 `todo-api` 為例，readiness probe 使用 `/health/ready`、liveness probe 使用 `/health/live`。若新服務沒有這些 endpoint，原封不動套用同一預設會讓 Pod 永遠無法 ready。因此 Operator 的合約還必須決定：平台是否要求服務遵守相同健康介面？不符合時要拒絕建立，還是另有受控設定？這個問題尚未在 CRD 與程式中解決，不能把現有 Todo manifest 當成所有服務的通用模板。

OTel 也一樣。現有 Deployment 明確設定 `OTEL_SERVICE_NAME`、`OTEL_SERVICE_VERSION` 與 Collector endpoint；規劃中的 Operator 要保留這些用途，但服務名稱可由 CR 名稱推導，版本則不能在 image 已更新時繼續沿用舊版固定值。只有 image digest，不一定能直接推得適合人閱讀的 release version，兩者要各自有明確來源。

## 建立資源不代表已可用

Operator 把 Deployment 與 Service 送到 API Server 後，應先記錄正在收斂；它還需要觀察 Deployment 是否已處理當前 generation、目標副本是否 available、Service selector 是否對得到 Pod。收到新 image 時，舊版留下的「可用」不能替新版背書。

目前 CRD 定義了 `status.observedGeneration` 等欄位，卻沒有 controller 寫入；`Ready`／`Stalled` conditions 也尚未加入 schema。只有完成這些狀態合約與 Operator 實作，Argo CD 才能據此判斷自訂資源是否健康。

## 怎麼驗收這份資源合約？

現階段可以對照現有 Todo API 的 CR、Deployment 與 Service，確認 image、port、Pod label／Service selector 的關係；不能執行「由 Operator 建立資源」的測試，因為目前沒有 Kopf 原始碼。實作時至少要檢查：一筆 CR 只產生同 Namespace 的一組受管資源；重送事件不建立重複 Deployment；更新 image 等待新版本 available；image pull 失敗時不回報 `Ready=True`。

資源輸入與輸出清楚後，開發者也不該為每次更新自己手寫 CR、找設定儲存庫目錄。下一篇改看 Backstage 如何讓服務團隊提供必要資訊，以及它的服務目錄與表單各負責什麼。
