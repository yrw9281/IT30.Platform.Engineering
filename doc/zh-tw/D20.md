# Day 20 - Operator 模式與 Kopf：怎麼處理 CRD 事件

## 前一日主題回顧

`Microservice` CRD 已能接受 `reminder-api` 的 image、port 與環境變數，但 API Server 只負責驗證與保存，並不會建立 Deployment、Service 或 OTel 設定。若只用一次性的 Python script 讀取 CR、產出 YAML、套用後離開，第一次執行或許順利，接下來的變更與失敗卻沒有地方收斂：

- image 從 `0.1.0` 改成新 digest 時，誰更新 Deployment？
- 有人手動刪掉 Service 時，誰發現平台的期望狀態被破壞？
- Deployment 建立後 Pod 無法 ready 時，誰把原因寫回 `Microservice.status`？
- 使用者刪除 CR 時，哪些資源應該被清理、哪些共享資源不該被誤刪？

這些不是 template renderer 能回答的問題；它們需要一個像 Kubernetes 原生 controller 一樣，持續觀察、比較並收斂的元件。

## Operator 模式：把營運知識變成控制迴路

**Operator** 將特定領域的部署與營運規則實作成 Kubernetes controller。它監看 Custom Resource 的生命週期，依 `spec` 管理 child resources，觀察實際狀態，再更新 CR 的 `status`。

```text
Microservice CR create / update / delete event
                 │
                 ▼
             Kopf handler
                 │
      desired Deployment + Service
                 │
                 ▼
        Kubernetes API / child resources
                 │
                 ▼
    observe readiness and failure conditions
                 │
                 ▼
      patch Microservice.status.conditions
```

Day 02 的 reconcile loop 到這裡再次出現：Operator 的工作不是「收到 create event 就成功」，而是反覆讓 `Microservice.spec` 和它管理的資源狀態靠近。每一次 event 都可能重送、亂序，或在上次處理一半時被中斷；因此正確性來自可重複收斂，而不是假設 handler 永遠只跑一次。

## 為何本系列選 Kopf，而不是一開始手寫 Go Operator？

Go 搭配 Kubebuilder 或 controller-runtime 是成熟且常見的 Operator 生態，對大型控制器、強型別 API、複雜 cache 與長期維護很有價值。但它也有一段較長的進入成本：scheme、reconciler、generated code、RBAC manifest 與測試樣板，容易讓本系列的焦點從「平台合約如何收斂」偏到「如何先學會框架儀式」。

**Kopf（Kubernetes Operator Pythonic Framework）** 讓我們以 Python decorator 定義 resource handler，先把重點放在事件、idempotency、ownership 與 status。這是一個教學與小型平台的選擇，不是宣稱 Python 永遠比 Go 適合 Operator：

| 選擇 | 適合的起點 | 需要承擔的風險 |
| --- | --- | --- |
| Kopf | 團隊熟悉 Python、控制邏輯相對聚焦、想快速驗證合約 | 仍要處理 retry、RBAC、可觀測性與部署生命週期 |
| Go controller-runtime | 高併發、複雜 reconciliation、長期維護多個 CRD | 初始樣板與團隊學習成本較高 |

換框架不會讓 controller 自動正確。無論使用什麼語言，只要「資源已存在」被當成 exception、「收到 event」被當成成功，平台就會在第一次重試時暴露問題。

## Handler 要表達的是收斂，不是一次性 create

以下是 Kopf handler 的規劃骨架，尚未寫入 `src/`。它刻意處理 create 與 `spec` 變動，而非監看所有 update；若將 status patch 也當成新的 spec reconcile 事件，controller 很容易因自己更新 status 而重複觸發。它透過 `patch.status` 更新 controller 擁有的狀態；不要依賴 handler 的 return value 當成公開 status contract，因為框架可能會以 handler 名稱儲存它。

```python
# 規劃片段：microservice_operator/handlers.py
import kopf


@kopf.on.create("platform.example.io", "v1alpha1", "microservices")
@kopf.on.field(
    "platform.example.io",
    "v1alpha1",
    "microservices",
    field="spec",
)
def reconcile_microservice(spec, meta, patch, **_):
    desired_resources = build_desired_resources(
        name=meta["name"],
        namespace=meta["namespace"],
        uid=meta["uid"],
        spec=spec,
    )

    apply_with_field_manager(desired_resources, manager="microservice-operator")

    patch.status["observedGeneration"] = meta["generation"]
    patch.status["conditions"] = [
        {
            "type": "Ready",
            "status": "False",
            "reason": "Reconciling",
            "message": "Waiting for managed Deployment to become available",
        }
    ]
```

這個 `apply_with_field_manager` 只是日後要實作的 server-side apply 概念，專案裡沒有可執行的 helper。實作時，它要用固定 field manager 宣告 Operator 擁有的欄位，並能安全重跑；既不能因資源已存在而失敗，也不能無條件覆寫其他 controller 擁有的欄位。

## Idempotency：重跑一次後結果應該相同

對 Operator 來說，下面這件事必須成立：同一份 `Microservice` event 被處理兩次，最終應留下同一份 Deployment、Service 與 status，而不是兩個重複資源、兩筆外部請求或一個被吞掉的錯誤。

可以用一張決策表先定義今天還沒實作的情境：

| 觀察到的狀態 | Operator 的期望動作 | 不應發生的事 |
| --- | --- | --- |
| CR 新建，child resources 不存在 | 建立或 server-side apply desired resources | 把「不存在」當作成功卻不建立 |
| CR image 改變 | 更新 Operator 擁有的 Deployment template 欄位 | 建立第二個 Deployment |
| Service 被手動刪除 | 重新收斂 Service，並留下可觀察事件 | 悄悄忽略 drift |
| Deployment 尚未 Available | `Ready=False`，保留原因與 observed generation | 建立資源後立刻寫 `Ready=True` |
| CR 被刪除 | 交由 owner reference GC child resources，或執行明確外部清理 | 手動廣泛刪除同 Namespace 所有資源 |

若 handler 遇到短暫 API error，實作時應以明確的 temporary error 與 retry policy 讓框架重試；若 schema 已知不可能恢復的資料違規，則應回報 permanent error 與清楚訊息。絕不能用廣泛 `except` 把錯誤吞掉、再把 status 偽裝成成功。

還有一個容易漏掉的前提：只監看 `Microservice` 的 create 與 `spec` 變動，不會在 child `Service` 被刪除時自動收到 CR event。實作時必須為受管 child resources 設計 owner-based event handler，或使用有明確頻率與成本上限的 timer/requeue；否則「手動刪除 Service 後會被補回」只是一句沒有 controller 事件來源支撐的承諾。

## Ownership 與 finalizer：刪除比建立更需要謹慎

Deployment 和 Service 這類純 child resources 可以設定 owner reference 指向 `Microservice`。當 CR 被刪除時，Kubernetes garbage collector 能依 ownership 清理它們；這比 Operator 自己用名稱猜測再刪除安全得多。

只有在需要清理 Kubernetes 以外的資源，例如外部 DNS record、database tenant 或 cloud load balancer 時，才值得以 delete handler 和 finalizer 暫停 CR 刪除，直到明確 cleanup 完成。Kopf 有 delete handler 時可以協助管理 finalizer，但它不能替我們判斷外部 cleanup 是否真的安全、可重試且不會永久卡住。

## 測試與驗證

Operator 尚未實作。後續會以四個狀態轉換測試它的收斂能力，而不是只看第一次 create：

```text
預期演練：
1. 建立 reminder-api CR 兩次或重送 event，確認只存在一組受管 Deployment/Service。
2. 更新 image digest，確認同一個 Deployment 的 template 更新，沒有重複資源。
3. 手動刪除受管 Service，確認 Operator 將它補回並保留可觀察的狀態或事件。
4. 讓 image 無法拉取，確認 CR 維持 Ready=False 並帶有可診斷原因，而非回報 Healthy。
```

這些情境通過後，才代表我們有一個 controller；否則只是把 YAML generation 換成了 Python。

Kopf 只減少框架樣板；可重複的 reconcile、正確的 ownership 與誠實的 `status` 仍是 controller 的責任。下一篇會把 `reminder-api` 的 `Microservice` 展開成 Deployment、Service 與 OTel 預設，並界定何時才能回報 ready。
