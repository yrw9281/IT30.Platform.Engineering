# Day 10 - Metrics、Logs、Traces：可觀測性怎麼用

## Canary 走到 10%，接下來要看什麼？

Day 09 的 Canary 發布把 `todo-api:0.1.1` 先交給一小部分流量。假設 Staging 的 CPU 沒有異常、首頁也能開啟，但測試人員回報某些清單新增待辦事項時很慢。此時 `Pod` 是 `Running`，並不能說明請求卡在哪裡，更不能判斷要繼續 promotion 還是 rollback。

發布決策需要的是可追查的證據：異常從何時開始、是否只發生在 candidate 版本、哪一段呼叫最慢，以及該請求當時留下了什麼錯誤資訊。這正是可觀測性要處理的問題。

## Monitoring 與 Observability 的分工

**Monitoring（監控）** 適合看已知風險並設定門檻。例如，五分鐘內 5xx 比例超過 1% 就通知值班者。它讓團隊知道該開始處理問題。

**Observability（可觀測性，O11y）** 則用系統輸出的訊號，調查事先沒有寫成警報條件的問題。它依賴可關聯的資料與可理解的查詢方式；只多收一批資料或多裝一套儀表板，都不會自動得到可觀測性。

| 情境 | Monitoring 先回答 | 接著用 Observability 釐清 |
| --- | --- | --- |
| `todo-api` 失敗率升高 | 是否觸發警報？ | 哪個 route、版本或下游依賴造成？ |
| 建立待辦事項變慢 | p95 latency 是否超標？ | 耗時在 BFF、`todo-api`、資料庫，還是重試？ |
| 某筆請求失敗 | 是否留下 error log？ | 它經過哪些服務，前後發生什麼事？ |

兩者必須一起工作。沒有 Monitoring，團隊可能直到使用者回報才知道異常；沒有 Observability，警報只會告訴我們「有事發生了」。

## 三種 telemetry signal 看的是同一件事

**Metrics** 是可聚合的數值序列，適合看趨勢與影響範圍，例如錯誤率、p95 latency、`Pod` restart 次數。**Logs** 記下單一事件的上下文，例如儲存 Todo 失敗時的錯誤分類、環境、版本與 trace ID。**Traces** 則描述一筆請求跨服務的因果和耗時，例如 BFF、`todo-api`、資料庫各自花了多久。

```text
Metrics：最近五分鐘的錯誤率或 p95 latency
Logs：一次儲存 Todo 失敗的錯誤碼與執行上下文
Traces：BFF -> todo-api -> database 的請求時間線
```

Metric 能先鎖定「Staging 在 10:08 到 10:13 變慢」；Trace 能找出一筆請求的 database span 花了 1.8 秒；Log 補上該事件的錯誤與業務上下文。單獨看任何一種訊號都可能誤判。

調查通常由 Metric 開始，再依序縮小範圍：

```text
error-rate / latency Metric
        │ 鎖定時間窗、服務與版本
        ▼
Trace
        │ 找出最慢或失敗的 span
        ▼
Structured Log
        │ 讀取事件的錯誤與必要上下文
        ▼
Metric
        └── 判斷是單點事件，還是系統性趨勢
```

## 先約定能把資料接起來的欄位

若 `todo-api` 的 log 寫著 `database timeout`，Trace 卻用了另一個服務名稱，Metric 也沒有環境標籤，三套後端很難拼出同一個事件。以下是規劃中的 structured log 形狀，並不表示目前服務已輸出這些欄位：

```json
{
  "timestamp": "2026-09-15T10:08:31.428+08:00",
  "level": "Error",
  "service.name": "todo-api",
  "deployment.environment.name": "staging",
  "service.version": "0.1.1",
  "trace_id": "4bf92f3577b34da6a3ce929d0e0e4736",
  "event": "todo.persist.failed",
  "message": "Todo item could not be persisted"
}
```

`trace_id` 用來由 log 回到同一筆 Trace；`service.name`、環境與版本讓三種訊號都能以相同條件查詢。這些欄位也要遵守資料最小化：使用者 email、完整 Todo 內容、`Authorization` header 與 access token 不應因為除錯方便而送入遙測資料。

Metric label 的選擇尤其需要克制。`service.name`、環境、正規化 route、status code 都是有限集合；request ID、trace ID、user ID 與原始 URL path 幾乎每次請求都不同，會產生高基數（high cardinality）時間序列，拖累 metrics backend 的成本與查詢效率。個別識別值應留在 Trace 或 Log。

## 讓 Canary 有可依據的判斷

當 `todo-api:0.1.1` 的失敗率升高，值班者可以先確認異常是否集中在 candidate 版本與特定時間窗，再開啟失敗或最慢的 Trace，分辨時間花在 BFF、Todo API 或資料庫。最後以 trace ID 查 structured log，讀取 error 分類與必要上下文；修正或 rollback 後，再回到 Metric 比較趨勢。

這不是服務上線後才補裝的附加功能。沒有這條路徑，Canary 的流量比例和 promotion 條件就缺乏足夠依據。

## 驗證目標

目前尚未部署 telemetry backend，也沒有 application instrumentation。後續應在 Staging 製造可控的慢請求，而非等事故發生才第一次練習：

```text
預期演練：
1. 對 Create Todo 注入可辨識的資料庫延遲。
2. 確認 latency Metric 在正確的 service、environment、version 維度出現異常。
3. 從異常時間窗開啟一筆 Trace，找出 database span 的延遲。
4. 以同一個 trace_id 找回 structured log，並確認其中不含 token、email 或 Todo 內容。
```

驗收重點是另一位未參與設定的工程師，能沿著這條路徑說出慢點、影響範圍，以及是否應停止發布。Day 11 會以 OpenTelemetry（OTel）定義這些資料的共同格式，讓 BFF、Account 與 Todo 不必各自綁定不同 vendor 的 SDK。
