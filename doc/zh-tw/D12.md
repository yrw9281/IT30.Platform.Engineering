# Day 12 - 用 Distributed Tracing 找出微服務的瓶頸

## 三段資料不會自己變成一次請求

Collector 可以一致地接收 telemetry，但不會自動知道 BFF 的 Create Todo 呼叫、`todo-api` 的處理，以及資料庫查詢是否屬於同一次操作。假設 BFF log 顯示 `/api/todos` 耗時 2.1 秒，`todo-api` log 又有一筆 database operation 花了 1.8 秒；中間是否還有 retry、queueing 或其他下游呼叫？光靠時間戳只能猜。

**Distributed Tracing（分散式追蹤）** 讓同一筆端到端操作共用一個 Trace，並用多個 Span 記錄各工作單位的開始、結束、名稱、attributes、狀態與父子關係。

```text
Trace: 4bf92f3577b34da6a3ce929d0e0e4736

POST /api/todos                         BFF server span        2,100 ms
└── POST todo-api /todos                HTTP client span       1,980 ms
    └── POST /todos                     todo-api server span   1,940 ms
        └── INSERT todo item            database client span   1,800 ms
```

database span 佔去 1.8 秒時，才值得往 SQL、connection pool 或 lock 調查。反之，若 BFF server span 為 2.1 秒、下游 HTTP client span 只有 50 毫秒，瓶頸更可能在 BFF 本身。

## 以 W3C Trace Context 跨越 HTTP 邊界

**W3C Trace Context** 以 HTTP header 的 `traceparent` 傳遞追蹤關係。上游注入目前 context，下游擷取後以相同 trace ID 建立 child span。

```text
traceparent: 00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01

version - trace-id                         - parent-id        - trace-flags
```

入口服務未收到有效 `traceparent` 時會建立 root span。BFF 呼叫 `todo-api` 時，將目前 context 注入 outgoing request；`todo-api` 擷取 incoming request 的 context，再建立 child span。常見 HTTP server 與 client instrumentation 通常能自動處理，但 message queue、background worker、gRPC、非同步 task 與手動建立的 HTTP client 都應列入 propagation 測試。

其中一段遺失 context，後端仍可能看見好看的 span 圖，卻無法回答端到端請求到底花了多久。

## 自動 instrumentation 負責技術邊界

HTTP、資料庫 client、runtime 等技術層操作，優先交給自動 instrumentation 產生一致的 span。手動 span 適合自動工具不知道、但業務診斷需要的邊界，例如規則驗證、排程提醒建立或第三方通知。

```csharp
// 規劃片段：僅示意業務邊界的手動 span，不代表已加入 Todo 原始碼
using var activity = TodoActivitySource.StartActivity("todo.reminder.schedule");
activity?.SetTag("todo.reminder.count", reminderCount);
```

不需要為每一行 code 建立 span。過細的 span 會增加成本與噪音；`todo.reminder.count` 能描述可聚合的批次特性，完整 Todo 內容或使用者 email 則不應成為 tag。

`traceparent` 只用於追蹤關係，並非 authentication token。OTel 的 Baggage 雖可傳遞額外 context，也會隨請求擴散，不能放 password、JWT、個資或未受信任輸入。Trace ID 是診斷索引，不是身分證明；Day 28–29 的 Service Mesh 與授權策略才處理 service identity。

## 由慢 Metric 找到具體證據

`todo-api:0.1.1` 的 error rate 升高時，可以在同一時間範圍內以 `service.name=todo-api` 和 `service.version=0.1.1` 篩選慢或失敗的 Trace。找出最長的 child span，確認它不是被父 span 重複包含的等待時間，再讀取 route、error type、database system 等安全 attributes。接著以 trace ID 查 structured log，補上 exception 分類、retry 次數或 deployment revision，最後再回看 Metrics 判斷是否為系統性趨勢。

父子 span 的 duration 不可直接相加：父 span 已包含等待 child 的時間。Trace 資料提供的是推理依據，不是可以忽略巢狀關係的加總表。

## 驗證 propagation，而非每個服務都有 Trace

目前尚未加入 instrumentation 或 tracing backend。以下是規劃中的測試請求；實作時要依實際 ingress 與驗證方式調整後才可執行：

```bash
# 規劃中的測試請求；實作時會依實際 ingress 與驗證方式調整
curl --fail \
  -H 'traceparent: 00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01' \
  -H 'content-type: application/json' \
  --data '{"title":"trace-test"}' \
  https://todo.staging.example.internal/api/todos
```

預期結果是 BFF、`todo-api` 與 database client spans 共用 `4bf92f3577b34da6a3ce929d0e0e4736`，而非各自建立新 Trace。測試資料只使用無敏感意義的 title，並確認 payload、`Authorization` header 與使用者資料沒有出現在 span attribute 或 log。
