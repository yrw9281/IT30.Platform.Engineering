# Day 01 - 序言與開始：從微服務交付走向平台工程

## 前言

上一個系列把微服務拆成可實作的服務；這個系列要面對另一個問題：服務寫完後，團隊如何穩定、快速且安全地把它交付到環境中？平台工程的目標不是替開發者增加一道流程，而是把重複的基礎設施決策收斂成可自助使用的黃金路徑。

接下來會從 Kubernetes、GitOps、可觀測性與 CI 的基礎開始，最後把它們串成具備狀態回饋與安全治理的 Internal Developer Platform（IDP）。

## 我們要解決的交付摩擦

當每個服務都要手動決定 Namespace、Deployment、監控、權限與發布方式，團隊會逐漸累積不一致的設定。平台提供的是受約束的選項，而非一套不能碰的黑盒子：開發者提交服務意圖，平台負責把它轉為一致的基礎設施與可追蹤的結果。

```text
Developer intent -> Platform contract -> GitOps -> Kubernetes
                                      <- Health and delivery status
```

## 旅程的終點

最後的 Portal 只收集服務真正需要的欄位，例如 Image、Port 與環境變數；平台再透過 `Microservice` 合約、Operator 與 Argo CD 展開部署。這條路徑也會內建 telemetry、RBAC、Policy 與 mTLS，而不是等事故發生才補上。

## 結語

今天先確立平台工程的問題邊界。明天從 Kubernetes 的宣告式 API 與控制迴路開始，理解所有自動化如何收斂。
