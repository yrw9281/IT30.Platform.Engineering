# Day 18 - 設計 `Microservice` CRD：把 Kubernetes 設定收進平台合約

## 服務表單要送出哪一種資源？

Day 17 把 Backstage 放在開發者入口，但表單不能直接變成任意 `Deployment` YAML。開發者想指定的是 `todo-api` 要使用哪個 image、對外提供哪個 port；副本數、Service selector 與觀測設定，應由平台以一致的規則處理。

Day 05 已建立 `Microservice` 的 Custom Resource Definition（CRD）與 `todo-api` 範例。這不是從零開始設計：現有 CRD 已要求 `spec.image` 和 `spec.port`，但還沒有環境變數合約或足以表達健康狀態的 conditions，也沒有將資源展開成工作負載的 Operator。這篇先核對現有合約，再決定要加什麼。

## 現有 CRD 能擋下哪些錯誤？

現有 `Microservice` 是 namespaced 資源，API group 為 `platform.example.io`，版本是 `v1alpha1`。schema 的關鍵部分如下，與 Day 05 的範例相同：

```yaml
spec:
  group: platform.example.io
  scope: Namespaced
  versions:
    - name: v1alpha1
      served: true
      storage: true
      subresources:
        status: {}
      schema:
        openAPIV3Schema:
          type: object
          properties:
            spec:
              type: object
              required:
                - image
                - port
              properties:
                image:
                  type: string
                  minLength: 1
                port:
                  type: integer
                  minimum: 1
                  maximum: 65535
```

`image` 不能是空字串，`port` 必須落在 `1` 到 `65535`。已有一筆 `port: 65536` 的錯誤範例，可在安裝 CRD 後用 Kubernetes API 的 server-side dry-run 確認它被拒絕。合法的 `Microservice` 被 API Server 接受，也只代表資料已儲存；還沒有 Operator 時，它不會自行產生 `Deployment`。

現有 `todo-api` 資源的 image 使用 `ghcr.io/yrw9281/it30-todo-api:0.1.0`。schema 只檢查它是非空字串，不會保證 image 來自核准的 GHCR repository，更不會要求使用 digest。要讓 Backstage 表單產出的設定使用 CI 的 digest，仍須由輸入驗證、Git 設定檢查與叢集政策分別守住自己的邊界。

## 補欄位之前，先分清楚由誰決定

如果 Todo 服務需要非敏感的 `LOG_LEVEL`，合約可以新增 `spec.env`，但不應因為表單需要一個欄位，就開放整段 Kubernetes `PodSpec`。

| 決策 | 由誰負責 | 目前狀態 |
| --- | --- | --- |
| 服務名稱、image、port | 服務團隊提出，API Server 驗證基本格式 | `image`、`port` 已在 CRD |
| 非敏感環境變數 | 服務團隊提出，平台限制可用名稱與值 | `env` 尚未加入 CRD |
| Namespace、目標環境、Git 位置 | 受控的團隊／環境設定與 Git review | 尚未建立設定儲存庫 |
| 副本數、label、probe、資源限制與 OTel 預設 | Operator | 尚未實作 |
| 受管資源是否可用 | Operator 觀察後回寫 `status` | CRD 只有初版 `phase` 等欄位，尚無 controller |

`env` 若採用 string map，需要在 schema 明確寫出 value 型別；Token、密碼與 connection string 不應直接放進這張表單或 Git。只靠 CRD schema 也不能驗證「這個 image 是否由授權 CI 建置」「使用者是否屬於 Todo 團隊」等跨系統規則。

## `status` 應回報哪一版資源的結果？

現有 CRD 的 `status` 定義了 `phase`、`observedGeneration` 與受管資源名稱，但沒有 controller 寫入它們，也無法靠單一 `phase` 判斷某次 image 更新是否已完成。規劃中的下一版合約會增加 `conditions`，由 Operator 在觀察 Deployment 後更新，例如 `Ready=False` 表示還在等待 Pod 就緒；確定無法自行恢復時，再明確回報卡住的原因。

關鍵是比較 `metadata.generation` 與 `status.observedGeneration`。假設新的 image 讓 generation 增加，舊版留下的 `Ready=True` 不能當作新版也健康。Argo CD 的自訂 health 判斷必須讀取當前 generation 的狀態；Backstage 顯示的服務現況也不能只看表單是否送出。

這些 conditions、環境變數與 Operator 都還是設計，本文不提供可直接套用的「新版 CRD」假片段。要修改合約，應先讓 CRD YAML、合法／非法資源與驗證結果同時存在於可執行範例中。

## 怎麼驗收合約的邊界？

就現有範例，驗證重點是：合法的 `todo-api` CR 能通過 schema、`port: 65536` 被拒絕，以及建立 CR 後不會憑空出現 Deployment。`status` 只有 schema，不代表有觀察結果。

擴充 `env` 和 `conditions` 時，再分別檢查非字串 env value 是否被拒絕、平台保留的環境變數能否在更靠近使用者的輸入層擋下，以及 Operator 是否只在讀到當前 generation 的資源狀態後回報 Ready。這些是驗收條件，現有專案尚無對應測試結果。
