# Day 18 - 從 Portal 到 Kubernetes：IDP 的控制流程

## 前一日主題回顧

Day 17 將 CI 與 GitOps 的交接點設計成一筆可 review 的 Git 變更：CI 產出 image digest，核准後才由 Argo CD 同步。這些設計仍待實作；即使完成，Todo 團隊要新增一個每天提醒未完成待辦事項的 `reminder-api`，還是得自己拼起整條流程：Namespace 怎麼選、digest 寫在哪裡、OTel 設定由誰負責、Application 名稱怎麼取，以及部署後該到哪裡確認狀態。

如果平台的答案是「這些都寫在 Wiki，照著做就好」，那它只是較完整的文件庫。開發者真正需要的是一條能把合理預設、安全邊界與可見回饋串起來的路徑，而不是更多需要記住的工具名稱。

## IDP 不等於一個表單

**Internal Developer Platform（IDP）** 是將組織交付能力組合成內部產品的系統。Portal 是使用者看到的介面，卻不是 IDP 的全部；一個 Portal 如果收到表單後直接呼叫 Kubernetes API，仍然繞過了 Git review、Argo CD health、deployment evidence 與權限分工。

以 `reminder-api` 為例，開發者希望完成的事情其實很簡單：

```text
我是 Todo team 的成員。
我要建立 reminder-api。
它使用已通過 CI 的 image digest，提供 HTTP port 8080，
並部署到 Todo team 的 Dev 環境。
```

Portal 不需要把 Kubernetes `PodSpec` 的每個欄位搬進表單。它應將這段意圖轉成能驗證、能 review、也能由 controller 收斂的部署請求。平台替常見需求維護的這條路，就是**黃金路徑（Golden Path）**。

## 先畫控制流，再開始寫 Portal

UI 與 API 都還沒實作，現在先把資料的去向、各元件能變更的範圍，以及狀態怎麼回來釐清。以下是本系列的規劃控制流與回饋流；它是設計合約，不是已可操作的系統。

```text
Developer
    │ authenticated Create Service request
    ▼
IDP Portal / API
    │ validate identity, team, contract, and image reference
    ▼
Git configuration branch -> Pull Request -> reviewed merge
    │
    ▼
Argo CD Application / ApplicationSet
    │ reconciles the approved Microservice manifest
    ▼
Kubernetes API -> Microservice CR -> Operator -> Deployment / Service
    │                                           │
    └──────── application and resource health ──┘
                        │
                        ▼
             Argo CD notification webhook
                        │
                        ▼
               IDP delivery-status database
                        │
                        ▼
                    Portal timeline
```

圖中向下的是**意圖控制流**：使用者請求最後成為 Kubernetes 的 desired state。向上的是**狀態回饋流**：叢集觀察到的結果回到提出請求的人。少了回饋流，Portal 只是「送出後請自行查看 Argo CD」的按鈕；繞過 Git 仲裁，則無法追查這次交付從何而來。

## 每個元件只負責一段可信的事

平台架構能否長期維護，通常取決於是否把責任邊界畫得夠窄：

| 元件 | 應負責的事 | 不應負責的事 |
| --- | --- | --- |
| Portal | 收集可理解的服務意圖、呈現狀態 | 直接建立 Pod 或保存 cluster credential |
| IDP API | 驗證使用者、team、輸入與 repository path，建立 Git branch/PR | 代替 Argo CD 判斷 deployment 成功 |
| Git config repository | 保存已 review 的 desired state | 保存明文 secret 或未審核的 request |
| Argo CD | 將核准的 Git revision 收斂到目標叢集 | 接受任意 Portal request 直接同步 |
| Operator | 將 `Microservice` 意圖展開為受管 Kubernetes resources，更新 status | 決定誰有權建立服務 |
| Webhook API | 驗證 delivery event、依序更新狀態 | 對外信任任何自稱 Argo CD 的 request |

這些界線也讓未來替換某個元件時不至於拖垮整條路徑。例如 Portal 可以換 UI，Git provider 可以換成不同平台，但只要「API 寫 Git、Argo CD 從 Git 拉、Operator 更新 CR status」的合約不變，核心流程仍能被推理。

## 服務交付不是布林值，而是一條狀態時間線

對使用者而言，「部署成功」並不是唯一狀態。IDP 應呈現請求正在經過哪個邊界，以及失敗是發生在輸入、review、同步還是 workload readiness。

```text
Draft
  -> Requested
  -> Validating
  -> AwaitingReview
  -> Merged
  -> Syncing
  -> Progressing
  -> Healthy

任何階段都可能轉為 Rejected、ValidationFailed 或 Degraded
```

這裡刻意把 Git merge 和 Kubernetes health 分開。`Merged` 只表示團隊同意這份 desired state；`Syncing` 表示 Argo CD 正在收斂；`Healthy` 則必須建立在 Operator 與底層資源的實際觀察上。若 Portal 將它們全部縮成綠色「Done」，排查問題時就又得回到多個工具找答案。

## 今日的最小輸入合約

在 Day 19 詳細設計 CRD 前，先定下 Portal 只應收集的最小輸入。它不是最終 API，也不是可直接送往 Kubernetes 的 YAML：

```json
{
  "serviceName": "reminder-api",
  "team": "todo",
  "environment": "dev",
  "image": "ghcr.io/yrw9281/reminder-api@sha256:******",
  "port": 8080,
  "env": {
    "REMINDER_BATCH_SIZE": "50"
  }
}
```

`team` 與 `environment` 不是讓使用者隨意填入的 deployment destination；IDP API 必須根據已驗證的身分與平台 mapping 推導 Namespace、repository path 與可用環境。image 必須是 CI 推送到 GHCR 的 digest，不是任意 image URL。secret 值也不放在這個 request 裡，避免 Portal、Git 與 telemetry 同時擴大敏感資料的暴露面。

## 測試與驗證

IDP 元件尚未實作；本日先驗證架構是否回答了必要問題。後續會以 `reminder-api` 的一次建立請求走讀完整預期路徑：

```text
預期演練：
1. Todo team 成員從 Portal 提出 reminder-api，API 僅接受允許的 team 與 environment。
2. API 建立包含 Microservice YAML 的 config branch 與 Pull Request，而不是呼叫 Kubernetes API。
3. merge 後，Argo CD 同步 CR，Operator 建立受管 resources。
4. Operator 將觀察結果寫入 CR status，Argo CD 轉成 health 狀態。
5. webhook 將該 revision 的 Healthy 或 Degraded 事件寫回 IDP，Portal 顯示同一條時間線。
```

如果任一環節只能以「某個人去看一下」補足，或任何元件同時握有不需要的 cluster、Git 與資料庫權限，這張架構圖就還沒有完成它的工作。

下一篇先收斂這條流程的輸入邊界：`Microservice` 可以讓開發者表達哪些服務意圖，又有哪些 Kubernetes 細節該留給平台決定。
