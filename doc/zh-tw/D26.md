# Day 26 - 平台安全基石：K8s RBAC 與 Namespace 多租戶隔離機制

## 前言

同一個叢集服務越多，預設信任會變成風險。Namespace 提供資源邊界，RBAC 則明確定義某個身分能在邊界內做什麼；兩者都不是多租戶的完整解答，但都是基礎。

## 讓服務帳號只讀取自身 Namespace 的 ConfigMap

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: catalog-api-reader
  namespace: commerce-dev
rules:
  - apiGroups: [""]
    resources: ["configmaps"]
    verbs: ["get", "list"]
```

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: catalog-api-reader
  namespace: commerce-dev
subjects:
  - kind: ServiceAccount
    name: catalog-api
roleRef:
  kind: Role
  name: catalog-api-reader
  apiGroup: rbac.authorization.k8s.io
```

## 最小權限的實務

避免給 application `cluster-admin`，避免用 shared ServiceAccount，並用 ResourceQuota、NetworkPolicy 與 Secret 管理補足隔離面向。Portal 的 team mapping 也必須和 Namespace ownership 一致。

## 結語

RBAC 限制「誰能做什麼」。下一篇加入 Admission Control，在資源進 API Server 前阻擋不符合平台規範的宣告。
