# Day 26 - Policy as Code：OPA Gatekeeper 怎麼檢查資源

Day 25 的 RBAC 能限制誰有權在 `todo-dev` 建立 Deployment，卻不會逐項檢查 Deployment 是否帶了資源限制、用了高權限容器，或引用未核准的 image。Argo CD 和 Operator 即使有合法的叢集身分，仍可能提交不符合平台要求的資源。這類問題要在 Kubernetes 接受資源前判斷。

這篇從機制看政策即程式碼（Policy as Code）。開放政策代理（Open Policy Agent，OPA）是可評估政策的引擎；OPA Gatekeeper 把政策接到 Kubernetes 的 Admission Webhook，依規則檢查 API 請求。目前沒有安裝 Gatekeeper，也沒有政策來源檔；以下是設計與導入判斷，不是已生效的安全防線。

## Admission 管「這次要寫入的資源」

使用者、CI、Argo CD 或 Operator 對 Kubernetes API 建立／更新資源時，API Server 在寫入前會經過 admission 階段。若 Gatekeeper 的 webhook、規則與比對範圍都已正確設定，符合條件的請求會被評估；違規時可依執行模式拒絕、警告或只記錄。

這和 CRD schema、RBAC 的問題不同：schema 問「欄位型別對不對」，RBAC 問「這個身分能不能執行動作」，Gatekeeper 則可問「這份有權提交且格式合法的 Deployment，是否滿足平台政策」。任何一層都不能取代另一層。

## 規則內容與適用範圍要分開

Gatekeeper 的 `ConstraintTemplate` 定義政策邏輯、參數結構與可使用的 constraint 類型；`Constraint` 是它的實例，決定比對哪些資源／Namespace、使用哪些參數與執行模式。以「Todo Dev 的 Deployment 必須有負責團隊 label」為例，Template 可描述怎麼判斷缺少 label，Constraint 再指定只檢查 `todo-dev` 的 Deployment。

不要把「有一份 Template」理解成「所有 Deployment 已受保護」。若沒有相應的 Constraint、比對範圍漏掉了目標資源，或 webhook 無法正常提供服務，實際保障都與預期不同。平台自己產生的 Deployment 也必須遵守規則，否則 Operator 每次執行 `reconcile` 都可能因 admission 拒絕而失敗，應把原因回報到 `Microservice.status`，不能假裝資源已成功建立。

| 觀察點 | 想回答的問題 | 容易誤會的地方 |
| --- | --- | --- |
| Admission | 新的建立／更新請求能否通過？ | 不會自動修好既有資源 |
| Audit | 叢集內現有資源有哪些違規？ | 找到違規不等於已拒絕或刪除 |
| `dryrun` | 規則會命中誰，是否有誤判？ | 可記錄違規但不阻擋請求 |
| `deny` | 要不要拒絕違規請求？ | 範圍設錯會連平台自身的資源也擋住 |

正式啟用前，應先決定政策要覆蓋 Deployment、Pod 還是兩者，盤點現有工作負載與例外，再核對 Gatekeeper 版本及 webhook 的失效處理。只在 Dev 以 `dryrun` 觀察，不能對外宣稱整個叢集已有強制政策。

## 用什麼證據判斷能否改成拒絕？

若要將 Todo Dev 的一條規則切到 `deny`，驗收應同時看合規與違規請求：缺 label 的 Deployment 被擋住，補上 label 的請求可進入，其他不在範圍內的 Namespace 不受波及，Operator 產出的資源也能通過。還要確認使用者看得懂錯誤、平台能查到 policy 版本與命中的 Constraint。

目前這些都只是**預期驗收情境**，沒有 fixture、政策或叢集結果。下一篇用三種常見的工作負載設定來看規則設計：哪些輸入應被指出、該如何修正，以及單一政策無法證明什麼。
