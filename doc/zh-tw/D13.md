# Day 13 - 在 Grafana 查看 Prometheus、Loki 與 Trace 資料

## 能看到資料，還不代表查得動問題

Day 12 定義了讓 BFF、`todo-api` 與資料庫的 span 成為同一條 Trace 的設計。可是 On-call 收到延遲警報後，若還要在 Prometheus 找時間、手動複製 service name 到 tracing backend，再將 trace ID 貼進 log search，調查時間仍耗在工具切換。

這裡規劃以 Prometheus、Loki、Tempo 與 Grafana 組成觀測介面。它們尚未部署；容量、保留期限、datasource link 與實際版本仍須在實作前確認。目標是讓人保留時間窗與服務上下文，從一種 signal 合理地走到下一種。

## 四個元件的資料流

```text
Todo applications
       │
       ▼
OpenTelemetry Collector
       ├── Metrics -> Prometheus
       ├── Logs    -> Loki
       └── Traces  -> Tempo
                         │
                         ▼
                     Grafana
              dashboards and data links
```

Prometheus 儲存與查詢時間序列 metrics，例如 error ratio、request rate、latency histogram。Loki 保存具上下文的 logs，並以少量 label 索引。Tempo 保存 Trace 與 Span。Grafana 將這些資料來源、dashboard、alert 與 data link 放在同一個調查入口；它不取代三個資料庫。

## 先為事故問題設計 dashboard

`todo-api` 的第一張營運 dashboard 不需要二十個 panel。收到「Create Todo 變慢」的回報時，應能先辨識受影響的環境、版本、route 和開始時間，接著比對錯誤率、流量、latency，以及 deployment revision；最後開啟同一時間窗的 Trace 與 Log。

先定義 `todo-api` 的 error ratio，才能讓 dashboard 顯示部署版本的錯誤趨勢。下面是規劃中的查詢；metric 名稱與 labels 要等 application instrumentation 和 Collector 設計落實後才能驗證。

```promql
sum(
  rate(todo_api_http_requests_total{
    service_name="todo-api",
    environment="staging",
    route="/api/todos",
    status_code=~"5.."
  }[5m])
)
/
sum(
  rate(todo_api_http_requests_total{
    service_name="todo-api",
    environment="staging",
    route="/api/todos"
  }[5m])
)
```

`route` 應是 `/api/todos/{id}` 這類正規化模板，而非每個 raw URL。`status_code` 也是有限集合。`trace_id`、request ID、使用者名稱不可作為 Prometheus label，否則會造成高基數。

## 從 Metric 到 Trace 需要明確設計

五分鐘 p95 latency 這類聚合 Metric 不會保留每筆 request 的 trace ID，因此 Grafana 無法從任一資料點憑空找到對應 Trace。本系列規劃以 **exemplar**，或帶時間與共同 resource filters 的 data link，補上這段關係。

```text
todo_api_request_duration_seconds_bucket{service_name="todo-api",le="2.5"} 42
  # exemplar: trace_id=4bf92f3577b34da6a3ce929d0e0e4736
```

exemplar 將少量代表性的 trace ID 附在 histogram 或 counter sample，而不把它變成高基數 Metric label。On-call 可由異常 latency bucket 開啟相關 Trace；但 exemplar 是抽樣證據，不會覆蓋每個資料點。因此 dashboard 仍需提供以時間窗、`service.name`、environment、version 篩選 Tempo 的路徑。

## 同一個欄位，在每個 backend 有不同位置

以下資料是規劃中的共同欄位，不代表目前已由任何 backend 索引：

```json
{
  "service.name": "todo-api",
  "service.namespace": "todo",
  "deployment.environment.name": "staging",
  "service.version": "0.1.1",
  "trace_id": "4bf92f3577b34da6a3ce929d0e0e4736",
  "event": "todo.persist.failed"
}
```

Prometheus 的 exporter 通常會將 `service.name` 映射為合法 label，例如 `service_name`；穩定且低基數的服務、環境、版本可經審查後成為維度。Loki 通常只將 service、environment、namespace 等穩定欄位設為 label，將 `trace_id` 留在 JSON log field 供查詢。Tempo 以 trace ID 定位 Trace，再以 resource attributes 關聯服務與環境。

可關聯不表示每個欄位都該建立索引。忽略後端的成本模型，觀測系統也會變成新的不穩定來源。

## 將調查路徑留給 On-call

理想的路徑應保留 Staging、`0.1.1`、時間範圍與服務條件：先從 Grafana 的 error ratio panel 鎖定異常，沿 exemplar 或 data link 開啟 Tempo；查看 database span 後，以 trace ID 到 Loki 讀 structured error log；rollback 或修正後，再比較 dashboard 前後的 error ratio。

Grafana 的 datasource link 設定會受 Loki、Tempo、Grafana 版本影響，`src/` 尚未有可直接套用的 config。實作時的最低驗收條件不是「panel 有畫線」，而是這條路徑不要求 On-call 背下四種查詢語法。

dashboard 也不能只看 CPU、memory 與 `Pod` restart。`todo-api` 至少還要呈現 Create Todo 成功率、p95 latency、request rate、`service.version`、GitOps revision、ready replicas，以及 Trace 與 Log 的入口。這些訊號才能回答問題是否只影響新版本、是否影響使用者操作、瓶頸在哪個階段。

## 在進入 CI 前驗證觀測路徑

所有 backend 與 Grafana 尚未實作。後續應以 Day 09 的受控慢請求，驗證 data link 是否真的縮短調查：

```text
預期演練：
1. 在 Staging 以 todo-api:0.1.1 建立一筆可追蹤的慢 Create Todo 請求。
2. 從 Grafana metric panel 鎖定異常時間窗與 version。
3. 不手動複製 service name 的情況下開啟相符的 Tempo trace。
4. 從 trace detail 帶著 trace_id 查到 Loki 的單筆 structured log。
5. 驗證 Loki 沒有將 trace_id、user ID 或完整 Todo 內容建立為 label。
```

這個觀測基礎讓團隊能在版本部署後調查問題，接下來才回到交付起點。Day 14 將從 GitHub Actions 建立 CI workflow，讓每個準備進入這條發布與觀測路徑的變更，先通過可重複的品質檢查。
