# Day 13 - 分散式追蹤 (Distributed Tracing)：微服務跨節點瓶頸定位實戰

## 前言

單一服務的 log 無法呈現一筆請求跨越 API、下游服務與資料庫的等待時間。Distributed Tracing 以 trace 與 span 建立因果關係，前提是 context 能在每個協定邊界正確傳遞。

## W3C Trace Context 的傳遞標頭

```text
traceparent: 00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01
```

入口服務建立 server span；呼叫下游時把 context 注入 HTTP header；下游再從 header 擷取並建立 child span。資料庫操作則建立 client span，並只記錄經過審查的 query metadata。

```text
GET /catalog
  catalog-api (server span)
    inventory-api (client/server spans)
      PostgreSQL (client span)
```

## 排查順序

先從慢請求的 trace 找最長 span，再跳到關聯 logs 確認錯誤上下文，最後以 metrics 判斷這是單點還是系統性退化。

## 結語

Trace 將跨服務時間線接起來。明天把 tracing、metrics 與 logs 放進 Grafana 的統一操作介面。
