# Day 11 - OpenTelemetry 的資料格式與元件

## 同一個服務，不能有三種名字

昨天的調查流程假設 Metric、Log、Trace 可以用服務名稱、環境與 trace ID 互相對照。實務上，Account、Todo、BFF 往往由不同人、不同語言與不同時間開發。若每個服務直接接不同 observability vendor 的 SDK，`todo-service`、`TodoAPI` 與 `todo-api` 很快就會同時出現在 dashboard；即使資料都送到了，仍然無法可靠地關聯。

OpenTelemetry 提供的是這套共同語言，而不是另一個監控產品。

## OTel 定義資料怎麼產生與傳遞

**OpenTelemetry（OTel）** 是開放的 observability framework 與規範。它定義 application 如何建立 telemetry、常見欄位的語意，以及資料如何傳輸；Grafana、Prometheus、Loki 或任何 SaaS backend 仍各自負責儲存、查詢與呈現。

| 元件 | 責任 | Todo 系統中的用途 |
| --- | --- | --- |
| API | 提供建立 span、metric、log 的抽象介面 | BFF 與 Todo 以相同介面加入 instrumentation |
| SDK | 實作 API，處理 sampling、processor、exporter | 在啟動時將 telemetry 送往 OTLP |
| Semantic Conventions | 定義欄位名稱與值的共同語意 | 所有服務的 `service.name` 意義一致 |
| OTLP | OpenTelemetry Protocol，傳輸資料的協定與格式 | application 和 Collector 的資料通道 |
| Collector | 接收、處理與轉送資料 | 將 backend 細節移出 application |

```text
Todo / BFF / Account application
        │ OTel API + SDK
        ▼
OTLP
        ▼
OpenTelemetry Collector
        ▼
Metrics、Logs、Traces backends
```

## Resource attributes 是跨訊號的座標

OTel 用 resource attributes 描述遙測資料的來源。它們不是每次 HTTP request 都會變動的欄位，而是工作負載、環境與版本的共同身分。以下是規劃中的 Todo 服務合約，尚未在 `src/` 實作：

```yaml
# 規劃片段：Todo 服務共用的 OTel resource contract
service.name: todo-api
service.namespace: todo
service.version: "0.1.1"
deployment.environment.name: staging
```

`service.name` 是跨 signals 查詢的主要條件；`service.namespace` 表示邏輯服務群組，不必等同 Kubernetes Namespace；`service.version` 用於比較 Canary 的 stable 與 candidate；`deployment.environment.name` 避免 Dev 資料混進 Staging。

HTTP method、route、response status 與錯誤類型則屬於單次操作的 attributes。把每個 request attribute 都提升為 resource，會失去穩定的聚合維度；收集 request body 也沒有必要，且會增加敏感資料外洩風險。

## Application 只需要知道 OTLP endpoint

在尚未加入實際 SDK 前，可以先規劃由環境變數提供基本 OTel 設定。實作時仍要依 Todo 專案的語言、SDK 套件與部署模型確認支援情況；下面不是已可套用的設定。

```bash
# 規劃片段：todo-api container 的 OTel 設定
OTEL_SERVICE_NAME=todo-api
OTEL_EXPORTER_OTLP_ENDPOINT=http://otel-collector.observability.svc:4318
OTEL_RESOURCE_ATTRIBUTES=service.namespace=todo,deployment.environment.name=staging,service.version=0.1.1
```

application 對外只依賴標準的 OTLP endpoint。未來更換 trace backend、增加 logs exporter，或調整 retry 與 batch 策略時，服務端不必同時改寫 vendor-specific code。

可攜性仍有邊界。不同語言的自動 instrumentation 覆蓋範圍不一，Semantic Conventions 會演進，sampling 也可能不保留某些 Trace。平台需要明定最低共通欄位與升級策略，不能把安裝 SDK 當成資料品質的保證。

## Collector 是集中治理點

本機實驗時，application 可以直接把 OTLP 傳給 backend；平台通常還需要 Collector 統一處理 retry、batch、記憶體保護與 sampling，補上或驗證 environment、cluster 等資源資訊，並在資料離開 workload 前移除敏感 attributes。它也能將同一種 signal 路由至多個 backend，讓 application 不必認識供應商設定。

Collector 不是安全魔法。application 若一開始就把 password 寫進 span，Collector 只能降低外流機率；第一道防線仍是 application 不要建立這種資料。

## 驗證共同合約

目前沒有 OTel SDK 或 Collector。後續實作時，先確認合約是否一致，再檢查 dashboard：

```text
預期演練：
1. 從 BFF 發出一筆 Create Todo 請求。
2. 確認 BFF、todo-api 的 telemetry 都具有一致的 service.namespace 與 environment。
3. 確認跨服務的 Trace 使用同一個 trace ID。
4. 檢查 Log、Metric 與 Trace 不含 Authorization header、token、email 或 Todo 內容。
```

若服務名稱或環境名稱已經分裂，後續的 Collector 與 Grafana 設定無法補救。Day 12 會處理 Collector 的 Receiver、Processor 與 Exporter，將這份合約放進實際資料管線。
