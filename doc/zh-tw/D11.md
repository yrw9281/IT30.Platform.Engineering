# Day 11 - 部署與設定 OpenTelemetry Collector

## 不要把營運規則散在每個服務裡

Day 10 定義 application 以 OTLP 輸出遙測資料。若每個服務各自維護 retry、採樣、敏感欄位過濾，以及三個 backend endpoint，平台只是在另一個地方累積設定差異。backend 暫時不可用時，application 該重試多久；發現不應送出的 attribute 時，又要改多少 repository？這些都是跨服務的營運決策。

OpenTelemetry Collector 適合集中處理它們。本文的設定均為概念設計，`src/` 尚未提供 Collector manifest 或可部署的設定檔。

## Pipeline 的順序就是治理規則

Collector 將資料流分成 Receiver、Processor 與 Exporter：

```text
Receiver
  接收資料，例如 OTLP/gRPC 或 OTLP/HTTP。
       │
       ▼
Processor
  保護記憶體、補充屬性、過濾或脫敏、批次處理。
       │
       ▼
Exporter
  以目標 backend 支援的協定送出資料。
```

敏感資料若先被 exporter 送出，再由另一個 processor 刪除，已經來不及補救。高流量下若少了記憶體保護，Collector 可能因 OOM 重啟，反過來放大 application 的 retry 壓力。

## Agent、Gateway 與 Hybrid 的取捨

| 模式 | 常見部署形態 | 適合情境 | 代價 |
| --- | --- | --- | --- |
| Agent | 每個 Node 一個 `DaemonSet` | 就近收集 container log 或 Node metadata | 每個 Node 都有資源與升級負擔 |
| Gateway | 集中的 `Deployment` | application 直接送 OTLP，需要集中路由與治理 | 需規劃容量與高可用 |
| Hybrid | Agent 收集後交給 Gateway | 大型、多叢集或多資料來源環境 | 管線與除錯路徑較複雜 |

本系列先規劃 Gateway：Todo 服務量仍小，目標是讓 application 將 OTLP 送到單一治理點。收集 Node 層級資料或跨叢集彙整時，再評估 Hybrid，不必一開始就建立兩層 pipeline。

## traces pipeline 的概念設定

以下片段呈現處理順序與意圖。endpoint、記憶體限制、保留欄位均應依實際流量與資料分類調整，不能直接視為 Production 設定。

```yaml
# 規劃片段：otel-collector-config.yaml
receivers:
  otlp:
    protocols:
      grpc: {}
      http: {}

processors:
  memory_limiter:
    check_interval: 1s
    limit_mib: 512
    spike_limit_mib: 128
  resource/platform:
    attributes:
      - key: platform.name
        value: todo-platform
        action: upsert
  attributes/remove-sensitive:
    actions:
      - key: enduser.id
        action: delete
  batch:
    timeout: 5s
    send_batch_size: 1024

exporters:
  otlphttp/traces:
    endpoint: https://traces.example.internal

service:
  pipelines:
    traces:
      receivers: [otlp]
      processors:
        - memory_limiter
        - resource/platform
        - attributes/remove-sensitive
        - batch
      exporters: [otlphttp/traces]
```

`memory_limiter` 先限制資源壓力；`resource/platform` 補上平台共同識別；`attributes/remove-sensitive` 必須在 exporter 前執行；`batch` 將完成安全處理的資料合併送出。範例中的 `enduser.id` 僅是待移除的測試欄位，不表示 application 應主動蒐集終端使用者身分。

logs 與 metrics 也遵循「先保護、後轉送」的原則，卻不必共用完全相同的 processors。metrics 要避免高基數 label，logs 可能需要不同的 redaction 規則。

## debug exporter 只留在受控環境

debug exporter 可在開發與測試環境確認資料是否送進 Collector，但它可能將 attributes 印入 Collector log。因此，它不適合作為 Production backend，且仍應在脫敏後才使用。

```yaml
# 規劃片段：僅限非 Production 的驗證 exporter
exporters:
  debug:
    verbosity: basic

service:
  pipelines:
    traces/debug:
      receivers: [otlp]
      processors: [memory_limiter, attributes/remove-sensitive]
      exporters: [debug]
```

實作時須確認同一筆資料不會沿著不同順序的 pipeline，將未脫敏 payload 送出。為了除錯而列印完整 payload，本身就是資料外洩風險。

application 不產生不必要的敏感 telemetry，SDK 與 logging policy 限制可收集欄位，Collector 集中防呆，backend 再以存取控制、retention 與 audit 保護保存資料。任何一層失誤時，才不會只剩最後一道防線。

## 驗證資料真的經過管線

Collector 尚未部署。後續可送入受控的 OTLP 測試 span，刻意攜帶應移除的 `enduser.id`：

```text
預期演練：
1. 將帶有 service.name、environment 與 enduser.id 的測試 span 送入 OTLP receiver。
2. 確認 Collector 未因 batch 壓力超過設定的記憶體限制。
3. 在非 Production 的 debug exporter 或測試 backend 確認 platform.name 存在。
4. 確認所有 exporter 輸出都不含 enduser.id。
```

`Collector Pod` 為 `Running` 不是驗收結果；必須證明資料依序被補充、脫敏、批次化並轉送。Day 12 會把 Trace Context 帶進 BFF、`todo-api` 與資料庫之間的呼叫。
