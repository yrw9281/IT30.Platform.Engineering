# Day 24 - 在 Backstage 查看服務與 Kubernetes 部署狀態

## 開發者現在能查到什麼？

前一篇的自訂 Health Check 說明 Argo CD 怎麼判斷 `Microservice`；那是**規劃中的判斷**，目前沒有 Operator 寫入 `Ready`／`Stalled`，也沒有套用 health 設定。如果要讓服務擁有者有地方查看現有工作負載，Backstage 的 Software Catalog 與 Kubernetes plugin 可以先處理「找服務、看資源」這件事，不必為了一個狀態畫面自製 Portal 與交付資料庫。

Catalog 的 `Component` 描述服務及負責人；Kubernetes plugin 依 entity 上的 annotation 與叢集連線，查詢相關資源。它需要 frontend、backend、叢集讀取權限與設定，並不會因為有一份 Catalog YAML 就顯示畫面。

## 先關聯已存在的 Todo API

現有 Deployment 與 Pod 有 `app: todo-api` label，位於 `todo` Namespace。Catalog 範例以這兩個條件描述要查找的資源：

```yaml
metadata:
  name: todo-api
  annotations:
    backstage.io/kubernetes-namespace: todo
    backstage.io/kubernetes-label-selector: app=todo-api
```

這是**現有原生 Kubernetes 資源**的關聯範例，不是 Operator 已建立的 `Microservice`。前面 Template 規劃產出的 CR 放在 `todo-dev`；若日後 Dev 的受管 Deployment、Pod 改在那個 Namespace，必須另外調整服務關聯設定與 plugin 的叢集查詢範圍，不能用 `todo` 的畫面冒充 Dev 部署結果。Operator 產出的資源也得帶有能對應的 label，否則 Catalog 查不到。

## 資源現況不等於交付歷史

Backstage Kubernetes plugin 可以呈現關聯的 Deployment、Pod 等資源及可觀察到的錯誤；它沒有替本系列記錄每一次設定 PR 的 review、CI image digest 驗證、merge 與所有 health 轉換。即使日後 Argo CD 能回報 `Microservice` health，也不能只靠 Kubernetes plugin 的資源列表推回完整時間線。

因此查問題時，資訊要回到各自的來源：CI 查 image 產出、Git PR 查誰審查與合併、Argo CD 查同步 revision 與 Application health、Kubernetes 查 Deployment／Pod 現況。Backstage 可連結或整合這些資訊，但**目前沒有安裝 Backstage、Argo CD 與 Catalog 的整合元件，也沒有自製事件儲存服務**。如果產品確實需要跨系統的交付事件歷史，應先說清楚事件來源、可靠性與維護成本，再決定是否補專用元件；不把它說成 Backstage 的預設功能。

## 驗證範圍

現在能核對的是 Catalog 範例的 Namespace／label selector 與既有 Todo API 原生 manifest 相符。只有等 Kubernetes plugin 安裝並能以受限憑證連上叢集，才能實際驗證：打開 `todo-api` entity，確認它只顯示預期的 Deployment／Pod，能看到權限錯誤而不是空白成功畫面；Pod 不健康時，畫面也不能因 Git 已同步就說服務健康。這些 UI 與權限測試**尚未執行**。

自助交付的入口、Git 審查與狀態查詢各有邊界。下一步要限制的是誰能在叢集操作哪些資源；入口頁面顯示的 `owner` 不能取代 Kubernetes 的 Namespace 與 RBAC 權限。
