# Day 24 - 在 Backstage 查看服務與 Kubernetes 部署狀態

## 開發者現在能查到什麼？

前一篇設計了 `Microservice` 的 Health Check，但目前還沒有 Operator 回寫 `Ready`／`Stalled`，health 設定也尚未套用。另一方面，Todo 的原生工作負載已經有可查詢的資源；服務團隊不必等整條 CR 交付路徑完成，才開始規劃查詢入口。

Backstage 的 Software Catalog 可以讓人找到 `todo-api`，Kubernetes plugin 再查詢相關資源。這篇整理兩者如何關聯，以及畫面上的資源現況能回答什麼；目前只有 Catalog 設定範例，還沒有完成 plugin 與叢集的整合，不需要為了這個查詢入口另外建立 Portal 或交付資料庫。

## 先關聯已存在的 Todo API

Catalog 範例在 `todo-api` entity 上指定 Namespace 與 label selector，讓 Kubernetes plugin 知道要查詢哪組資源：

```yaml
metadata:
  name: todo-api
  annotations:
    backstage.io/kubernetes-namespace: todo
    backstage.io/kubernetes-label-selector: app=todo-api
```

這組條件指向 `todo` Namespace 中帶有 `app=todo-api` 的資源。既有 `Deployment` 的 Pod template 有這個 label，所以建立的 Pod 能符合條件；但 `Deployment`、`Service` 本身的 `metadata.labels` 尚未設定它。`spec.selector` 用來選 Pod，不等於資源本身有相同 label，不能據此宣稱 plugin 已能列出整組工作負載。

要讓同一 selector 查到需要的資源，必須先統一它們的 metadata labels，並確認沒有把其他服務一起選進來。Operator 產生資源時，也應維持相同的查詢合約。

環境同樣不能混用。Software Template 的目標是 `todo-dev`，這份 Catalog 設定卻指向 `todo`。即使既有 Pod 看起來正常，也不能拿它當作 Dev 版本更新的結果；查詢新環境時，entity 的關聯條件與 plugin 可讀取的叢集、Namespace 都要一起確認。

## 查詢會經過哪些元件？

Kubernetes plugin 需要前端元件、後端 plugin、叢集連線與讀取權限。Catalog YAML 只提供關聯資訊，不會自行建立這些元件。下圖是完成設定後的查詢方向；現階段尚未接通。

```mermaid
flowchart TD
    Developer["開發者<br/>開啟 todo-api entity"]
    Catalog["Software Catalog<br/>提供服務資訊與 annotation"]
    Frontend["Kubernetes plugin 前端<br/>呈現資源或查詢錯誤"]
    Backend["Kubernetes plugin 後端<br/>使用受限身分查詢目標叢集"]
    API["Kubernetes API<br/>檢查讀取權限與查詢條件"]
    Current["todo｜既有環境<br/>Pod 符合 app=todo-api<br/>Deployment、Service metadata labels 待補"]
    Dev["todo-dev｜規劃環境<br/>尚未建立，不以 todo 的狀態代替"]

    Developer --> Catalog
    Catalog -->|"Namespace 與 label selector"| Frontend
    Frontend -->|"請求資源現況"| Backend
    Backend --> API
    API -->|"查詢 todo"| Current
    Current -->|"資源觀察結果"| Backend
    Backend -->|"回傳結果或明確錯誤"| Frontend
    Catalog -.->|"若要查 Dev，需另設正確關聯與權限"| Dev
```

後端能讀取哪些資源，以及登入 Backstage 的人能看到哪些服務，也需要各自限制。Catalog 的 `owner` 只是負責團隊資訊，不能把它當成 Kubernetes 的授權規則。遇到權限不足、叢集無法連線或 selector 找不到資源時，畫面應能區分原因，不要一律顯示空白列表。

## 資源現況不等於交付歷史

完成關聯後，Kubernetes plugin 可以呈現支援的 `Deployment`、Pod 等資源與可觀察到的錯誤，但不會因此記錄每筆 PR 的 review、digest 驗證、合併與所有 health 轉換。自訂的 `Microservice` 和 Argo CD `Application` 也不能假設會自動出現在預設畫面，仍要確認 plugin 的資源支援與整合設定。

例如，`todo-api` 現在有兩個就緒 Pod，可以幫助判斷工作負載現況，卻不能回答誰核准了這個版本。後者要回到 Git PR；image 從哪個 commit 建出來要看 CI；核准設定是否同步則看 Argo CD 的 revision 與 health。Backstage 可以連結或整合這些來源，但查詢入口不等於歷史資料庫。

如果確實需要完整的交付時間線，就得另外定義事件來源、保存方式、漏收事件時的處理與維護責任。目前沒有這種事件儲存服務，也沒有完成 Backstage 與 Argo CD 的整合。

## 驗證範圍

目前只能從 Catalog 與原生 manifest 核對 Namespace、selector 與 label，並找出前述的資源標籤缺口。完成 plugin 設定後，才有辦法驗收畫面：

| 情境 | 應確認的結果 |
| --- | --- |
| 查詢 `todo-api` | 只列出目標叢集、Namespace 中與服務相關的資源 |
| selector 沒有匹配 | 顯示找不到資源，不解讀為服務健康 |
| 查詢身分權限不足 | 顯示存取錯誤，能與沒有資源區分 |
| Pod 尚未就緒 | 呈現工作負載的實際狀態，不因 Git 已同步就宣稱健康 |
| 改查 `todo-dev` | 不沿用 `todo` 的資源，確認新的關聯與讀取範圍 |

這些 UI 與權限情境尚未測試，截圖也仍待執行環境備妥後補上。
