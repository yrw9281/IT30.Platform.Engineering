# Day 07 - 用 Argo CD 將 Git 的 YAML 同步到 Kubernetes

## 前一日主題回顧

Day 06 將 `todo-platform-config` 定義為環境期望狀態的仲裁者，但 Git repository 不會自行讀取 commit，也不會對 Kubernetes API 做 reconcile。我們需要一個常駐在叢集內、知道該信任哪個 repository，並能回報同步與健康結果的 controller。

Argo CD 就是這個 controller。它不會取代 Kubernetes controller，而是在 Kubernetes 之上加一層 GitOps 控制迴路：觀察 Git 的 manifests、比對叢集內的 resources，再依同步政策處理差異。

## Argo CD 如何讀 Git 並寫入叢集

初學 Argo CD 時，很容易把它當成「有 UI 的 `kubectl apply`」。實際上，它以 `Application` 作為部署合約，將 Git source、manifest path、目標叢集與 Namespace 綁在一起。

```text
Git commit
    │
    ▼
Repo Server 取回並渲染 Kustomize / Helm / plain YAML
    │
    ▼
Application Controller 比較 desired 與 live state
    │
    ├── OutOfSync：差異存在，等待或執行 sync
    └── Synced：受管資源已套用到預期 revision
             │
             ▼
       Health assessment：資源是否真的準備好？
```

API Server 與 Web UI 供人或自動化工具查看、建立 `Application`；Repo Server 取得並渲染 Git 內容；Application Controller 比對並同步。實作時，repository credential 應只有讀取權限，Argo CD 對目標 Namespace 的權限則由 `AppProject` 與 Kubernetes RBAC 一起限制，不應預設擁有所有叢集資源。

## `Application` 定義一個部署邊界

以下是規劃中的 `todo-api-dev` `Application`，用來說明各欄位如何限制部署範圍。本專案目前的 `src/` 沒有對應 manifest，也尚未部署 Argo CD；請先在 `src/` 建立對應檔案並填入實際 repository、叢集與權限設定，再複製這個概念片段。

```yaml
# 規劃片段：platform/argocd/todo-api-dev.yaml
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: todo-api-dev
  namespace: argocd
  finalizers:
    - resources-finalizer.argocd.argoproj.io
spec:
  project: todo
  source:
    repoURL: https://github.com/example/todo-platform-config.git
    targetRevision: main
    path: apps/todo-api/overlays/dev
  destination:
    server: https://kubernetes.default.svc
    namespace: todo-dev
  syncPolicy:
    automated:
      prune: true
      selfHeal: true
    syncOptions:
      - CreateNamespace=true
```

`source` 定義要相信哪份 Git 內容；`destination` 定義可套用到哪裡。兩者都是安全邊界。`AppProject` 應限制 Todo 團隊只能使用核准的 repository 與 `todo-*` Namespace，避免 `Application` 指向其他團隊或 cluster。

`finalizers` 定義刪除 `Application` 時如何處理它管理的 resources，這是需要刻意決定的生命週期。`CreateNamespace=true` 只會在 Namespace 不存在時建立它，不能取代 Day 26 會補上的 Namespace baseline、RBAC 與 quota。

## `Synced` 不等於服務已可正常使用

Argo CD 顯示的狀態至少要分兩層看：

- `Synced`：Git revision 對應的資源宣告，已成功被套用並與 live manifests 沒有差異。
- `Healthy`：Argo CD 根據各資源的 health assessment 判斷它們已達可用狀態。

若 image 無法拉取，`Deployment` 仍可能成功建立。因此 Application 可能是 `Synced`，但 Pod 不會 ready，整體 health 仍是 `Progressing` 或 `Degraded`。`Healthy` 也不是 SLO 保證，它不會告訴我們建立 Todo 的 p99 latency 是否超標。這是後面要加入 observability 的原因。

可以把一次預期中的交付想成這樣：

```text
configuration PR merged
  -> Application detects a new Git revision
  -> OutOfSync
  -> resources applied
  -> Synced + Progressing
  -> Pods ready
  -> Synced + Healthy
```

## 啟用自動同步前，先確認資源邊界

`automated.prune` 讓 Git 已刪除的受管 resources 被一併刪除；`selfHeal` 讓手動 drift 回到 Git 宣告。這兩個選項在 Dev 往往很合理，在 Production 則需要更嚴謹的 review、緊急處置流程與 resource ownership 設計。

例如，若把不屬於 Application 的共享 `ConfigMap` 放入同一路徑，之後又在整理 YAML 時刪除，Argo CD 若將它視為受管 resource，`prune` 可能照著宣告刪除它。自動化無法判斷這是不是疏失，因此越自動的路徑越需要清楚的資源邊界。

## 測試與驗證

Argo CD 目前尚未部署，以下指令不能直接執行。先在 `src/` 建立相符的 manifest、部署 Argo CD 並設定 `Application` 後，從 revision 改變開始驗證，而不只從 UI 按鈕確認：

```bash
# 檢查 Application 綁定的 source、destination、sync 與 health 狀態
argocd app get todo-api-dev --refresh

# 等待指定 revision 的資源同步並達到健康狀態
argocd app wait todo-api-dev --sync --health --timeout 300

# 發生問題時，從 Application 事件回查是哪個 resource 卡住
kubectl describe application todo-api-dev -n argocd
```

驗收時應能區分三種狀態：Git 有新 revision 但尚未同步、資源已套用但 Pod 尚未健康，以及所有受管資源已健康。不能只因看到 `Synced` 就視為上線成功。

`Application` 讓一個 Git 路徑與一個部署目標形成可追蹤的合約。不過 `todo-api` 有 Dev、Staging、Prod，未來也不只一個服務。Day 08 會由 `ApplicationSet` 根據目錄或清單生成這些重複的 `Application`，避免以複製貼上維持一致性。
