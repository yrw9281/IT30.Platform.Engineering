# Day 17 - CI 完成後，怎麼把 Image 更新交給 GitOps

## 前一日主題回顧

Day 16 的設計讓 CI 產生 `todo-api` 的 immutable digest。接下來很容易想讓 workflow 拿著 digest 直接部署到 Staging 或 Production。這樣做雖然省事，卻會讓同一個 CI job 同時持有 source read、GHCR push 與 cluster write 等能力，也可能繞過 Git review。

問題不只在權限範圍變大。build workflow、第三方 action 或 runner 被誤用時，錯誤腳本就能直接改變環境；部署理由也只留在 workflow log，沒有出現在團隊能 review 的 configuration history。

## 用一筆 Git 變更交接 CI 與 CD

較容易追查的流程是：CI 成功後，將已驗證 image 的 digest 寫入 GitOps configuration repository 的 branch，然後建立 Pull Request。review 通過並 merge 到受保護 branch 後，Argo CD 才讀到新的 desired state，並同步到目標叢集。

```text
source commit
  -> CI test / build / scan
  -> image digest
  -> config repository branch
  -> image-update pull request
  -> review and merge
  -> Argo CD detects revision
  -> Kubernetes reconciles resources
```

每個角色都會在自己的交接點留下證據：

- application CI 證明某個 source commit 產出了哪個 image digest。
- config PR 表達哪個環境將採用哪個 digest，以及誰核准。
- Argo CD 記錄哪個 config revision 被同步，以及 Kubernetes 最後觀察到什麼健康狀態。

## GitOps 變更應小到能被人看懂

Day 04 的 Kustomize overlay 很適合作為 image promotion 的交接面。CI 不需要重寫 Deployment、Service 或 Ingress，只要更新目標環境的 image digest。下列 YAML 尚未存在於目前 repository，僅用來說明 config PR 應有的最小變更。

```yaml
# 規劃片段：apps/todo-api/overlays/staging/kustomization.yaml
images:
  - name: ghcr.io/yrw9281/todo-api
    newName: ghcr.io/yrw9281/todo-api
    digest: sha256:******
```

reviewer 應能從 config PR diff 直接看出：`todo-api` 的 Staging 由舊 digest 改為新 digest，其他資源沒有變動。若 CI 還重排大量 YAML、更新無關 Chart 或修改 Namespace，這筆變更就很難審查。

同一個 image 要推進 Production 時，也應另外建立針對 Production overlay 的變更。promotion 因此是明確決策，而不是 Staging build 綠燈後讓 Production 跟著 tag 移動。

## 權限要沿著資料流切開

最小權限不只是 workflow 裡的一行 `permissions`，還要沿著資料流劃清每個身分能做的事：

| 身分 | 應有的能力 | 不應有的能力 |
| --- | --- | --- |
| PR CI | 讀 source、跑 test | 推 image、寫 config repo、寫叢集 |
| Release CI | 讀已核准 source、推指定 image、建立 config PR | 直接 merge protected branch、寫 Kubernetes |
| Config reviewer | 核准或拒絕環境變更 | 修改 image bytes、取得 GHCR push credential |
| Argo CD | 讀核准 config、對指定 Namespace reconcile | 改 application source、寫任意 cluster |

實作時，config repository 可使用權限範圍明確、可輪替的 GitHub App installation token 或同等的短期身分，不要將長期 Personal Access Token 放進 workflow secret。branch protection 必須要求必要檢查與 review；CI 自動建立 PR 不代表 CI 可以自行 merge 到 Production。

## 讓交付鏈可以反向追查

部署後出現問題時，團隊應能從部署端一路往回查：

```text
Argo CD Application revision
  -> config repository merge commit
  -> image digest in Kustomize overlay
  -> CI run that emitted the digest
  -> source commit and pull request
```

反過來，這條鏈也能回答某個 source commit 是否已進入 Production。任何一段若靠手動複製 tag，或以未記錄的 `kubectl` 操作跳過，就會失去追溯性。緊急修復也要回寫 Git，否則下次 Argo CD self-heal 或環境重建可能覆蓋這次修復。

## Config repository 也需要自己的品質閘門

source CI 綠燈不代表 Kustomize 一定能渲染，也不代表 image digest 寫在正確環境。config PR 需要獨立檢查，例如：

```text
config PR checks:
- Kustomize build 產生有效 manifest
- Kubernetes server-side dry-run 驗證 schema
- image reference 符合 `ghcr.io/yrw9281/` 與 digest 格式
- 後續導入的 admission policy 預檢
```

這些檢查不應使用 Production cluster 的寬鬆憑證。能在隔離環境、schema validation 或 policy engine 完成的檢查，不該為了方便而直接改動正式環境。

## 測試與驗證

目前沒有 GitHub App、config repository、GHCR package 或 Argo CD 實作，無法驗證上述流程。建置完成後，可選一個已知 source commit 走完整條鏈：

```text
預期演練：
1. 從成功的 Todo CI run 記下 source SHA 與 image digest。
2. 確認 workflow 只建立 Staging config PR，沒有 Kubernetes API 呼叫。
3. 確認 PR diff 只改變 Staging overlay 的 digest，並通過 config checks。
4. merge 後，確認 Argo CD Application revision 指向該 config commit。
5. 從 deployment image digest 反向找回相同的 CI run 與 source SHA。
```

若其中任何一步只能靠人工記憶回答，表示交付邊界仍有缺口。
