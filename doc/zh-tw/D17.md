# Day 17 - 從 Backstage 到 Kubernetes：IDP 的控制流程

## 一份 image，要怎麼交到開發者手上？

Day 16 將 CI 與部署分開：Todo API 的 release workflow 能產出 image digest，但還沒有建立 GitOps 設定 Pull Request。即使把這段接上，開發者要替 `todo-api` 更新版本，仍得知道設定寫在哪裡、誰能審查，以及合併後到哪裡確認服務是否可用。

平台工程要處理的是這些反覆出現的交付工作。**內部開發者平台（Internal Developer Platform，IDP）** 不是某個產品的名稱，而是一組讓團隊能依規則交付、查詢和維護服務的能力。本系列選 Backstage 作為開發者入口；它提供服務目錄與表單，但不會取代 Git review、Argo CD 或 Kubernetes Operator。

## Backstage、GitOps 和 Operator 各負責哪一段？

假設 Todo 團隊要將 `todo-api` 的新 digest 送進 Dev。規劃中的路徑是：

```text
已核准的 todo-api image digest
  -> Backstage Software Template 確認固定的服務與 Dev 環境，收集 digest
  -> Git 設定 Pull Request，review 後合併
  -> Argo CD 同步 Microservice 資源
  -> Operator 依 spec 建立或更新 Deployment、Service
  -> Backstage 查詢服務與 Kubernetes 資源的目前狀態
```

向下走的是**部署意圖**：誰要使用哪個 image、部署到哪個環境，經審查後成為 Git 中的設定。向上查的是**目前狀態**：Kubernetes 有哪些資源、Pod 是否準備好。查到當下的狀態，不等於擁有從申請到每次健康變化的完整事件時間線。

這條路徑目前仍是規劃。現有 release workflow 只輸出 digest；Argo CD 的 `Application` 讀取原生 Kubernetes 設定，沒有同步 `Microservice`；CRD 雖已定義 `image`、`port`，卻沒有 Operator。專案也尚未安裝 Backstage 或建立獨立的設定儲存庫，因此不能照著上圖直接建立服務。

## Backstage 的目錄與表單不是同一件事

Backstage 的 **Software Catalog** 整理服務名稱、擁有者與相關資訊，讓開發者找到 `todo-api`；Catalog 中的 `Component` 是 Backstage 的服務紀錄，不是 Kubernetes 的 `Microservice` 資源。**Software Templates** 則提供填寫服務需求並執行建立步驟的入口。模板可以產生設定、提出 Git Pull Request，但必須另外安裝並設定對應的 GitHub action，不能只建立一張表單就假設 Git 變更已送出。

| 元件 | 要處理的事 | 不替誰做決定 |
| --- | --- | --- |
| Backstage Catalog / Template | 找到服務、收集受控輸入、提出 Git 變更 | 不直接判定叢集已部署成功 |
| Git Pull Request | 審查要使用的 digest、環境與設定差異 | 不自動證明服務健康 |
| Argo CD | 讀取核准的 Git 設定並同步資源 | 不建置 image、不代替 Operator 展開 `Microservice` |
| Operator | 依 `Microservice.spec` 管理受管資源與 `status` | 不決定誰可以核准 Git 變更 |
| Kubernetes plugin | 查詢與服務關聯的叢集資源現況 | 不自動提供完整的 PR 審查與交付事件歷史 |

Backstage Software Template 也不能讓瀏覽器任意指定 Git path、目標 branch 或 Kubernetes Namespace。這些值應來自受控設定與已驗證的團隊身分；表單只開放服務真正需要決定的欄位。Git token 留在受限的後端，設定儲存庫仍以獨立檢查及 protected branch 擋住不合格變更。

## 如何知道服務真的已經更新？

從 Backstage 按下「建立」後，模板任務完成最多代表它指定的步驟已完成。Pull Request 建立、合併、Argo CD `Synced`、Pod `Ready` 分別是不同事件，不該合成一個「部署成功」。如果要在 Backstage 看見 Kubernetes 工作負載，需要安裝 Kubernetes frontend/backend plugins、設定可讀取的叢集身分，並把 Catalog 服務與目標資源關聯起來。

我們可以先用 `todo-api` 檢查這張架構圖是否回答了問題：CI 的 digest 放在哪裡？誰能改設定與核准？Argo CD 實際讀哪個來源？Operator 收到 CR 後會建立什麼？Backstage 查到的狀態來自 Kubernetes，還是只是表單任務的結果？目前後面三個交接點尚無可執行整合，答案必須留在設計與驗收條件，不能寫成測試通過。

下一篇先看 `Microservice` 的輸入合約：現有 CRD 能驗證哪些欄位，要讓服務團隊填入環境變數並查看健康狀態，又需要補哪些欄位。
