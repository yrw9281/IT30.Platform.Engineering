# Day 25 - 用 Webhook 把 Kubernetes 狀態回傳 IDP 資料庫

## 前一日主題回顧

Day 24 讓 Argo CD 能從 `Microservice.status.conditions` 判斷 `reminder-api` 是 `Progressing`、`Healthy` 還是 `Degraded`，也限制 notification 只在有意義的狀態轉換時發出。最後一段回饋流要把結果帶回開發者工作的地方：Portal。

它看似只是「收到 webhook，更新一欄 status」，卻要面對重送、亂序、錯誤來源，以及已被新 revision 取代的 deployment。receiver 若照最後收到的內容覆寫，舊版本的 `Healthy` 事件可能蓋掉新版本的失敗。

## Portal DB 是交付狀態的投影，不是新的真實來源

Git 仍然是 desired state 的單一真實來源，Kubernetes/Argo CD 是 observed state 的權威。IDP database 的角色是把一個 delivery request 的 PR、Git revision、同步與 health 事件整理成開發者易讀的時間線；它不應自行發明 deployment 成功或成為另一條控制路徑。

```text
Portal request -> delivery record -> config PR -> merged revision
                                             │
Argo CD observed health event ───────────────┘
              │
              ▼
      immutable delivery event history
              │
              ▼
       current Portal status projection
```

這個分層讓我們能同時回答兩件事：現在 `reminder-api` 的最新交付狀態是什麼？它為什麼會變成這個狀態？前者讀 projection，後者讀不可變 event history。

## Webhook payload 必須能對應一筆交付

IDP receiver 至少需要 Application、Git revision、sync/health 狀態與可去重的事件鍵。不要依賴 payload 裡的「現在時間」做 identity，因為同一通知重送時時間可能不同。

```json
{
  "eventKey": "reminder-api-dev:a1b2c3d:Healthy",
  "application": "reminder-api-dev",
  "project": "todo",
  "revision": "a1b2c3d",
  "syncStatus": "Synced",
  "healthStatus": "Healthy",
  "namespace": "todo-dev"
}
```

範例將 `eventKey` 寫成易讀的形式。真正實作時，應以 application、revision、health status 等穩定欄位，加上明確 delimiter 或 hash 建立，並在資料庫設 unique constraint。`application` 也必須符合 Day 08 的生成命名契約，`reminder-api-dev` 才能安全對應 Todo team 的 delivery record。

注意 `eventKey` 是 idempotency key，不是 authentication。任何人都能猜到 application 名稱，因此不能因為 request 帶了正確 key 就相信它來自 Argo CD。

這個第一版 key 能分辨同一 revision 的首次 `Healthy` 與首次 `Degraded`，但不能分辨第二次 `Healthy` 是第一次通知的 retry，還是 `Healthy -> Degraded -> Healthy` 的真正恢復。若 Portal 產品需要完整 oscillation 時間線，webhook payload 必須再帶由 sender 或受信任 relay 一次產生、重送時不變的 `eventId`；絕不能改用 receiver 的接收時間，否則每次 retry 都會變成假的新事件。

## Argo CD Notification 的責任與限制

Argo CD Notifications webhook service 可以設定 URL、HTTP method、body template 與靜態 header。以下是規劃中的 config：token 由 `argocd-notifications-secret` 提供，文中以 `******` 遮蔽，絕不提交實際值。

```yaml
# 規劃片段：argocd-notifications-cm 的 webhook service/template
data:
  service.webhook.idp-delivery: |
    url: https://idp.example.internal/v1/delivery-events
    headers:
      - name: Content-Type
        value: application/json
      - name: X-IDP-Webhook-Token
        value: Bearer $idp-webhook-token

  template.webhook-delivery-status: |
    webhook:
      idp-delivery:
        method: POST
        body: |
          {
            "eventKey": "{{.app.metadata.name}}:{{.app.status.sync.revision}}:{{.app.status.health.status}}",
            "application": "{{.app.metadata.name}}",
            "project": "{{.app.spec.project}}",
            "revision": "{{.app.status.sync.revision}}",
            "syncStatus": "{{.app.status.sync.status}}",
            "healthStatus": "{{.app.status.health.status}}",
            "namespace": "{{.app.spec.destination.namespace}}"
          }
```

```yaml
# 規劃片段：argocd-notifications-secret 的 key 形狀
apiVersion: v1
kind: Secret
metadata:
  name: argocd-notifications-secret
  namespace: argocd
type: Opaque
stringData:
  idp-webhook-token: "******"
```

範例中的 header value 是遮蔽字串，不能直接套用。實作時要將它改為 Notifications 支援的 Secret key reference，例如 `$idp-webhook-token`，讓它引用 `argocd-notifications-secret` 的同名 key；Secret 的實際值仍不可出現在 Git。這個機制不會自動替 payload 計算 HMAC 簽章。未來若需要 HMAC，必須加上受信任的 signing relay，或實作能驗證簽名的 sender；receiver 不能只假設某個 header 是 HMAC。第一版先使用短期、可輪替的 bearer token、內部網路限制、TLS 與 receiver 的 constant-time token comparison；高信任場景再評估 mTLS 或專用 webhook gateway。

## Receiver 要按照固定順序處理事件

一個可靠的 receiver 不應一收到 JSON 就更新主表。建議將處理順序設計為：

```text
authenticate source
  -> validate JSON schema and bounded field sizes
  -> derive and verify eventKey
  -> find delivery by application + revision
  -> append immutable event if not already seen
  -> validate allowed state transition
  -> update current delivery projection
  -> return a clear success or error response
```

`application + revision` 找不到對應 delivery 時，不能默默忽略。這可能是 repository naming drift、已刪除服務的延遲事件，或未授權來源試圖寫入 Portal；receiver 應留下安全 audit event 並回傳定義明確的失敗結果。若 event 已存在，則安全地回傳成功，不重複寫歷史，也不再觸發下游副作用。

## 亂序事件需要 revision-aware 的狀態機

Portal 的狀態不是任意字串覆蓋，而是受 delivery request 與 revision 限制。以下是規劃中的核心規則：

```text
AwaitingReview -> Merged -> Syncing -> Progressing -> Healthy
                                            └─────> Degraded

同一 revision、同一 eventKey 的重送：記為 duplicate，不改變 projection
同一 revision 的首次不同 terminal status：保留兩個可辨識觀察，再依允許轉換更新 projection
較舊 revision 的延遲事件：保留在 history，不覆蓋目前 revision
未知 revision 的事件：拒絕投影更新並留下 audit record
```

當產品尚未有穩定 `eventId` 時，receiver 必須保守處理重複 `Healthy`：它不能宣稱那是一次新的恢復。等 sender/relay 能提供 occurrence ID 後，才可將同一 revision 的 `Degraded -> Healthy` 視為新的、可驗證的轉換。無論採哪種版本，都必須確認事件屬於同一 revision，且較舊 revision 的 `Healthy` 永遠不能蓋掉新 image 的 `Degraded`。

資料模型也應保存接收時間、事件原始 revision、health/sync value、驗證結果與 request correlation ID。不要只留「目前狀態」一欄，否則使用者問「為什麼剛剛從健康變失敗」時，平台沒有任何可以回答的歷史。

## 不讓 webhook 成為另一個攻擊入口

除了 token 驗證與去重，receiver 還需限制：

- 僅接受預期 HTTP method、content type 與合理大小的 JSON body。
- 不把 event 中的 message、URL 或 resource name 直接插入 SQL、shell 或 HTML。
- 將 webhook endpoint 限制在預期的內部網路與 TLS 範圍，並為 token rotation 保留雙 token 重疊期。
- 對 auth failure、unknown application、schema error 與 invalid transition 留下可查 audit event。
- 對外回傳不洩露其他 team delivery 是否存在的最小必要錯誤資訊。

Webhook 是非同步整合，不是可信內部函式呼叫。它的錯誤處理、observability 與 rate limit 也應被視為 IDP 的正式產品需求。

## 測試與驗證

Notifications、receiver 與資料庫均未實作。後續會用以下 fixture 驗證安全與狀態一致性：

```text
預期演練：
1. 合法 Healthy payload 只為同一 application/revision 新增一筆 event，並將對應 delivery 投影為 Healthy。
2. 同一 payload 重送兩次，第二次回應成功但不增加 history 或觸發重複通知。
3. 新 revision 已為 Degraded 時，送入舊 revision 的 Healthy payload，確認只記錄歷史、不覆蓋當前狀態。
4. 缺少或錯誤 bearer token、過大 body、無效 JSON、未知 application，確認拒絕並留下安全 audit。
5. 對同一 revision 的重複 `Healthy` payload，確認 receiver 不會把 retry 假裝成健康恢復；若要支援完整 oscillation 時間線，先驗證 sender/relay 提供的穩定 `eventId` 能區分新事件與重送。
```

驗收後，開發者應能從 Portal 的一筆 delivery record 看見自己提出什麼、何時被 merge、Argo CD 觀察到什麼，以及目前狀態是否屬於最新 revision。

至此，規劃中的 Todo 平台已把開發者意圖、Git review、Argo CD、Operator 與 Portal 狀態接成閉環；它們仍未在本專案實作，不能據此宣稱服務已能自助交付。下一階段處理自助服務帶來的風險：當更多人能建立服務，要如何用 Namespace、RBAC 與 Policy 收住權限與可接受行為？
