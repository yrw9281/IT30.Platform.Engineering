# Day 25 - Kubernetes RBAC 與 Namespace 能隔離什麼

Day 24 讓我們知道 Backstage 的 Catalog 可以幫開發者找到服務，Kubernetes plugin 則能查資源現況。查得到資源，不代表可以修改它；Catalog 的 `owner` 也不是 Kubernetes 的權限設定。如果 `todo-api` 被入侵，或有人提交了錯誤的部署設定，它能在叢集裡做什麼，得看另一套邊界。

這篇用 Todo 團隊的 Dev 環境討論 Namespace 與角色型存取控制（Role-Based Access Control，RBAC）。目前沒有 Todo Dev 的 Namespace／RBAC 來源檔，也沒有權限測試結果；以下談的是**如何設計與驗收**，不是宣稱已完成隔離。

## Namespace 劃範圍，RBAC 決定 API 動作

假設 `todo-dev` 與另一個團隊的 `payments-dev` 共用叢集。Namespace 讓多數資源的名稱與權限有各自的範圍，但光是建立兩個 Namespace，不會自動擋住跨 Namespace 的 API 存取，更不會隔離 Pod 對外的網路流量。

RBAC 規則要回答的是：「哪個身分，能對哪種 Kubernetes 資源，執行哪個動作？」`Role` 列出特定 Namespace 中允許的 API 動作；`RoleBinding` 將它授予使用者、群組或 `ServiceAccount`。`ClusterRole` 可重用權限規則；用 `RoleBinding` 綁定時仍可限定在一個 Namespace，而 `ClusterRoleBinding` 的作用範圍則可能擴及整個叢集。RBAC 權限是累加的，**沒有一條通用的 deny 規則可以抵銷已授予的權限**；要看到拒絕，得確認沒有其他 binding 放行。

## 工作負載與平台元件不能共用一組權限

`todo-api` 若不需要呼叫 Kubernetes API，就不必預先取得 API 權限；是否掛載 `ServiceAccount` token，也應依實際使用的元件評估。若某個服務只需讀自己的具名 `ConfigMap`，授予該 Namespace 中指定資源的 `get`，通常比允許列出所有設定與 `Secret` 更符合需求。

Operator 與 Argo CD 則不同。Operator 規劃要觀察 `Microservice` 並建立受管 Deployment／Service；Argo CD 要將已審查的 Git 設定同步到允許的叢集與 Namespace。兩者都需要比應用程式更廣的權限，但仍應分開身分與可操作範圍。Backstage 模板的 Git PR 權限不應因此取得叢集寫入權限。Catalog `owner: todo` 可以幫人找到負責團隊，不能拿它代替 Git 權限或 RBAC 授權。

## 別把所有隔離要求都交給 RBAC

RBAC 管的是 Kubernetes API，不管 `todo-api` 能否透過網路連到別的 Service；`ResourceQuota` 管資源預算，Pod Security 管部分容器權限，`NetworkPolicy` 與 Service Mesh 各處理不同層次的流量。Namespace 本身也不是叢集層級資源、Secret 管理或 Node 隔離的完整答案。尤其 Pod 若取得了高權限的 ServiceAccount token，前面的最小權限設計就失效了。

如果要驗收這個設計，至少要確認四種預期結果：Todo 服務可讀自己獲准的設定，不能讀另一團隊的 `Secret`，不能修改不屬於自己的 Deployment；Operator 與 Argo CD 只能在授權範圍內完成各自工作。這些是**待建立來源檔與測試身分後的驗收條件**，不是本篇在叢集跑出的 `yes`／`no`。下一篇處理另一個問題：即使某個身分有權建立 Deployment，它提交的內容是否符合平台要求？
