# Day 25 - 用 Kubernetes RBAC 與 Namespace 隔離團隊權限

Day 24 把交付狀態回傳到 Portal，開發者現在能提出服務需求，也能追蹤它是否健康。這條路徑變短後，權限邊界不能再靠約定維持：一個設定錯誤或遭入侵的 workload，不該因此讀到其他團隊的 `Secret`，更不該能修改別人的部署。

本日先定義同一個 Kubernetes 叢集中的團隊邊界。`Namespace` 劃出資源範圍，RBAC（Role-Based Access Control）限制 API 動作；兩者還要和資源配額、網路策略及 Secret 管理一起使用。`src/` 目前沒有對應檔案，以下 YAML 與指令都是**概念範例**，不能當成已部署設定或驗證結果。

## `Namespace` 是隔離的起點

`Namespace` 為 namespaced resource 提供名稱、權限與 quota 的範圍。Todo team 的 Dev 與 Production 不應只靠 label 區分，而要有各自的 `Namespace`、`ServiceAccount`、`RoleBinding` 和資源預算。

下列概念範例日後應新增為 `src/security/rbac/todo-dev-namespace.yaml`：

```yaml
# 規劃片段：Todo Dev 的 Namespace baseline
apiVersion: v1
kind: Namespace
metadata:
  name: todo-dev
  labels:
    platform.example.io/team: todo
    platform.example.io/environment: dev
    pod-security.kubernetes.io/enforce: restricted
```

`pod-security.kubernetes.io/enforce: restricted` 是值得評估的基線，不能只加上標籤就假設既有 workload 一定相容。導入前要確認 image、sidecar 與 `securityContext`。`Namespace` 也不會自動封鎖網路流量、跨 `Namespace` 的 `RoleBinding`、cluster-scoped resource 或 Node 層級風險。

## 每個 workload 都要有自己的 API 身分

Kubernetes workload 以 `ServiceAccount` 身分呼叫 Kubernetes API。`reminder-api` 不應使用預設 `ServiceAccount`，不同 Todo 服務也不應共用一個帳號；否則 audit log 無法辨識呼叫來源，之後也難以縮減權限。

若 application 不需呼叫 Kubernetes API，應避免掛載 API token。下列概念範例日後應放在 `src/security/rbac/reminder-api-serviceaccount.yaml`；是否可關閉 token automount，仍要和 Service Mesh、sidecar 及 application 的需求一起測試。

```yaml
# 規劃片段：reminder-api 的專屬 workload identity
apiVersion: v1
kind: ServiceAccount
metadata:
  name: reminder-api
  namespace: todo-dev
automountServiceAccountToken: false
```

這個 `ServiceAccount` 仍能作為 workload identity 與 audit 識別。未來若 `reminder-api` 必須讀取 Kubernetes `ConfigMap` 或使用其他 in-cluster API，再以最小的 `RoleBinding` 加回所需權限；不要預先授予 `list`、`watch` 或 `secrets`。

## 用 `Role` 和 `RoleBinding` 寫清楚允許的動作

假設 `reminder-api` 需要讀取名稱已知、專屬的 `ConfigMap`。權限可以限縮為單一 resource name 與 `get`，而不是列出整個 `Namespace` 的所有 `ConfigMap`。以下兩段概念範例日後應新增為 `src/security/rbac/reminder-api-read-config.yaml`：

```yaml
# 規劃片段：僅讀取指定 ConfigMap 的 Role
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: reminder-api-read-config
  namespace: todo-dev
rules:
  - apiGroups: [""]
    resources: ["configmaps"]
    resourceNames: ["reminder-api-config"]
    verbs: ["get"]
```

```yaml
# 規劃片段：只在 todo-dev 綁定 reminder-api 身分
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: reminder-api-read-config
  namespace: todo-dev
subjects:
  - kind: ServiceAccount
    name: reminder-api
    namespace: todo-dev
roleRef:
  apiGroup: rbac.authorization.k8s.io
  kind: Role
  name: reminder-api-read-config
```

`Role` 描述一個 `Namespace` 中可做的動作；`RoleBinding` 指定哪個 subject 能在該 `Namespace` 使用它。即使 `ServiceAccount` 與 `RoleBinding` 位於同一個 `Namespace`，仍明確寫出 subject namespace，讓 review 時不必猜測身分來源。

跨 `Namespace` 存取不是把 `Role` 換成 `ClusterRoleBinding` 就能帶過。先確認需求是否真的存在，能否用 API 或事件整合取代直接讀取其他團隊的 `Secret`。若無法避免，仍要把 resource、verb、`Namespace` 與 subject 縮到最小，並留下可追溯的例外核准。

## 平台元件與 application workload 分開授權

`reminder-api`、Microservice Operator、Argo CD 與 IDP backend 的責任不同，不能共用一組寬鬆權限。設計 RBAC 時可先用下表檢查權限是否合理：

| 身分 | 可能需要的權限 | 不應取得的權限 |
| --- | --- | --- |
| `reminder-api` | 預設不呼叫 Kubernetes API；必要時只讀自己的具名設定 | 讀任何 Secret、建立 Deployment、跨 Namespace list |
| Microservice Operator | 對受管 CR 與 child Deployment/Service 的明確讀寫 | 修改無關 team 的 workload、讀所有 Secret |
| Argo CD | 讀核准 repository，對允許 destination reconcile | 寫 application source、存取任意 cluster/Namespace |
| IDP API | 建 branch/PR、寫 delivery projection | 直接建立 Kubernetes resource、使用 cluster-admin |

平台可以用 `ClusterRole` 定義 Operator 可重用的權限，再用 `Namespace` 的 `RoleBinding` 或 Project 邊界限制實際範圍。`cluster-admin` 只應保留給嚴格控管、可稽核的 break-glass 身分，不能成為 application 的預設解法。

## 配額、網路與 Secret 是另外幾道邊界

RBAC 能限制 Kubernetes API 動作，卻管不到合法 Pod 是否耗盡 CPU，也不會阻止它呼叫另一個 Service。Namespace baseline 還需要逐步加入資源配額。下列概念範例日後應新增為 `src/security/rbac/todo-dev-resourcequota.yaml`：

```yaml
# 規劃片段：todo-dev 的資源預算
apiVersion: v1
kind: ResourceQuota
metadata:
  name: team-budget
  namespace: todo-dev
spec:
  hard:
    requests.cpu: "4"
    requests.memory: 8Gi
    limits.cpu: "8"
    limits.memory: 16Gi
    pods: "20"
```

`ResourceQuota` 要搭配 `requests` 與 `limits` 才有可預測的效果。Day 27 會用 admission policy 要求 workload 宣告這些限制；Day 28–29 則處理東西向流量。Secret manager、encryption at rest、Pod Security 與 admission policy 各自處理不同風險，不能互相替代。

## 後續驗證

RBAC、Namespace baseline 和 quota 尚未實作。新增 `src/security/rbac/` 中的 manifests 並部署到測試叢集後，可用以下**概念驗證指令**檢查 allow/deny 結果：

```bash
# 規劃中的 Kubernetes RBAC 檢查
kubectl auth can-i get configmaps/reminder-api-config \
  --as=system:serviceaccount:todo-dev:reminder-api \
  -n todo-dev

kubectl auth can-i get secrets/other-team-secret \
  --as=system:serviceaccount:todo-dev:reminder-api \
  -n payments-dev

kubectl auth can-i create deployments \
  --as=system:serviceaccount:todo-dev:reminder-api \
  -n todo-dev
```

依這份設計，第一個問題應回覆 `yes`，後兩個應回覆 `no`。還要確認 workload 未使用預設 `ServiceAccount`、超過 `ResourceQuota` 時新資源被拒絕，且 Portal team mapping 不會讓非 Todo 成員建立 `todo-dev` 的 CR。下一步是把 workload 本身可接受的設定交給 admission policy 檢查。
