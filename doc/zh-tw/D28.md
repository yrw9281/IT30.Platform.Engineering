# Day 28 - Istio Sidecar 如何改變微服務流量

Day 27 的政策關注 Deployment 寫入 Kubernetes 時的設定。Pod 啟動後，`todo-bff` 呼叫 `todo-api` 又是另一回事：RBAC 不管這條 HTTP 連線，admission 也不會逐筆檢查它。若要替服務間流量加上共同的身分、加密、路由及觀察能力，可以評估 Service Mesh；但那不代表目前的平台已經需要或已經安裝 Istio。

本篇以 **Istio Sidecar 模式**討論它如何處理流量。現有 Todo API／BFF 是原生 Kubernetes 工作負載，位於 `todo` Namespace，沒有 Istio 安裝、注入設定或流量規則。下面的 Todo Dev 路徑是設計情境，沒有可執行的 mesh 範例。

## 誰處理請求，誰發佈規則？

在 Sidecar 模式下，應用程式 Pod 旁有 Envoy proxy。當 `todo-bff` 呼叫 `todo-api`，網路路徑可以經過呼叫端與接收端的 Envoy；應用程式仍處理自己的 HTTP 請求，proxy 處理 mesh 層的流量規則、身分與 telemetry。這些 proxy 是**資料平面（data plane）**。

`istiod` 是**控制平面（control plane）**：它讓 proxy 取得服務發現、流量／安全設定與工作負載身分相關資訊，但不代替 proxy 轉送每一筆業務請求。外部流量若要進入 mesh，可經額外設定的 ingress gateway；它不是每個內部服務呼叫都必經的元件。

## 「不用改程式」不等於「部署沒有成本」

Sidecar injection 通常不需重寫應用程式的 HTTP client，就能把符合條件的流量交給 Envoy；但只有完成 Istio 安裝、加入對應的 injection 設定並重新建立 Pod，才會出現 sidecar。原有 Pod 不會因為改了 Namespace label 就憑空多出一個 container。

導入時還要看 proxy 的 CPU／memory 成本、Pod 啟動與 probe 的先後、HTTP/gRPC 協定辨識、對外 egress、沒有加入 mesh 的呼叫端，以及既有 OpenTelemetry trace／metric 的重複與關聯問題。現有 Todo API Deployment 尚未配置 CPU／memory limits；若連工作負載的資源預算都沒盤點，直接把 proxy 加進來會讓容量評估更難。

`NetworkPolicy` 可以處理叢集網路層的連線邊界，但不會提供 Istio 的工作負載身分或 HTTP 路由。Istio 也不取代 Kubernetes RBAC、admission、安全的 image 來源，或應用程式的使用者授權。是否值得加入 proxy，應從需要解決的流量問題與維運成本判斷，而不是因為前面有 Operator 就一定要裝 mesh。

## 如果要試，先確認原本的服務仍然可用

一個可控的驗收情境是先在隔離的非 Production 環境確認 `todo-bff` 呼叫 `todo-api` 的原始路徑，再逐個工作負載加入 sidecar，對照 Pod container 數、proxy 就緒、請求結果及 trace／log。尚未加入 mesh 的 client 也要納入測試；同時更改 injection、流量規則與加密模式，會讓失敗很難定位。

這是**導入時應驗證的清單，不是本篇已跑過的結果**。下一篇再把 mTLS 的傳輸身分與 `AuthorizationPolicy` 的服務授權拆開，看兩者各自擋得住什麼。
