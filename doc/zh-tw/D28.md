# Day 28 - 用 Rego 阻擋高風險 YAML

Day 27 說明 Gatekeeper 能在 admission 邊界執行規則，接下來要決定先擋哪些風險。Todo 平台先聚焦三件修正方式明確的事：workload 缺少 CPU 或 memory limits、container 設定 `privileged: true`，以及 image 不是從核准的 GHCR repository 拉取。

這些設定尚未加入 `src/`，以下 YAML、Rego 與驗證資料都是**概念範例**，不能視為已安裝的 policy、已通過的測試或已存在的 Operator 產物。實作時需新增對應的 source file，並先用 fixture 驗證。

## 定義輸入與套用範圍

本日定義 `TodoPlatformWorkloadSecurity` `ConstraintTemplate`，再用 Constraint 將三條規則套到 Todo Dev。schema 只暴露環境可調整的 `allowedRepos`；資源 limit 與 privileged 則是所有 team 都不能自行關閉的底線。

下列骨架日後應新增為 `src/security/gatekeeper/todo-platform-workload-security-template.yaml`：

```yaml
# 規劃片段：三條 Rego 規則共用的 ConstraintTemplate 骨架
apiVersion: templates.gatekeeper.sh/v1
kind: ConstraintTemplate
metadata:
  name: todoplatformworkloadsecurity
spec:
  crd:
    spec:
      names:
        kind: TodoPlatformWorkloadSecurity
      validation:
        openAPIV3Schema:
          type: object
          properties:
            allowedRepos:
              type: array
              items:
                type: string
  targets:
    - target: admission.k8s.gatekeeper.sh
      rego: |
        # 將下方 package todoplatform 的完整 Rego module 放在這裡
```

以下 Rego 的 target 是 `apps/v1` `Deployment`。它同時檢查一般 container 與 init container，避免 policy 只覆蓋最常見的一半。完整 module 日後應放入上述 `ConstraintTemplate.spec.targets[].rego`，或另存為 `src/security/gatekeeper/todo-platform-workload-security.rego` 後由產生流程嵌入；目前兩者都不存在。

```rego
# 規劃片段：三種規則共用的 container 集合
package todoplatform

containers[container] {
  container := input.review.object.spec.template.spec.containers[_]
}

containers[container] {
  container := input.review.object.spec.template.spec.initContainers[_]
}
```

Constraint 的 `match` 也必須限制為 `apps/Deployment`。若直接套用到 `Pod`，`.spec.template` 不存在，規則可能出錯或得出意外結果。

## 規則一：每個 container 都要有 CPU 與 memory limits

平台若要確保產生的 `Deployment` 不會被這條 policy 阻擋，就必須在其 resources 中提供 limits。`object.get` 可處理 `resources` 或 `limits` 不存在的輸入，讓違規訊息仍指向明確欄位：

```rego
# 規劃片段：要求 CPU limit
violation[{"msg": msg, "details": {"container": container.name}}] {
  container := containers[_]
  limits := object.get(object.get(container, "resources", {}), "limits", {})
  not limits.cpu
  msg := sprintf("container %q must set resources.limits.cpu", [container.name])
}

# 規劃片段：要求 memory limit
violation[{"msg": msg, "details": {"container": container.name}}] {
  container := containers[_]
  limits := object.get(object.get(container, "resources", {}), "limits", {})
  not limits.memory
  msg := sprintf("container %q must set resources.limits.memory", [container.name])
}
```

這裡要求 `limits`，因為它是保護 Node 的硬上限。實務上通常也要要求 `requests`，讓 scheduler 有足夠資料 placement。requests 是否要和 limits 相同、是否允許 burst、值的上下限如何訂，應由工作負載特性與 `ResourceQuota` 一起決定。

## 規則二：拒絕 privileged container

`privileged: true` 會大幅放寬 container 隔離限制。一般 application workload 不該需要它；Node-level agent 等例外應使用專用 `Namespace`、額外 review 與明確例外，而不是讓一般服務用一個 boolean 繞過。

```rego
# 規劃片段：拒絕一般與 init container 的 privileged mode
violation[{"msg": msg, "details": {"container": container.name}}] {
  container := containers[_]
  security_context := object.get(container, "securityContext", {})
  security_context.privileged == true
  msg := sprintf("container %q must not set securityContext.privileged=true", [container.name])
}
```

這條規則只處理 privileged。`hostNetwork`、`hostPID`、hostPath volume、capabilities、`runAsNonRoot` 等風險應分別用可讀、可測的 policy 處理，避免堆成一個難以 review 的 Rego 檔。

## 規則三：限定核准的 GHCR repository

`contains(image, "ghcr.io/yrw9281")` 不安全，因為 `ghcr.io/yrw9281.evil.example/image` 也會通過。Constraint 應傳入包含結尾 slash 的完整 GHCR repository prefix，規則再以 `startswith` 比對：

```rego
# 規劃片段：只允許 approved repository prefix
approved_image(image) {
  allowed_prefix := input.parameters.allowedRepos[_]
  startswith(image, allowed_prefix)
}

violation[{"msg": msg, "details": {"container": container.name, "image": container.image}}] {
  container := containers[_]
  not approved_image(container.image)
  msg := sprintf(
    "container %q must use an approved image repository; got %q",
    [container.name, container.image]
  )
}
```

以下概念 Constraint 日後應新增為 `src/security/gatekeeper/todo-dev-workload-security.yaml`：

```yaml
# 規劃片段：Constraint 以明確 prefix 套用三條規則
apiVersion: constraints.gatekeeper.sh/v1beta1
kind: TodoPlatformWorkloadSecurity
metadata:
  name: todo-dev-workload-security
spec:
  enforcementAction: dryrun
  match:
    namespaces: ["todo-dev"]
    kinds:
      - apiGroups: ["apps"]
        kinds: ["Deployment"]
  parameters:
    allowedRepos:
      - ghcr.io/yrw9281/
```

這條 rule 只驗證來源 prefix，不能保證 image 已掃描、tag 不可變或 digest 已簽章。Day 16–17 的 CI/GitOps 仍負責產生與推進 digest；之後可另加要求 `@sha256:` 或驗證 provenance 的 policy。

## 以 fixture 描述允許與拒絕

安全規則的 fixture 也是可讀的合約。日後應新增違規 fixture，例如 `src/security/gatekeeper/fixtures/invalid-deployment.yaml`：

```yaml
# 規劃片段：預期被拒絕的 Deployment 片段
spec:
  template:
    spec:
      containers:
        - name: reminder-api
          image: docker.io/library/nginx:latest
          securityContext:
            privileged: true
```

依設計，這筆資料應產生缺少 CPU limit、缺少 memory limit、未核准 image 與 privileged container 四類違規。合規 fixture 則必須使用 `ghcr.io/yrw9281/` 前綴、明確 CPU/memory limits，且未設定 privileged。兩種 fixture 都要覆蓋一般 container 與 init container。

## 從 audit 漸進切到 `deny`

規則寫完不代表可以立刻切到 `deny`。較安全的導入順序如下：

```text
write rule and allow/deny fixtures
  -> run local/CI policy tests
  -> deploy Constraint with dryrun
  -> inspect audit violations and classify exceptions
  -> fix platform defaults and application manifests
  -> move a small scope to deny
  -> expand only after observing no unexpected blocks
```

例外不應藏在 Rego 的 `if namespace == "special"`。應用 `Constraint` 的 `match.excludedNamespaces`、經 review 的參數或可到期的例外資源表示，並記錄 owner 與原因。

## 後續驗證

目前沒有 Gatekeeper、template、fixture 或 policy test。新增 `src/security/gatekeeper/` 的來源檔後，應依序執行以下**預期演練**：

```text
預期演練：
1. 對每條 Rego 規則執行合規、缺漏欄位、initContainer 與違規 image fixture。
2. 在 todo-dev 用 dryrun 套用 Constraint，確認既有 Deployment 的 audit 違規可被分類。
3. 確認 Day 21 Operator 產生的 resources 有 CPU/memory limits、非 privileged 且使用核准的 GHCR repository。
4. 將小範圍 Constraint 切為 deny，提交違規 Deployment，確認 API Server 回傳各容器對應的可讀訊息。
5. 提交合規 Deployment，確認 policy 不會造成 false positive。
```

YAML admission 已經擋住高風險設定後，仍要限制運行中 Pod 的橫向連線。Day 29 開始將控制點移到服務之間的流量。
