# Day 08 - 用 Argo CD ApplicationSet 管理多個服務與環境

## 前一日主題回顧

Day 07 的一份 `Application` 已能把 `apps/todo-api/overlays/dev` 部署到 `todo-dev`。多加兩個環境，就要再寫 Staging 與 Production；`reminder-api` 加入後，數量又增加一輪。十個服務、三個環境會有三十份 `Application`，也有三十次可能漏掉 `project`、Namespace 或同步政策的複製貼上。

這種結構化的重複適合交給 controller 生成。Argo CD 的 `ApplicationSet` 描述服務與環境清單從哪裡來，以及每一項要產生什麼 `Application`；ApplicationSet controller 會持續維護結果。

## `ApplicationSet` 產生的是 `Application`

這個關係是理解 ApplicationSet 的第一個門檻：

```text
Git directories or environment list
              │
              ▼
      ApplicationSet generator
              │
              ▼
    generated Argo CD Applications
              │
              ▼
Deployment / Service / Microservice resources
```

ApplicationSet controller 擁有它產生的 child `Application`。直接修改 `todo-api-dev` child Application 後，下一次 generator reconcile 很可能被 template 覆寫。共通設定應改 `ApplicationSet` template；新增服務或環境應改 generator 的資料來源；例外則要有清楚且可 review 的設定位置。

## 用 Git 目錄列出服務與環境

Day 04 已規劃 `apps/<service>/overlays/<environment>` 結構。除了收納檔案，這個結構也能作為 `ApplicationSet` 的資料來源：新增符合約定的 overlay 目錄，即表示該服務要出現在該環境。

以下片段啟用 Go template，從所有 overlay 目錄建立 `Application`。本專案的 `src/` 尚無對應 manifest，也沒有真實 repository 或 cluster 連線；這是設計片段。複製前，必須先在 `src/` 建立對應檔案，並依實際環境設定 repository、cluster、權限與 `AppProject` 限制。

```yaml
# 規劃片段：platform/argocd/todo-applicationset.yaml
apiVersion: argoproj.io/v1alpha1
kind: ApplicationSet
metadata:
  name: todo-applications
  namespace: argocd
spec:
  goTemplate: true
  generators:
    - git:
        repoURL: https://github.com/example/todo-platform-config.git
        revision: main
        directories:
          - path: apps/*/overlays/*
  template:
    metadata:
      name: '{{index .path.segments 1}}-{{.path.basename}}'
    spec:
      project: todo
      source:
        repoURL: https://github.com/example/todo-platform-config.git
        targetRevision: main
        path: '{{.path.path}}'
      destination:
        server: https://kubernetes.default.svc
        namespace: 'todo-{{.path.basename}}'
      syncPolicy:
        automated:
          prune: true
          selfHeal: true
```

對 `apps/todo-api/overlays/dev` 而言，`path.segments` 的第二段是 `todo-api`，`path.basename` 是 `dev`，產物就是 `todo-api-dev` Application。這個命名規則會用在日後查事件、讀告警與找 Git 路徑。

目錄命名因此成了 API。將 `prod` 改成 `production` 不只是重新命名資料夾，也可能產生不同 Namespace 與 Application 名稱。先定義命名規則並經過 code review，再讓 generator 信任它。

## 目的地不能從目錄推導時，改用 List Generator

不是每個維度都適合從 Git path 推導。多叢集情境常需要一份受平台管理的目標清單，例如 region、cluster API server 與環境名稱。這時使用 List Generator，將受控的部署目的地明確列成資料，而不是取代 Git。

```yaml
# 規劃片段：需先建立在 src/ 的 List Generator 環境資料
generators:
  - list:
      elements:
        - environment: dev
          cluster: https://kubernetes.default.svc
          namespace: todo-dev
        - environment: staging
          cluster: https://staging.example.internal
          namespace: todo-staging
```

若未來把 Git Generator 與 List Generator 組合，必須特別審查 template 最終可以指向哪些 `server` 和 Namespace。自動生成不應繞過 Day 07 提到的 `AppProject` allow list；否則一行清單變更就可能讓同一份服務設定被送到不該碰的 cluster。

## 不要把例外藏進模板字串

ApplicationSet 適合處理每個服務都遵循同一份部署合約的重複。不同服務的特殊 rollout、不同資料 migration 順序或例外權限，不適合全塞進巢狀 template 條件。

判斷方式很簡單：reviewer 若只看一個 overlay 目錄，卻無法預測它會產生哪個 Application、部署到哪裡，template 就太複雜了。此時可將差異留在 Kustomize overlay、拆成另一個 `ApplicationSet`，或重新設計平台合約。

## 測試與驗證

目前沒有 ApplicationSet controller 或 GitOps repository，以下指令尚不能執行。待在 `src/` 建立相符 manifest、設定 controller 與 repository 後，先 preview 產物，再讓 controller 建立任何 `Application`：

```bash
# 從 ApplicationSet manifest 預覽將生成的 Applications
argocd appset preview -f platform/argocd/todo-applicationset.yaml

# controller 導入後，確認 child Application 的 owner 與目的地
kubectl get applications -n argocd
kubectl describe applicationset todo-applications -n argocd
```

驗收時可新增 `apps/todo-api/overlays/staging`，預期只多出 `todo-api-staging`，且目標是 `todo-staging`。也要確認不符合目錄約定的路徑不會被納入；意外多出一個 `Application` 是部署風險。

ApplicationSet 用一致的生成規則處理部署物件數量，但不會降低新版本本身的風險。Day 09 回到 `todo-api` 的發布策略：若新版讓建立待辦事項失敗，要怎麼先讓少量流量承擔風險，而非一次替換所有使用者？
