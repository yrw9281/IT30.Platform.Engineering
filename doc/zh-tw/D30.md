# Day 30 - 設定 mTLS 與 AuthorizationPolicy

Day 29 將 `todo-bff` 與 `reminder-api` 的流量導入 Envoy sidecar，但只多一層 proxy 還不構成零信任。若 mesh 接受 plaintext client，或任何已注入的 workload 都能呼叫 `reminder-api`，預設信任仍然太大。

本日分開處理傳輸身分與服務授權：mTLS（mutual TLS）讓雙方以 workload identity 建立加密連線，`AuthorizationPolicy` 決定這個身分能否呼叫目標服務。Istio、ServiceAccount 與 policies 尚未實作，`src/` 也沒有對應檔案；下列 YAML、流程與驗證都是**概念範例**。

## mTLS 證明連線兩端的 workload 身分

在 Istio mesh 中，已注入的 workload 可依 Kubernetes `ServiceAccount` 取得可輪替的 workload certificate。Envoy 用它和對端 Envoy 建立 mutual TLS：client 驗證 server、server 也驗證 client，流量在兩端之間加密。

```text
todo-bff Pod                           reminder-api Pod
ServiceAccount: todo-bff               ServiceAccount: reminder-api
        │                                        │
        └── Envoy <--- mTLS handshake ---> Envoy ┘
             verify workload identity + encrypt traffic
```

這種身分常以 SPIFFE 形式表達。在 Istio `AuthorizationPolicy` 的 `source.principals`，可比對 `cluster.local/ns/todo-dev/sa/todo-bff` 這樣的 workload principal。它不是使用者 JWT，也不是 Kubernetes RBAC subject；三者負責不同層次的認證與授權。

## 用 `PeerAuthentication` 要求嚴格加密

導入初期常用 `PERMISSIVE`，讓 plaintext 與 mTLS 共存，降低舊 client 切換的風險。盤點後確認 Todo Dev 的必要 client 都已注入並可用，才可將 `Namespace` 切為 `STRICT`。下列概念檔日後應新增為 `src/security/istio/todo-dev-peer-authentication.yaml`：

```yaml
# 規劃片段：todo-dev 內的 server workload 只接受 mTLS
apiVersion: security.istio.io/v1
kind: PeerAuthentication
metadata:
  name: default
  namespace: todo-dev
spec:
  mtls:
    mode: STRICT
```

這是 server-side 要求，不能自動修正 client。沒有 sidecar、使用錯誤 port/protocol、繞過 mesh 或無法取得有效 certificate 的 client，切換後都可能連線失敗。較安全的順序是盤點與注入 client、觀察既有流量、在 Dev 小範圍切 `STRICT`，驗證後再擴大；不應直接把 mesh-wide policy 設為嚴格。

`STRICT` 只確認傳輸身分，不決定呼叫是否合理。`todo-bff`、`reminder-api` 和不該信任的 worker 都可能持有有效 mTLS 身分，因此還要設定授權。

## 用 `AuthorizationPolicy` 建立 allow list

假設 `reminder-api` 提供 BFF 使用的 HTTP endpoint `/internal/reminders`。以下 policy 選取 `reminder-api` Pod，允許 `todo-bff` `ServiceAccount` 對指定 path 發出 `POST`。概念檔日後應新增為 `src/security/istio/allow-todo-bff-to-reminder-api.yaml`：

```yaml
# 規劃片段：只有 todo-bff 可以呼叫 reminder-api 的內部 endpoint
apiVersion: security.istio.io/v1
kind: AuthorizationPolicy
metadata:
  name: allow-todo-bff-to-reminder-api
  namespace: todo-dev
spec:
  selector:
    matchLabels:
      app.kubernetes.io/name: reminder-api
  action: ALLOW
  rules:
    - from:
        - source:
            principals:
              - cluster.local/ns/todo-dev/sa/todo-bff
      to:
        - operation:
            methods: ["POST"]
            paths: ["/internal/reminders"]
```

只要 workload 有相符的 `ALLOW` policy，未匹配 rule 的請求就會被拒絕。allow list 的風險在於容易漏掉實際 client，例如 health probe、metrics scrape、background worker、migration job 或 ingress gateway。因此導入前必須先盤點呼叫端，再逐一測試。

`methods` 與 `paths` 是 L7 HTTP 條件，只有 Envoy 能正確辨識協定時才適用。若 `reminder-api` 最終使用 gRPC 或 TCP，應改用正確的 operation match，並以真實流量驗證；不能直接套用 HTTP 範例。

## 預設拒絕不取代 application authorization

敏感服務可以先用 workload selector 建立小範圍 `ALLOW` policy，確認必要 client、health check 與 maintenance workflow 都在清單中；對需要立刻阻止的高風險來源，再使用明確 `DENY` policy 並 review 它與 `ALLOW` 的優先順序。

Istio authorization 是 workload 對 workload 的存取控制。它不知道使用者是否能看特定 Todo、BFF 的 JWT 是否有正確 role，或已被允許的 BFF 是否濫用 API。application authorization、rate limiting、audit log 與業務規則仍在 application 層。

## 以小範圍 rollout 降低中斷風險

mTLS 和 `AuthorizationPolicy` 都可能同時影響多條服務依賴，應分段處理：

```text
1. 盤點 reminder-api 的所有 client 與 HTTP/gRPC operations。
2. 確認每個必要 client 都使用專屬 ServiceAccount 並已進入 mesh。
3. 在 todo-dev 先建立 allow policy，透過 telemetry 檢查被拒絕的來源。
4. 將 PeerAuthentication 從 PERMISSIVE 切到 STRICT。
5. 用合格與不合格 client 驗證加密、身分與授權結果。
6. 將 policies 經 GitOps PR 推進到下一個環境。
```

發生失敗時不應先把所有 policy 刪掉。從 Envoy access log、Istio telemetry、`AuthorizationPolicy` selector、source principal、`DestinationRule` 與 application route 逐項確認；每次 break-glass 放寬都要有 Git 變更與到期追蹤。

## 後續驗證

待新增 `src/security/istio/` 下的 manifests、安裝 Istio 並準備測試 client 後，應進行下列**預期演練**，目前尚無執行結果：

```text
預期演練：
1. 已注入、使用 todo-bff ServiceAccount 的 client 對 POST /internal/reminders 發出請求，確認成功且流量使用 mTLS。
2. 已注入但使用其他 ServiceAccount 的 workload 發出同一請求，確認被 AuthorizationPolicy 拒絕，並能從 proxy telemetry 找到 source principal。
3. 未注入 sidecar 的 client 在 STRICT mode 嘗試連線，確認 plaintext 被拒絕且不影響已就緒的 mesh client。
4. 以 istioctl analyze、proxy status 與 application/Envoy log 檢查 policy selector、certificate 與拒絕原因。
5. 對 health probe、metrics scrape 與必要 background job 逐一驗證，確認它們不是因 allow list 遺漏而意外失效。
```
