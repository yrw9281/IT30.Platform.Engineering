# Day 30 - 30 篇後：展示 Todo 平台的交付成果

Day 01 問的是：微服務能跑之後，誰負責建置、部署、觀察與維護？今天回到 `todo-api`，從提出版本、管理工作負載到查詢部署與請求，看看這 30 篇留下了哪些成果。

這次展示沿用前面已有的畫面與觀察方式，不把各元件的成果拼成一段未驗證的全自動部署。Backstage 已能提出設定 Pull Request（PR），Operator 已能管理 Todo API，自訂資源（Custom Resource，CR）同步與健康檢查也有設定範例；是否完成同一次版本變更的端到端交付，仍要比對各環節的紀錄。

## 從 image 到一筆可以審查的設定 PR

Day 15 的 release workflow 建置 Todo image、推送到 GitHub Container Registry（GHCR），並輸出 digest。這讓我們可以固定要交付的內容，而不只依賴可能被重新指向的 tag。CI 仍負責建置與檢查，不直接替開發者決定部署到哪個環境。

Day 23、24 則把換版需求放進 Backstage 表單。開發者提供 Todo API 的 digest，模板產生 `Microservice` 設定，將服務名稱、`todo` Namespace 與 port 留在平台預設裡，再提出 Git PR。前面已展示任務成功建立 PR，並提供開啟變更的連結：

![Backstage 完成 Todo API 設定渲染與 PR 建立，任務結果提供 Review the config change 連結](../assets/day-24-backstage-pr-result.png)

審查者不必從一整份 `Deployment` 猜這次要改什麼，而是核對服務設定的 diff。第一次建立設定包含 `Microservice` 與 Kustomize 宣告；之後單純換版應聚焦 image digest：

![Todo API 設定 PR 的 Files changed，顯示 Kustomize 宣告與帶有 image digest 的 Microservice](../assets/day-24-github-config-diff.png)

這個成果證明需求已進入 Git，不代表已核准或完成部署。現有 PR description 沒有自動帶入 CI 來源，獨立的設定檢查與必要 review 也仍需安排；PR 建立成功不能替代這些條件。

## Operator 將服務合約轉成工作負載

Day 21、22 的 Kopf Operator 讀取 `Microservice`，管理 Todo API 的 `Deployment` 與 `Service`，加入 probes、資源需求與 OpenTelemetry（OTel）設定。它會檢查所有權，避免直接覆寫不屬於這筆 CR 的同名資源，也會定期檢查並補回缺少的受管資源。

這讓常見部署細節集中在平台實作，服務需求則留在 CR。不過，Operator 的預設仍是針對目前 Todo API，不是所有 Web 服務都能直接套用。

前面展示的健康回報如下。重點不是看見 `Ready=True`，而是先確認 `status.observedGeneration` 對應目前的 `metadata.generation`，再看 conditions：

![Todo API 的 Microservice 狀態，顯示 Operator 回報的 generation 與 Ready condition](../assets/day-22-operator-ready-status.png)

image 拉取失敗時，Operator 能回報 `Stalled`；舊副本仍可用，也不會被當成新版已就緒。資源補回與同名衝突的演練則讓我們確認，控制迴路不只在第一次建立時執行。

Day 25 的 Argo CD Health Check 將這份回報轉成 `Progressing`、`Healthy` 或 `Degraded`。目前已有只同步 CR 的 `Application` 設定，但不能僅憑檔案存在，就宣稱某筆 PR 已經完成同步、rollout 與健康判斷。

## 從入口查部署，再用遙測查實際請求

Day 26 的 Backstage Catalog 保存 `todo-api` 的服務資訊，Kubernetes plugin 使用唯讀身分查詢 `todo` 裡符合 label 的工作負載。開發者能從同一個服務入口找部署現況，不需要為了查詢取得寫入權限。

展示時要核對查詢到的 image、目標副本與 Pod 狀態，而不是只數有幾個綠色圖示。目前 plugin 不會直接顯示 `Microservice` conditions，也不會自動產生 PR 到部署的完整時間線。

部署就緒之後，還要確認 BFF 到 Todo API 的實際請求。Day 13 已展示 Grafana 中的跨服務 Trace，可以從同一筆請求查看兩個服務的 span：

工作負載就緒與業務操作成功是不同的證據。Backstage 回答資源現在長什麼樣子，CR conditions 回答 Operator 觀察到哪一版，Grafana 則協助查看請求的延遲、錯誤與 log；它們不應互相冒充。

## 把成果與尚待整合的部分放在一起

Kubernetes 提供服務的執行與連線資源，GitOps 管理要同步的設定，CI 產出 image，遙測資料則讓我們在執行時找問題。這些部分已有各自的範例，但「各自存在」與「已串成同一條交付路徑」仍有差別：

| 範圍 | 已有內容 | 還不能據此宣稱什麼 |
| --- | --- | --- |
| Kubernetes 與 Operator | Todo 工作負載、`Microservice` CRD、Kopf Operator；已接管既有 API，驗證更新、補回與所有權衝突 | 僅支援目前 Todo API 的合約，沒有通用服務、多環境或 HA 管理 |
| GitOps | 原生 manifest 與只同步 `Microservice` 的兩種 `AppProject`／`Application` 設定 | 不能同時共管 Todo API 工作負載；仍需核對設定來源、同步 revision 與所有權移交 |
| 可觀測性 | Todo API／BFF 的 OTel instrumentation、Collector、Prometheus、Loki、Tempo 與 Grafana 設定 | 單一副本、`emptyDir` 的範例不具備正式環境的持久化與高可用性 |
| CI 與 image | PR 檢查、服務專屬 release workflow、GHCR image 與 digest 輸出 | Todo 的 .NET 服務尚無 unit test project，也沒有自動更新 GitOps 設定 PR；Operator 另有 Python 測試 |
| Backstage | Catalog、Kubernetes plugin 查詢設定、Template 與已展示的真實設定 PR | 不會自行核准版本，也沒有完整交付事件時間線；Guest 示範不適合公開入口 |
| CR health | Operator 回寫當前 generation 的 `Ready`／`Stalled`；已有 Lua 與整合操作範例 | 仍需取得同一次 Git 設定變更的 Application health 與工作負載結果，不能只憑範例宣稱接通 |
| API 權限與政策 | Operator／查詢身分的有限 RBAC，以及 Gatekeeper 機制、風險與導入情境 | 不代表完整團隊隔離；沒有 Gatekeeper 強制政策與拒絕回饋的整合結果 |

系列最後聚焦交付權限與資源政策，沒有展開 Day 01 原先預告的服務間流量安全。這些成果不能據此視為完整的執行期安全設計。

沿著交付路徑看，Backstage 的 PR、Operator 的工作負載與查詢能力已有成果；CR 同步與健康判斷已有設定，還需要同一次換版的整合紀錄；Gatekeeper 則仍是政策設計。把這些狀態分開，才能知道下一個缺口在哪裡。

其中，原生 manifest 與 Operator 路徑不是要同時修改同一組工作負載。改由 Operator 管理時，必須明確移交資源所有權，避免 Argo CD 依原生 YAML 還原設定，Operator 又依 CR 改回去。

Backstage 是這套內部開發者平台（Internal Developer Platform，IDP）的入口，不是整個平台。它能整合服務資訊與查詢，但 Kubernetes 資源現況仍不能取代 Git review 紀錄，也不會自動形成完整交付時間線。

## 平台不是把責任集中到一個團隊

平台團隊要決定共用規則與預設值，服務團隊則仍需對 image、業務行為與發布需求負責。把 `Deployment` 收進 Operator，不代表平台能替應用程式決定正確的健康檢查；把版本更新收進表單，也不代表 reviewer 不必檢查變更。

這個界線需要持續調整。若 `Microservice` CRD 把所有 Kubernetes 欄位都暴露出去，平台只是在 Backstage 表單後面放了一份更難用的 YAML。反過來說，若合約太窄，團隊碰到合理例外時只能繞過平台。好的平台合約會從常見服務的需求開始，明確保留擴充與例外處理的路徑。

## 先接通一個服務與一個環境

要接通剩下的路徑，可以繼續限定 `todo-api` 與既有 `todo` Namespace，作為本系列的 Dev 環境，不急著同時支援所有服務或另建環境。沿用已有的 CR 同步設定，確認受審查的 PR 合併後，由 Argo CD 提交同一筆 CR、Operator 更新工作負載，再從 Backstage 查到這次版本的結果。

這條路徑至少要能追到：CI 產出的 digest、設定 PR 的合併 commit、Argo CD 同步的 revision、CR 的 generation，以及工作負載的更新結果。Operator 已測過 image 拉取失敗與恢復，整合後仍要確認同樣的錯誤能回到使用者看得到的位置，舊版健康狀態不會掩蓋新版失敗。

Gatekeeper 政策則依 Day 29 的方式逐項導入。每加一條限制，都應同時證明必要請求仍能通過、不該允許的操作會被拒絕，也要確認拒絕原因能回到使用者看得到的位置；不要一次啟用所有政策後，才猜是哪一層擋住服務。

## 從這裡繼續演進

完成最小路徑後，下一輪問題通常會落在這幾個方向：

- **可靠性**：定義服務水準目標（Service Level Objective，SLO）、錯誤預算與發布門檻，讓發布判斷有團隊同意的依據。
- **成本**：將 Namespace 配額、資源需求與實際用量放進回饋流程，避免平台只會提供資源、不會顯示代價。
- **開發者體驗**：觀察 Backstage 表單、PR 審查與部署等待中最常卡住的步驟，再改善合約、錯誤訊息或自助文件。
- **AI 輔助開發**：讓 AI 協助產生初稿、查詢文件或整理事故資訊。AI 產出的設定仍要通過 schema、政策、測試與 PR review，不能因為產生得快，就取得更寬的部署權限。

## 思考問題

如果明天要讓另一個團隊把服務交給這個平台，他們需要手動理解哪些 Kubernetes 細節？哪些資訊又無法從目前的 `Microservice` 合約、Git 歷史或 Backstage 的資源現況找到？

先找出其中一個會讓交付卡住的缺口，為它定義輸入、責任與可觀察的結果，再決定需要哪個工具。
