# Day 30 - 30 篇後：把微服務交付流程變成平台

Day 01 問的是：微服務能跑之後，誰負責建置、部署、觀察與維護？一路走到前一篇的服務間授權，可以看見這些工作有不同的輸入、權限與判斷條件，不能交給一個「部署成功」的訊號概括。

這 30 篇留下了 Todo 的部署、可觀測性與 CI 範例，也做出了管理既有 Todo API 的 Kopf Operator。Backstage 已有查詢入口，Git PR 到 CR 的交付路徑則仍未串接。它還不是一套能直接上線的完整平台；這篇把已完成與尚未完成的部分放在一起，整理下一步需要哪些證據。

## 哪些已有範例，哪些仍是設計？

Kubernetes 提供服務的執行與連線資源，GitOps 管理要同步的設定，CI 產出 image，遙測資料則讓我們在執行時找問題。這些部分已有各自的範例，但「各自存在」與「已串成同一條交付路徑」仍有差別：

| 範圍 | 已有內容 | 還不能據此宣稱什麼 |
| --- | --- | --- |
| Kubernetes 與 Operator | Todo 工作負載、`Microservice` CRD、Kopf Operator；已接管既有 API，驗證更新、補回與所有權衝突 | 僅支援目前 Todo API 的合約，沒有通用服務、多環境或 HA 管理 |
| GitOps | Argo CD `AppProject` 與 `Application`，讀取既有原生 manifest | 尚未讀取以 `todo` 為目標的 Dev `Microservice` 設定 |
| 可觀測性 | Todo API／BFF 的 OTel instrumentation、Collector、Prometheus、Loki、Tempo 與 Grafana 設定 | 單一副本、`emptyDir` 的範例不具備正式環境的持久化與高可用性 |
| CI 與 image | PR 檢查、服務專屬 release workflow、GHCR image 與 digest 輸出 | Todo 的 .NET 服務尚無 unit test project，也沒有自動更新 GitOps 設定 PR；Operator 另有 Python 測試 |
| Backstage | 執行環境、Catalog、Kubernetes plugin 查詢設定；Template 與本機檢查 | Git 權限、真實 PR、Dev 設定來源與 CR 部署尚未接通，UI 邊界仍需驗證 |
| CR health | Operator 回寫當前 generation 的 `Ready`／`Stalled`，已測試錯誤 image 與恢復；另有 Lua 範例 | 自訂 Argo CD Health Check 尚未套用，沒有 CR 路徑的 Application health 結果 |
| 安全與流量 | Operator／查詢身分的有限 RBAC，以及 Gatekeeper、Todo Istio 的概念與驗收情境 | 不代表完整團隊隔離，也沒有這組服務的強制政策或 mTLS 實測結果 |

## 把現況放回平台藍圖

相較於 Day 01 的藍圖，現在可以明確指出哪些交接還沒完成。下圖的實線表示已運作或已有設定的關係，虛線表示尚待串接或導入；有來源檔不等於已完成整合驗證。

```mermaid
flowchart TD
    Source["應用程式 source 與 release tag"] --> CI["CI<br/>驗證、建置並推送 GHCR，輸出 digest"]
    CI -.->|"交接發布內容"| Developer["開發者"]
    Developer --> Backstage["Backstage 入口<br/>已有 Catalog 與查詢設定<br/>Template PR 仍待串接"]
    Backstage -.->|"提出設定 PR"| Config["Git 設定儲存庫<br/>待建立 checks、review 與受保護分支"]
    Config -.->|"待設定 CR 同步來源"| Argo["Argo CD"]
    Native["Git 中的原生 Todo manifest"] -->|"既有 Application 範例的來源"| Argo
    Argo -.->|"不與 Operator 共管同一組 child"| Workload["Kubernetes<br/>Todo Deployment、Service、Pod"]
    Argo -.->|"規劃中的 CR 同步"| CR["Microservice<br/>image、port、conditions"]
    Manual["目前手動提交 CR"] --> CR
    CR --> Operator["已部署的 Kopf Operator<br/>todo｜單一副本"]
    Operator -->|"已明確接管 Todo API"| Workload
    Operator -->|"當前 generation 的 status"| CR
    Workload -->|"OTel 資料"| Observability["Collector 與遙測 backend<br/>Grafana 查詢"]
    Backstage -->|"Kubernetes plugin 查詢設定"| Workload
    Security["安全與流量設計<br/>已有有限 RBAC<br/>Gatekeeper／Todo mesh 待導入"] -.-> Workload
    Next["持續演進<br/>可靠性、成本、開發者體驗、AI 輔助"] -.-> Backstage
    Next -.-> Observability
```

其中，原生 manifest 與 Operator 路徑不是要同時修改同一組工作負載。改由 Operator 管理時，必須明確移交資源所有權，避免 Argo CD 依原生 YAML 還原設定，Operator 又依 CR 改回去。

Backstage 是這套內部開發者平台（Internal Developer Platform，IDP）的入口，不是整個平台。它能整合服務資訊與查詢，但 Kubernetes 資源現況仍不能取代 Git review 紀錄，也不會自動形成完整交付時間線。

## 平台不是把責任集中到一個團隊

平台團隊要決定共用規則與預設值，服務團隊則仍需對 image、業務行為與發布需求負責。把 `Deployment` 收進 Operator，不代表平台能替應用程式決定正確的健康檢查；把版本更新收進表單，也不代表 reviewer 不必檢查變更。

這個界線需要持續調整。若 `Microservice` CRD 把所有 Kubernetes 欄位都暴露出去，平台只是在 Backstage 表單後面放了一份更難用的 YAML。反過來說，若合約太窄，團隊碰到合理例外時只能繞過平台。好的平台合約會從常見服務的需求開始，明確保留擴充與例外處理的路徑。

## 先接通一個服務與一個環境

要接通剩下的路徑，可以繼續限定 `todo-api` 與既有 `todo` Namespace，作為本系列的 Dev 環境，不急著同時支援所有服務或另建環境。CRD 狀態合約與 Operator 已運作，模板與 Catalog 也指向 `todo`；下一個缺口是讓受審查的設定 PR 真正經過 Argo CD，交給同一個 Operator，再確認 Backstage 查到本次版本更新的結果。

這條路徑至少要能追到：CI 產出的 digest、設定 PR 的合併 commit、Argo CD 同步的 revision、CR 的 generation，以及工作負載的更新結果。Operator 已測過 image 拉取失敗與恢復，整合後仍要確認同樣的錯誤能回到使用者看得到的位置，舊版健康狀態不會掩蓋新版失敗。

安全與流量機制則依實際需求逐項導入。每加一條限制，都應同時證明必要請求仍能通過、不該允許的操作會被拒絕；不要一次啟用所有政策後，才猜是哪一層擋住服務。

## 從這裡繼續演進

完成最小路徑後，下一輪問題通常會落在這幾個方向：

- **可靠性**：定義服務水準目標（Service Level Objective，SLO）、錯誤預算與發布門檻，讓發布判斷有團隊同意的依據。
- **成本**：將 Namespace 配額、資源需求與實際用量放進回饋流程，避免平台只會提供資源、不會顯示代價。
- **開發者體驗**：觀察 Backstage 表單、PR 審查與部署等待中最常卡住的步驟，再改善合約、錯誤訊息或自助文件。
- **AI 輔助開發**：讓 AI 協助產生初稿、查詢文件或整理事故資訊。AI 產出的設定仍要通過 schema、政策、測試與 PR review，不能因為產生得快，就取得更寬的部署權限。

先找出其中一個會讓交付卡住的缺口，為它定義輸入、責任與可觀察的結果，再決定需要哪個工具。
