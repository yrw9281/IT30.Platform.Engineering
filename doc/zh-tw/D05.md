# Day 05 - CRD 是什麼：讓 Kubernetes 認識自訂資源

## 前一日主題回顧

我們已經知道如何用 `Deployment`、`Service`、`Ingress` 與 Kustomize 交付 Todo 微服務。但請回想一下，如果新進工程師想建立 `reminder-api`，他仍得理解哪些 label 不可改、probe 怎麼寫、Service selector 要對誰、observability 設定放在哪裡。把這些規則寫進文件當然有幫助，但文件不會阻止一份不合規的 YAML 被部署。

如果開發者的真正意圖只是「我要一個使用這個 image、開這個 port 的微服務」，為什麼他必須先學會所有 Kubernetes 底層資源？這就是 **Custom Resource Definition（CRD）** 要解決的問題。

## 問題與設計：讓 Kubernetes 認得團隊的語言

Kubernetes 原生知道 `Deployment`、`Service`、`ConfigMap` 等資源，但不知道「我們團隊定義的一個可交付微服務」是什麼。CRD 可以把這個領域名詞註冊進 Kubernetes API；註冊後，叢集會接受一種新的 `kind`，例如 `Microservice`。

這裡有四個名稱很像、責任卻不同的角色：

- **CRD**：資源型別的 API 定義，包含 group、version、名稱與 schema。
- **Custom Resource（CR）**：開發者建立的一筆實際資源，例如 `reminder-api`。
- **Controller / Operator**：監看 CR，將意圖轉成 Deployment、Service 等原生資源，並回報 status。
- **API Server**：依 CRD schema 驗證並儲存 CR，但不會自動創造任何工作負載。

最後一點很重要。安裝 CRD 後能成功執行 `kubectl get microservices`，不代表平台功能已經存在；沒有 controller 的 CRD 只是一份被 API Server 保存的資料。

## 先設計最小合約，不要複製 PodSpec

平台合約最容易犯的錯，是把整個 Kubernetes `PodSpec` 原封不動塞進 CRD。這樣看似保留彈性，實際上只是替原生 YAML 換了一層名字；平台無法提供可靠預設，開發者也還是要學會所有低階選項。

對 Todo 系統的第一版，我們先收斂成服務擁有者真的需要決定的欄位：使用哪個 image、服務 port 是多少。副本策略、受管 labels、健康檢查、預設 resource policy 與 telemetry 注入則保留給平台。以下是這份合約的核心 schema：

```yaml
apiVersion: apiextensions.k8s.io/v1
kind: CustomResourceDefinition
metadata:
  name: microservices.platform.example.io
spec:
  group: platform.example.io
  scope: Namespaced
  names:
    plural: microservices
    singular: microservice
    kind: Microservice
    shortNames:
      - ms
  versions:
    - name: v1alpha1
      served: true
      storage: true
      subresources:
        status: {}
      schema:
        openAPIV3Schema:
          type: object
          properties:
            spec:
              type: object
              required:
                - image
                - port
              properties:
                image:
                  type: string
                  minLength: 1
                port:
                  type: integer
                  minimum: 1
                  maximum: 65535
            status:
              type: object
              properties:
                phase:
                  type: string
                observedGeneration:
                  type: integer
                managedResources:
                  type: object
                  properties:
                    deployment:
                      type: string
                    service:
                      type: string
```

`v1alpha1` 是一個誠實的訊號：合約仍可能演進，不表示可以隨意破壞已存在的 CR。即使在 alpha 階段，也應盡早思考欄位新增是否相容、舊資料如何讀取，以及未來 version conversion 的成本。

## 開發者看到的 CR 應該像服務意圖

裝好 CRD 後，服務團隊提交的內容會像這樣，而不是一大段 `Deployment`：

```yaml
apiVersion: platform.example.io/v1alpha1
kind: Microservice
metadata:
  name: reminder-api
  namespace: todo-dev
  labels:
    app.kubernetes.io/owner: todo-team
spec:
  image: ghcr.io/yrw9281/reminder-api:0.1.0
  port: 8080
```

這裡的 `spec` 屬於服務擁有者：他可以要求某個 image 和 port。反過來說，下面這類資訊不應由他手動聲稱：

```yaml
# Operator 觀察後寫回的狀態範例
status:
  observedGeneration: 4
  phase: Progressing
  managedResources:
    deployment: reminder-api
    service: reminder-api
```

啟用 `status` subresource 後，平台 controller 可以有專門權限更新 `status`，而一般服務提交者只管理 `spec`。這個界線會防止「表單已送出」被誤當成「服務已健康」，也是 Day 24 Argo CD health check 的基礎。

這裡的 `phase` 是用來說明早期 CRD 概念的簡化草圖。Day 19 會將它收斂為以 `observedGeneration` 與 `conditions` 為主的合約；後續 Operator、Argo CD health 和 Portal 都以那份較精確的狀態模型為準。

## CRD 不是萬能抽象

將概念提升成 CRD 有成本。每一個欄位都是未來要維護的 API 承諾；太早抽象會把尚未穩定的部署細節鎖死，太晚抽象則讓各團隊各自發明 YAML。值得做成 CRD 的通常是跨多個服務重複出現、需要控制器持續維持、而且具備清楚領域語意的能力。

CRD 也不會取代 RBAC、Policy 或 Git review。它只能約束結構與欄位範圍；誰可以建立、image 是否來自受信任的 GHCR repository、何時能進 Production，仍要由後續的 GitOps 與安全治理共同處理。

## 測試與驗證

安裝 CRD 後，以下命令可以直接驗證合約：

```bash
# 先確認 CRD schema 可被 API Server 接受
kubectl apply --server-side --dry-run=server -f microservice-crd.yaml

# 驗證合法 CR 的欄位形狀
kubectl apply --server-side --dry-run=server -f reminder-api.yaml

# 驗證 port 超出範圍時應在寫入前被拒絕
kubectl apply --server-side --dry-run=server -f invalid-reminder-api.yaml
```

預期行為是：合法的 CR 可以被接受但不會自動產生 Deployment，因為 Operator 尚未實作；不合法的 `port` 或缺少 `image` 應在 API 邊界被拒絕。未知欄位則應依 CRD schema 的 pruning 規則被移除，不能把它誤解為驗證失敗。這個差異能幫我們確認自己理解 CRD 是「合約」而不是「自動化本身」。

## 結語

CRD 讓 Kubernetes 開始理解平台的領域語言，但所有服務意圖仍需要一個可信的地方保存與仲裁。下一階段會把 Git 變成單一真實來源，讓每個 `Microservice` 變更都能 review、追溯與重建。
