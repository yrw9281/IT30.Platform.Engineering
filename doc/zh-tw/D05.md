# Day 05 - K8s 擴充性基石：CRD (Custom Resource Definition) 簡介

## 前言

Kubernetes 內建 `Deployment`，卻不知道什麼是團隊定義的「微服務」。Custom Resource Definition（CRD）可以把這個領域概念註冊成 API；Custom Resource（CR）則是開發者提交的實際物件。

## 先定義 API，再實作行為

```yaml
apiVersion: apiextensions.k8s.io/v1
kind: CustomResourceDefinition
metadata:
  name: microservices.platform.example.io
spec:
  group: platform.example.io
  names:
    kind: Microservice
    plural: microservices
  scope: Namespaced
  versions:
    - name: v1alpha1
      served: true
      storage: true
```

CRD 只讓 API Server 接受與驗證物件；真正將 `Microservice` 展開為原生資源的是後續的 controller 或 Operator。

## 合約的邊界

設計 CRD 時，`spec` 僅暴露服務擁有者需要決策的欄位；例如 Image、Port 與環境變數。資源限制、標籤、監控與安全預設應由平台管理，避免每個服務重新發明一遍。

## 結語

CRD 是平台和開發者溝通的宣告式合約。下一階段把 Git 變成合約與部署狀態的唯一真實來源。
