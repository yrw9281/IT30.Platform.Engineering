# Day 04 - Helm 與 Kustomize：怎麼管理不同環境的設定

## 前一日主題回顧

昨天我們為 `todo-api` 拆出了 Deployment、Service 與 Ingress。第一份 YAML 寫完時通常很順，但很快就會有第二個問題：Dev 只需要一個副本、Staging 要接測試網域、Prod 要三個副本與較高的資源限制。若直接複製整個目錄三次，下一次修改 readiness probe 時，誰能保證三個環境都被同步修改？

這不是單純的「懶得複製貼上」。設定漂移會讓同一個服務在不同環境表現出不同故障模式，也讓 code review 難以分辨某個差異是刻意設計，還是某次忘了同步。

## 問題與設計：哪些內容應相同，哪些內容可以不同？

先不要急著選工具。對 `todo-api` 而言，可以先把設定分成三類：

- **服務不變的骨架**：container port、label 合約、probe 路徑、Service selector。
- **環境差異**：Namespace、hostname、副本數、資源大小、image digest。
- **可重用的套件能力**：像 Argo CD、Prometheus、OpenTelemetry Collector 這類被多個團隊安裝的元件。

Helm 與 Kustomize 都能減少重複，但它們處理複雜度的方式不同。**Helm** 以 template 加 values 產生 manifest，特別適合發布可配置的套件；**Kustomize** 以原生 YAML base 疊加 overlay，特別適合讓環境差異在 review 中一眼可見。

## Kustomize：把 Todo API 的共同骨架放在 base

若團隊擁有 `todo-api` 的部署 YAML，我會先規劃成「一份可讀的 base，加上少量環境 overlay」。下面是預計採用的目錄形狀，僅是概念設計，尚未建立在 repository 或 `src/`：

```text
apps/
  todo-api/
    base/
      deployment.yaml
      service.yaml
      kustomization.yaml
    overlays/
      dev/kustomization.yaml
      prod/kustomization.yaml
```

`src/` 目前沒有這些來源檔，以下 YAML 與 template 都是概念片段，不能直接渲染或套用。實作前要先建立對應檔案，再以實際環境值與使用的 Kustomize、Helm 版本確認。base 的 `kustomization.yaml` 只列出服務不可變的組成，不偷渡某個環境專屬值：

```yaml
# 規劃片段：apps/todo-api/base/kustomization.yaml
apiVersion: kustomize.config.k8s.io/v1beta1
kind: Kustomization
resources:
  - deployment.yaml
  - service.yaml
labels:
  - includeSelectors: true
    pairs:
      app.kubernetes.io/name: todo-api
      app.kubernetes.io/part-of: todo-platform
```

Prod overlay 則只描述「相對於 base 有什麼不同」。這個小檔案比另一份完整 Deployment 更容易被 review。

```yaml
# 規劃片段：apps/todo-api/overlays/prod/kustomization.yaml
apiVersion: kustomize.config.k8s.io/v1beta1
kind: Kustomization
resources:
  - ../../base
namespace: todo-prod
images:
  - name: ghcr.io/yrw9281/todo-api
    newTag: "0.1.0"
replicas:
  - name: todo-api
    count: 3
patches:
  - path: ingress-host.yaml
```

Kustomize 的優點是最後仍可看到完整的 Kubernetes YAML；缺點也很明顯：當差異越來越多、patch 互相覆蓋，讀者得在腦中合成多層內容。它不是把所有邏輯都塞進 overlay 的理由。若一個 patch 複雜到難以預測輸出，應重新檢討 base 邊界或把功能抽成明確元件。

## Helm：把可安裝的能力包成有參數的 Chart

Helm 比較像 package manager。Chart 作者決定 template 的結構，使用者透過 values 調整允許的旋鈕。以下是同一個服務概念上的 values 片段：

```yaml
# 規劃片段：values-prod.yaml
replicaCount: 3

image:
  repository: ghcr.io/yrw9281/todo-api
  tag: "0.1.0"

ingress:
  enabled: true
  className: platform-ingress
  host: todo.example.internal

resources:
  requests:
    cpu: 250m
    memory: 256Mi
```

template 可以使用 `Values` 將設定投影成 Deployment。這裡只展示 image 與 replica 的關鍵行，避免把整份 manifest 重新藏進模板。

```gotemplate
# 規劃片段：templates/deployment.yaml 的關鍵欄位
spec:
  replicas: {{ .Values.replicaCount }}
  template:
    spec:
      containers:
        - name: todo-api
          image: "{{ .Values.image.repository }}:{{ .Values.image.tag }}"
```

Helm 的強項是將多人共用的安裝知識封裝起來，例如 Argo CD 或 observability stack。代價是 template 很容易變成另一種難讀的程式語言：一連串巢狀 `if`、預設值與例外條件，會讓使用者無法從 values 推理實際產物。Chart 應提供清楚的 values schema 與文件，而不是把每個 Kubernetes 欄位都暴露成參數。

## 不必把 Helm 與 Kustomize 當成宗教選擇

這個系列的初步決策是：Todo 團隊擁有的應用程式使用 Kustomize 管理環境 overlay；平台安裝的第三方元件優先使用官方或受維護的 Helm Chart。這不是唯一正解，而是基於兩個實際考量：

1. 應用程式的環境差異需要讓服務團隊在 Git review 中直接看懂。
2. 平台元件往往有龐大的可配置面，重新手寫一套 YAML 反而失去上游 Chart 的維護價值。

兩者也可在同一個交付流程中共存。重點是 Git 中保存的必須是可審查的意圖，且任何人都能重現渲染結果。

## 測試與驗證

尚未建立 `apps/` 目錄、Chart 或對應 `src/` 檔案。範例實作完成後，先在提交前渲染而不直接套用：

```bash
# 檢視 Kustomize 為 Prod 組合出的完整 manifest
kustomize build apps/todo-api/overlays/prod

# 檢視 Helm values 會產生什麼，而不連線到叢集
helm template todo-api ./charts/todo-api -f values-prod.yaml
```

驗收時不只比較「有沒有輸出 YAML」，還要逐項確認：Prod 是否真的是 `todo-prod` Namespace、image 是否為預期版本、replica 是否為三，以及 base 的 readiness probe 和 Service selector 是否仍被保留。若任何環境都需要複製一大段 Deployment 才能調整一個值，代表目前的抽象仍不夠好。

## 結語

設定管理的目標不是讓 YAML 看起來花俏，而是讓共用骨架與環境差異各歸其位。即使原生資源已管理得很好，開發者仍得理解 `Deployment`、`Service`、`Ingress` 等低階細節；下一篇要擴充 Kubernetes API，讓平台直接理解「我想建立一個微服務」。
