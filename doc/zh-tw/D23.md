# Day 23 - 設定 Argo CD Health Check 與 Notification

## 前一日主題回顧

Day 22 的 PR merge 只代表 `Microservice/reminder-api` 進入 GitOps 的 desired state。Argo CD 可以同步它到 Kubernetes，卻不會預設理解自訂資源的 `Ready=False`：它可能正在啟動、image 拉不下來，或是 Operator 已停止收斂。若 Portal 把 `Synced` 顯示成「服務已可用」，這個綠色狀態反而會誤導使用者。

要完成 IDP 的回饋閉環，Argo CD 必須讀懂 Day 18、21 定義的 `Microservice.status.conditions`，並只在有意義的狀態轉換時發出 notification。

## 先把「尚未完成」和「已經卡住」分開

`Ready=False` 不一定是失敗。剛建立 Deployment、等待 image pull、等待兩個 Pod 變 ready 時，都可能是正常的 `Progressing`；反過來說，若 Operator 已經判斷某個錯誤無法靠重試自行恢復，就不該讓 Portal 無限顯示「部署中」。

因此在 Day 18 的 `Ready` condition 之外，Operator 需要用一個明確的 `Stalled` condition 表示收斂已卡住：

```yaml
# 規劃片段：同一個 Microservice 的兩種 status 情境
status:
  observedGeneration: 8
  conditions:
    - type: Ready
      status: "False"
      reason: WaitingForDeployment
      message: "Waiting for 2 available replicas"

---

status:
  observedGeneration: 8
  conditions:
    - type: Ready
      status: "False"
      reason: ImagePullBackOff
      message: "The configured image cannot be pulled"
    - type: Stalled
      status: "True"
      reason: ImagePullBackOff
      message: "Manual intervention is required"
```

這不是為了多造一個欄位，而是讓 health model 有足夠資訊區分暫態與需要人處理的失敗。Operator 也必須確認 `observedGeneration` 已追上 `metadata.generation`；舊版本留下的 `Ready=True` 不能被拿來替新 image 背書。

## 將 CR conditions 映射為 Argo CD health

Argo CD 可在 `argocd-cm` 的 `resource.customizations.health.<group>_<kind>` 設定 Lua health check。以下是針對 `platform.example.io/Microservice` 的規劃片段：它先拒絕過期 status、再辨識 `Stalled=True`、最後才接受當前 generation 的 `Ready=True`。

```yaml
# 規劃片段：argocd-cm 的 custom health 設定
apiVersion: v1
kind: ConfigMap
metadata:
  name: argocd-cm
  namespace: argocd
data:
  resource.customizations.health.platform.example.io_Microservice: |
    hs = {}

    if obj.status == nil or
       obj.status.observedGeneration ~= obj.metadata.generation then
      hs.status = "Progressing"
      hs.message = "Waiting for the operator to observe this generation"
      return hs
    end

    for _, condition in ipairs(obj.status.conditions or {}) do
      if condition.type == "Stalled" and condition.status == "True" then
        hs.status = "Degraded"
        hs.message = condition.message or condition.reason
        return hs
      end
    end

    for _, condition in ipairs(obj.status.conditions or {}) do
      if condition.type == "Ready" and condition.status == "True" then
        hs.status = "Healthy"
        hs.message = condition.message or "Managed resources are ready"
        return hs
      end
    end

    hs.status = "Progressing"
    hs.message = "Waiting for managed resources to become ready"
    return hs
```

Lua script 收到的 `obj` 是 Kubernetes resource 的內容，回傳值至少包含 `status`，可再提供 `message`。`Healthy`、`Progressing`、`Degraded` 是 UI 與 Application health 聚合會使用的語意，不能隨意拿來當字串標籤。所有未知、尚未觀察或暫態錯誤應有保守的 `Progressing`；已知不可自動收斂的錯誤才變成 `Degraded`。

這段 script 是規劃片段，專案尚未套用，也必須與 Operator 的 status contract 一起測試。Lua 若假設了 Operator 從未寫入的 condition，Argo CD 只會持續回報錯誤的健康狀態。

## `Synced`、resource health、Application health 是三個層次

現在可以把 Day 07 的狀態模型補完整：

```text
Synced
  Git 宣告已被套用；不代表 Pod 已可用。

Microservice health
  Lua 依 CR 當前 generation 的 conditions 回報 Progressing、Healthy 或 Degraded。

Application health
  Argo CD 聚合受管資源 health，作為 notification 與 Portal 回饋的依據。
```

例如 `reminder-api` image 拼錯時，Argo CD 可能已成功建立 CR，所以 Sync status 是 `Synced`；Operator 觀察到 ImagePullBackOff 後設 `Stalled=True`，custom health 才會將 Application 轉成 `Degraded`。把這三層資料拆開，Portal 才能說出「設定已同步，但工作負載無法啟動」，而不只是顯示紅色或綠色。

## Notification 應記錄轉換，不應在每次 reconcile 騷擾使用者

Argo CD Notifications 的 trigger 可以根據 Application status 決定何時送出 template。對 IDP 而言，值得通知的是「某個 revision 已成功健康」與「某個 revision 進入 Degraded」這類狀態轉換，而不是每一輪 `Progressing`。

```yaml
# 規劃片段：argocd-notifications-cm 的 trigger
data:
  trigger.on-microservice-healthy: |
    - when: app.status.operationState.phase in ['Succeeded'] and app.status.health.status == 'Healthy'
      oncePer: app.status.sync.revision
      send: [webhook-delivery-status]

  trigger.on-microservice-degraded: |
    - when: app.status.health.status == 'Degraded'
      oncePer: app.status.sync.revision
      send: [webhook-delivery-status]
```

`oncePer` 以 revision 去重，讓同一 revision 不會在每次 controller reconcile 重複發出相同通知。這份第一版設計的承諾是「每個 revision 的首次 Healthy／Degraded 觀察」，不是完整記錄每一次 health oscillation。實際 trigger 還需依 Argo CD Notifications 版本與 Application workflow 調整；若產品需要 `Healthy -> Degraded -> Healthy` 的完整時間線，sender 或受信任 relay 必須提供穩定的事件 occurrence ID，不能用 receiver 收到 request 的當下時間拼湊。Day 24 會再由 IDP 端做第二層 idempotency，因為網路重送始終可能發生。

## 測試與驗證

CRD、Operator、Argo CD custom health 與 Notifications 尚未實作。後續會用三種 status fixture 驗證 Lua mapping，再驗證 notification 去重：

```text
預期演練：
1. metadata.generation 已更新但 observedGeneration 落後，確認 Application 是 Progressing。
2. Ready=True 且 observedGeneration 相同，確認 Application 是 Healthy。
3. Stalled=True 且原因為 ImagePullBackOff，確認 Application 是 Degraded，Portal 可讀到原因。
4. 同一 revision 重複 reconcile，確認 Healthy 或 Degraded trigger 不重複送出相同事件。
5. 新 revision 開始時，確認舊 revision 的 Healthy 結果不會覆蓋新 revision 的 Progressing。
```

驗收並非只看 Lua syntax 是否正確，而是確認 health 的每一個顏色都對應到 Operator 觀察到的真實狀態與目前 generation。

Argo CD 現在能區分「已同步」、「正在收斂」與「需要介入」，並在狀態轉換時發出事件。但通知送出不等於 Portal 資料正確。下一篇會處理 webhook receiver 的驗證、去重與狀態機，讓 delivery history 成為可靠投影。
