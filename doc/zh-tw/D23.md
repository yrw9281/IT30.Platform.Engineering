# Day 23 - 讓 Argo CD 判斷 `Microservice` 是否健康

## 設定同步了，服務就能用嗎？

設定 PR 合併後，Argo CD 若能同步 `Microservice`，`Synced` 只表示 Git 宣告與叢集中的資源一致。Pod 可能還在等 image，Operator 也可能尚未處理這次變更。把同步成功顯示成「服務可用」，會讓開發者找錯排查方向。

Argo CD 能替標準資源判斷 health，卻不知道我們的 `Microservice` 什麼時候才算健康。要讓它判斷自訂資源，得先約定 Operator 如何寫入 status，再給 Argo CD 一段自訂 Health Check。

## Operator 必須提供當前版本的狀態

目前的 CRD 只有 `status.phase`、`observedGeneration` 和 `managedResources`；**還沒有 `conditions`，也沒有會更新 status 的 Kopf Operator**。這裡先定義健康判斷需要的合約：

```text
metadata.generation     這次 spec 變更的版本
status.observedGeneration   Operator 已處理的版本
Ready=True              此版本的受管工作負載可用
Stalled=True            此版本遇到需要介入的錯誤
```

`Ready=False` 不一定代表失敗：Deployment 剛建立、Pod 尚未 ready 時，仍可能持續收斂。只有 Operator 明確設 `Stalled=True`，我們才把它判為 `Degraded`。若 `observedGeneration` 落後 `generation`，即使看到舊的 `Ready=True`，也只能回報 `Progressing`。

## 用 Lua 將 CR status 映射到 health

Argo CD 可在 `argocd-cm` 的 `resource.customizations.health.<group>_<kind>` 設定 Lua script。下方是**尚未套用叢集**的關鍵段落，判斷順序不能顛倒：先排除過期狀態，再判斷卡住，最後才接受健康。

```yaml
data:
  resource.customizations.health.platform.example.io_Microservice: |
    hs = {}

    if obj.status == nil or
       obj.status.observedGeneration ~= obj.metadata.generation then
      hs.status = "Progressing"
      hs.message = "Waiting for the operator to observe this generation"
      return hs
    end

    for _, condition in ipairs(obj.status.conditions or {}) do
      if condition.type == "Stalled" and condition.status == "True" then
        hs.status = "Degraded"
        hs.message = condition.message or condition.reason or "Reconciliation stalled"
        return hs
      end
    end

    for _, condition in ipairs(obj.status.conditions or {}) do
      if condition.type == "Ready" and condition.status == "True" then
        hs.status = "Healthy"
        hs.message = condition.message or "Managed resources are ready"
        return hs
      end
    end

    hs.status = "Progressing"
    hs.message = "Waiting for managed resources to become ready"
    return hs
```

`Stalled=True` 優先於 `Ready=True`，避免同時存在的矛盾 condition 被解讀為健康。若 Operator 尚未寫入 condition，或 `Ready=False` 且未卡住，就維持 `Progressing`。這段 script 需要與 CRD schema、Operator 寫入邏輯一同建立，不能只放進 Argo CD 就期待狀態自動出現。

還要留意 `argocd-cm` 是 Argo CD 的既有設定；套用範例中的整份 ConfigMap 可能覆蓋其他設定。整合時應把這個 key 併入現有設定並驗證 Argo CD 版本，而不是直接取代整份 ConfigMap。

## 用幾個狀態確認判斷邊界

| CR 的觀察結果 | 預期 health | 為什麼 |
| --- | --- | --- |
| 沒有 status，或 `observedGeneration` 落後 | `Progressing` | 不能拿舊的 `Ready=True` 代表新版本 |
| 當前版本 `Ready=True`、未卡住 | `Healthy` | Operator 已確認受管資源可用 |
| 當前版本 `Stalled=True` | `Degraded` | Operator 明確要求介入 |
| 當前版本沒有上述真值 | `Progressing` | 尚不能宣稱完成或失敗 |

目前只能檢查設定檔的 YAML 結構；沒有 Operator 產生的 conditions，也沒有 Argo CD 實際執行 Lua 與聚合 Application health 的結果。等這些元件存在後，要用上述四種 CR 狀態測試資源與 Application health，尤其檢查新 image 更新後，舊的健康結果不會被沿用。**Application 的 `Synced` 和 health 是不同狀態。**
