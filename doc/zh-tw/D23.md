# Day 23 - IDP API：用 Pull Request 與 Schema 檢查 YAML

## 前一日主題回顧

Day 22 的 IDP API 能把 `reminder-api` 渲染到 `idp/todo/reminder-api/dev/<request-id>` branch。若 API 接著直接 merge `main`，只是把手動 `kubectl` 換成較漂亮的表單；錯誤設定、越權變更與缺少 review 的風險都還在。

自動化適合加速建立 branch、產生清楚 diff、執行 validation、附上脈絡等可判斷的工作。Production 影響、資源成本或例外理由仍需要人在 Pull Request review 中做取捨。

## 一份 IDP 請求應走過哪些關卡？

從 Portal 到 GitOps `main` 的路徑可以先拆成可觀察的階段：

```text
Portal request
  -> input and authorization validation
  -> render Microservice YAML
  -> static YAML / CRD schema validation
  -> create config branch and commit
  -> create Pull Request
  -> config repository checks
  -> human or policy-required review
  -> protected-branch merge
  -> Argo CD observes the new revision
```

前四步避免明顯無效的資料佔用 reviewer 時間；後四步確保「結構合法」不會被誤當成「可以接受」。例如 `port: 8080` 符合 schema，仍不代表這個 image digest 被批准推進 Production，或它不會讓既有 service name 衝突。

## 驗證有層次：語法、合約、政策與狀態

將所有檢查叫做「validation」很方便，卻會讓錯誤訊息沒有方向。這個平台至少區分四種：

| 類型 | 典型問題 | 最適合在哪裡執行 |
| --- | --- | --- |
| YAML 語法 | 縮排、型別、無法解析的文件 | IDP API render 前後 |
| CRD schema | 缺少 image、port 超出範圍、未知 spec 欄位 | API 與 config PR check |
| 組織政策 | GHCR image repository、resources、privileged 設定 | PR 預檢與 Day 27–28 Admission Control |
| 目前狀態 | 名稱是否已被使用、branch 是否衝突、目標環境是否凍結 | API 與 merge 前檢查 |

Day 27–28 才會導入正式的 OPA Gatekeeper，因此本日不會假裝 policy engine 已經在 cluster 執行。現在可以先讓 API 檢查明確的 platform allow list、讓 config CI 做 schema/dry-run；正式 admission policy 上線後，再將相同規則收斂到叢集入口，避免只靠其中一層。

## PR 要讓 reviewer 看懂「為什麼」和「會改什麼」

IDP 產生的 Pull Request 不該只是一句「automated update」。它至少要帶出提出者、team、目標環境、image digest、request/delivery ID 與 validation 結果，讓 reviewer 不必切回 Portal 才知道這筆變更的上下文。

```yaml
# 規劃片段：IDP 產生的 PR metadata
branch: idp/todo/reminder-api/dev/dpl_01J...
changedFiles:
  - apps/reminder-api/overlays/dev/microservice.yaml
context:
  requester: todo-team-member
  environment: dev
  image: ghcr.io/yrw9281/reminder-api@sha256:******
  deliveryId: dpl_01J...
checks:
  - yaml-parse
  - microservice-schema
  - config-render
```

PR title 與 description 由後端用結構化欄位產生，並對使用者輸入做適當跳脫；不要把未受信任的 service description 直接插進 Markdown、shell command 或 YAML annotation。變更也應盡可能小：理想情況下只新增或修改一個環境中的 `Microservice` 文件，而不是順手重排整個 config repository。

## 後端先做同步檢查，repository 再做獨立檢查

IDP API 可以在建立 PR 前做快速失敗的檢查；repository CI 則是第二道、不可被 Portal 繞過的防線。兩者重複某些 schema validation 並不違反 DRY，因為它們守住不同的 trust boundary：前者改善使用者回饋，後者確保任何 Git 來源都無法跳過規則。

```bash
# 規劃片段：config PR 中未來會執行的檢查
kustomize build apps/reminder-api/overlays/dev

# 在受控驗證叢集或相符 CRD schema 中驗證完整 render，而非直接改 Production
kustomize build apps/reminder-api/overlays/dev \
  | kubectl apply --server-side --dry-run=server -f -
```

這兩行命令是未來 config PR 的概念性檢查，專案目前沒有 config repository、CRD 或驗證叢集，不能執行。它們也不是完整安全策略：`kustomize build` 只證明 render 能產生結果，server-side dry-run 只證明 API schema 接受結果，兩者都不能證明 Workload 最後一定 healthy。

## 讓錯誤回到正確的人與正確的欄位

Portal 不應只顯示 Git provider 的原始錯誤；它需要區分可以由使用者修正、需要 reviewer 決定與需要平台維護者處理的失敗。

```json
{
  "deliveryId": "dpl_01J...",
  "status": "ValidationFailed",
  "errors": [
    {
      "field": "image",
      "code": "unapproved_registry",
      "message": "請選擇 `ghcr.io/yrw9281/` 中、含 immutable digest 的 image。"
    }
  ]
}
```

當 YAML/schema 已經合法但 review 拒絕時，狀態應是 `Rejected`，並連結 PR review，而不是假裝是輸入驗證失敗。當 branch 因同名服務或 concurrent request 衝突時，應回傳可重試或需要合併的明確狀態；不應吞掉衝突後留下一個使用者永遠看不見的 branch。

## 重送、重複與 race condition 都是產品行為

Portal request 可能因網路重送，兩位工程師也可能同時申請 `reminder-api`。Day 22 的 idempotency key 處理同一使用者同一操作；但不同 request 的名稱衝突還需要 Git branch 與 merge-time protection。

```text
same idempotency key
  -> return the original delivery request

different request, same service/environment
  -> detect existing path or open PR
  -> explain conflict before creating a second ambiguous change

two valid branches race to merge
  -> protected branch and CI re-check final diff
```

這些狀態應被記錄在 delivery timeline。平台不是只在「順利跑完」時才有使用者體驗；能否解釋為什麼重複請求被拒絕、如何安全重試，也是自助服務的一部分。

## 測試與驗證

Git provider integration、config CI 與 CRD 都未實作。後續會用成功與失敗分支驗證整條 PR 防呆流程：

```text
預期演練：
1. 合法 reminder-api request 只建立一個 branch、一個小型 diff 與一個可 review 的 PR。
2. 讓 YAML 語法或 CRD schema 失敗，確認 PR 不會被建立或無法合併，Portal 顯示欄位級錯誤。
3. 以不在 `ghcr.io/yrw9281/` 的 image、重複服務名稱與環境凍結測試 policy/state failure 的不同訊息。
4. 重送同一 key 與平行送出相同服務，確認不會產生重複 deployment 意圖。
5. 嘗試用 API token 直接 merge protected branch，確認權限被拒絕並留下 audit 記錄。
```

驗收後，`main` 中的每一份 `Microservice` 都應有一條可追到 Portal request、validation、PR review 與 merge 的歷史。

IDP 已能把自助請求變成受驗證、可 review 的 GitOps 變更，但 Portal 還只知道 PR 是否合併。下一篇讓 Argo CD 讀懂 `Microservice.status.conditions`，區分「YAML 已同步」與「Operator 管理的服務真的健康」。
