# Day 03 - 應用程式交付解構：Deployment、Service 到 Ingress 的流量骨架

## 前言

一個可被外部使用的微服務至少要處理工作負載、副本選擇與入口流量。先看清這些資源的責任，才能理解平台要替開發者隱藏多少細節。

## 三個資源的合約

```yaml
apiVersion: v1
kind: Service
metadata:
  name: catalog-api
spec:
  selector:
    app: catalog-api
  ports:
    - port: 80
      targetPort: http
```

`Deployment` 管理 Pod 副本；`Service` 以 label selector 提供穩定的服務端點；`Ingress` 則把 HTTP 路徑導向 Service。

```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: catalog-api
spec:
  rules:
    - host: api.example.internal
      http:
        paths:
          - path: /catalog
            pathType: Prefix
            backend:
              service:
                name: catalog-api
                port:
                  number: 80
```

## 設計提醒

資源間的 label 必須一致，並以 readiness probe 決定 Service 是否將流量送進 Pod。這些可預期卻容易漏掉的設定，是後續 CRD 抽象化的候選項目。

## 結語

服務上線不是一份 YAML，而是一組互相連結的宣告。明天會用 Helm 與 Kustomize 管理這些宣告在不同環境的差異。
