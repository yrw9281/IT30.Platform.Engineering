# Day 03 - 部署一個服務時，Deployment、Service 與 Ingress 各做什麼

## 前一日主題回顧

昨天的 `Deployment` 告訴 Kubernetes：「請一直維持指定數量的 `todo-api` Pod。」但如果 BFF 或瀏覽器要呼叫它，事情還沒有結束。Pod 會被重建、IP 會改變、剛啟動的服務也不一定已經能接流量；一個健康副本和一個可被正確找到、正確路由的服務，是兩件不同的事。

今天用 Todo 系統常見的「取得待辦清單」請求，拆解它穿過叢集時必經的骨架。為了聚焦資源責任，本文暫時省略 BFF，讓 `todo-api` 直接成為 Ingress backend；未來改回 BFF，也不會改變 `Deployment`、`Service` 與 `Ingress` 各自的工作。

## 問題與設計：請求到底走到哪裡？

一條理想的 HTTP 請求不該依賴某個 Pod IP：

```text
Client
  -> Ingress controller
  -> todo-api Service
  -> ready todo-api Pod
  -> application container
```

這四個節點各自處理不同問題：

- `Deployment` 決定應有多少個 Pod、使用哪個 image，以及如何逐步替換版本。
- `Service` 透過 label selector 找出可用 Pod，提供穩定的 DNS 名稱與虛擬 IP。
- `Ingress` 描述 hostname 與 path 要導向哪個 Service。
- Ingress controller 才是實際讀取 `Ingress` 資源並處理 L7 流量的元件；只有建立 `Ingress`，叢集不會憑空出現入口能力。

## 先建立工作負載：Deployment 與健康檢查

以下是日後 `todo-api` 可能採用的概念片段。目前 `src/` 沒有對應 manifest，不能直接套用；實作前應先建立對應來源檔，並依實際 image、健康檢查端點與叢集設定核對。最需要留意的不是 image 名稱，而是 `selector` 與 Pod template label 必須完全對得起來；這個關係建立後不應隨意改動。

```yaml
# 規劃片段：todo-api Deployment
apiVersion: apps/v1
kind: Deployment
metadata:
  name: todo-api
  namespace: todo-dev
spec:
  replicas: 2
  selector:
    matchLabels:
      app.kubernetes.io/name: todo-api
  template:
    metadata:
      labels:
        app.kubernetes.io/name: todo-api
        app.kubernetes.io/part-of: todo-platform
    spec:
      containers:
        - name: todo-api
          image: ghcr.io/yrw9281/todo-api:0.1.0
          ports:
            - name: http
              containerPort: 8080
          readinessProbe:
            httpGet:
              path: /health/ready
              port: http
            initialDelaySeconds: 5
          livenessProbe:
            httpGet:
              path: /health/live
              port: http
            initialDelaySeconds: 15
```

`readinessProbe` 回答「現在能不能收請求」；它失敗時，Pod 不會被 Service 選入可用 endpoints。`livenessProbe` 回答「process 是否卡住到應重啟」；它失敗時 kubelet 可能重啟 container。兩者不能共用一個隨便回 `200` 的端點，否則啟動中的服務可能過早接流量，或暫時無法連到資料庫時被不斷重啟。

## 將會變動的 Pod 藏在穩定的 Service 後面

Service 不直接「啟動」任何東西，它只根據 selector 尋找符合 label 且 ready 的 Pod。這也是為什麼名稱、label 和 port 必須被視為一份跨資源合約。

```yaml
# 規劃片段：todo-api Service
apiVersion: v1
kind: Service
metadata:
  name: todo-api
  namespace: todo-dev
spec:
  type: ClusterIP
  selector:
    app.kubernetes.io/name: todo-api
  ports:
    - name: http
      port: 80
      targetPort: http
      protocol: TCP
```

這裡的 `targetPort: http` 對應到 Deployment container port 的名稱，而不是硬寫 `8080`。這不是必須遵守的唯一寫法，卻能讓讀者在一串 YAML 中更容易追蹤「Service 的 80 最後進到哪個 container port」。

當 selector 寫錯時，Service 仍然可能存在，卻沒有任何 endpoints；看到 `Service` 成功建立並不代表流量真的有地方可去。這是交付時非常常見的「看起來都綠色，打 API 卻失敗」原因。

## 讓外部請求進來：Ingress 是路由規則，不是入口本身

`Ingress` 將 HTTP hostname 和 path 對應到 Service。以下使用 `platform-ingress` 作為規劃中的 IngressClass 名稱；實作階段必須依實際選用的 controller 調整，而不能假定任何叢集都已安裝 NGINX 或其他 controller。

```yaml
# 規劃片段：todo-api 對外路由
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: todo-api
  namespace: todo-dev
spec:
  ingressClassName: platform-ingress
  rules:
    - host: todo.dev.example.internal
      http:
        paths:
          - path: /api/todos
            pathType: Prefix
            backend:
              service:
                name: todo-api
                port:
                  name: http
```

這裡也刻意不先塞 TLS、rate limit、authentication annotation 等設定。它們很重要，但若一開始所有責任都塞進範例，讀者反而看不見最基本的流量關係。平台最終可以將其中一部分做成共用預設或 policy，而不是要求每個服務複製貼上。

## 哪些問題不該被 YAML 表面掩蓋？

當請求失敗時，可以沿著骨架反查，而不是直接重啟所有 Pod：

1. Ingress controller 是否收到符合 host 和 path 的請求？
2. Ingress backend 指向的 Service 名稱與 port 是否存在？
3. Service 的 selector 是否選到 ready endpoints？
4. Pod 的 readiness 是否因應用程式、依賴服務或設定問題而失敗？

這個順序的價值在於縮小責任邊界。`Deployment` 有可用副本卻沒有 Service endpoints，通常是 label 或 readiness 問題；Service 有 endpoints 而 Ingress 仍回 404，則更可能是路由或 controller 設定問題。

## 測試與驗證

目前尚未建立 `src/` manifests 或叢集。建立對應檔案後，可以按以下計畫逐段驗證，而不是只確認 `kubectl apply` 沒有報錯：

```bash
# 檢查三個資源與 Service 實際選到的 endpoints
kubectl get deployment,service,ingress -n todo-dev
kubectl get endpointslice -n todo-dev -l kubernetes.io/service-name=todo-api

# 確認 Pod 為何尚未 ready，或驗證 probe 的事件
kubectl describe pod <todo-api-pod-name> -n todo-dev

# 先透過 Service 驗證叢集內路徑，再驗證 Ingress 路徑
kubectl port-forward service/todo-api 8080:80 -n todo-dev
curl --fail http://127.0.0.1:8080/health/ready
```

驗收不只看 HTTP 是否成功，還要能說清楚回應經過哪個 Service、哪個 selector 選到 Pod，以及 readiness 失敗時為何不該把流量送進去。

## 結語

一個服務上線不是單獨一份 Deployment，而是一組由 labels、ports 與健康狀態連結起來的資源。Dev、Staging、Prod 都需要這組骨架後，下一個問題就很現實了：我們要複製三份 YAML，還是讓差異有規則地被管理？
