# Day 19 - 設計 `Microservice` CRD：把 Kubernetes 設定收進平台合約

## 前一日主題回顧

Day 18 的 Portal 看起來只需要幾個欄位，但這些欄位一旦被寫進 Git、由 Argo CD 同步到 Kubernetes，就會成為平台對開發者的 API 承諾。若我們讓表單直接暴露整段 `PodSpec`，開發者仍要決定 selector、Service、probe、security context、資源限制與 telemetry；若欄位收得太死，第一個真實需求出現時又只能請平台工程師手動繞過。

所以今天不追求「最通用的 CRD」。我們先替 `reminder-api` 設計一份可長期維護的 `Microservice` 合約，讓開發者表達服務需求，不必理解每一個 Kubernetes 實作細節。

## 先決定誰擁有什麼決策

一份好的平台合約不是把 Kubernetes API 藏起來而已，而是清楚說明每一種決策由誰負責：

| 決策 | 第一版 `Microservice` 的擁有者 | 原因 |
| --- | --- | --- |
| 服務名稱、image digest、HTTP port、非敏感 env | 服務團隊 | 這些反映應用程式的功能與交付版本 |
| Deployment replicas、labels、resources、probe、OTel 基本設定 | 平台 Operator | 這些是跨服務一致性與平台預設 |
| Namespace、Git path、可用環境 | IDP API 與 team mapping | 不能讓表單任意選擇租戶邊界 |
| 是否健康、錯誤原因、受管資源名稱 | Operator | 必須由實際叢集狀態觀察得出 |

這張表故意讓 `replicas` 不在開發者輸入中。不是說服務永遠不需要擴展策略，而是我們還沒定義 autoscaling、環境容量與成本責任前，不應先丟一個看似方便、實際沒有治理的旋鈕。平台 API 可以演進，但每新增一個欄位都要有清楚的 owner、default 與驗證方式。

## 讓 `spec` 像服務意圖，而不是縮小版 PodSpec

以下是 `reminder-api` 的第一版 Custom Resource 規劃片段。它只使用前面定下的輸入，不把 resource limit、Service selector 或 Kubernetes secret schema 全部暴露給服務團隊。

```yaml
# 規劃片段：apps/reminder-api/overlays/dev/microservice.yaml
apiVersion: platform.example.io/v1alpha1
kind: Microservice
metadata:
  name: reminder-api
  namespace: todo-dev
  labels:
    app.kubernetes.io/owner: todo-team
spec:
  image: ghcr.io/yrw9281/reminder-api@sha256:******
  port: 8080
  env:
    REMINDER_BATCH_SIZE: "50"
    LOG_LEVEL: Information
```

`env` 在第一版只允許非敏感的 string 設定。connection string、access token、第三方 API key 不能被塞成 YAML value；後續若要支援 secret reference，也應設計成單獨、可被 RBAC 與 Policy 審查的合約，而不是讓 `env` 變成任意敏感資料的通道。

這是說明合約的規劃內容，尚未存在於 GitOps repository，也不能直接當成專案範例套用。不過讀者即使不熟悉 `Deployment` 的欄位，仍能看出服務歸屬、CI 產出的 image、監聽 port 與非敏感設定。

## 用 CRD schema 把基本錯誤擋在 API 邊界

CRD schema 不能取代所有商業規則，但應先拒絕結構明確錯誤的資料，例如缺少 image、port 超出範圍。以下是第一版 schema 的核心部分：

```yaml
# 規劃片段：microservice-crd.yaml 的 version schema
versions:
  - name: v1alpha1
    served: true
    storage: true
    subresources:
      status: {}
    schema:
      openAPIV3Schema:
        type: object
        properties:
          spec:
            type: object
            required:
              - image
              - port
            properties:
              image:
                type: string
                minLength: 1
              port:
                type: integer
                minimum: 1
                maximum: 65535
              env:
                type: object
                additionalProperties:
                  type: string
          status:
            type: object
            properties:
              observedGeneration:
                type: integer
              conditions:
                type: array
                items:
                  type: object
                  required: [type, status]
                  properties:
                    type:
                      type: string
                    status:
                      type: string
                    reason:
                      type: string
                    message:
                      type: string
                    observedGeneration:
                      type: integer
              managedResources:
                type: object
                properties:
                  deployment:
                    type: string
                  service:
                    type: string
```

`spec` 明確列出允許的欄位，未宣告的欄位會依 CRD schema 的 pruning 規則被移除，而不是被當成驗證錯誤。若平台需要拒絕 `imagee` 這類拼字錯誤，必須在 IDP API、PR check 或 validating admission policy 額外驗證。`env` 則明確是一組 string map，允許新增環境變數 key。這種結構化 schema 也讓 IDP API、Git PR checks、`kubectl` dry-run 使用同一份契約，而不是每一層重寫不同驗證。

image 是否來自允許的 GHCR repository、名字是否符合 team 規則、或一個環境最多能建立多少服務，則不是單靠這段 schema 就能安全表達的事。它們會在 IDP API、Git review 與 Day 27–28 的 admission policy 各自守住對應邊界。

## `status` 是觀察結果，不是前端欄位

`subresources.status` 將 status 的寫入路徑與 spec 分開。使用者與 GitOps 操作 `spec`；Operator 根據真正的 Deployment、Service、Pod readiness 等結果更新 status。比起一個模糊的 `phase: Healthy`，第一版會採用 Kubernetes 常見的 conditions 模式：

```yaml
# 規劃片段：Operator 未來寫回的狀態
status:
  observedGeneration: 7
  managedResources:
    deployment: reminder-api
    service: reminder-api
  conditions:
    - type: Ready
      status: "False"
      reason: DeploymentUnavailable
      message: "Waiting for 2 available replicas"
```

`observedGeneration` 讓我們知道 Operator 已觀察到哪一版 `spec`。如果使用者剛更新 image、metadata 的 generation 已變成 8，但 status 仍寫著 7，Portal 和 Argo CD 就不應把舊的 `Ready=True` 當成新版本已完成。Day 24 的 health check 會直接使用這個關係，避免將「Git 已同步」誤判為「新版本已健康」。

## 合約如何演進才不會傷到使用者？

`v1alpha1` 表示這份合約仍可能調整，並不代表可以任意刪欄位或改變語意。每個 CRD version 的 `served` 與 `storage` 有不同責任：前者決定 API 是否接受該 version，後者決定叢集實際用哪個 version 儲存資料。

新增 optional field 通常比改變既有欄位的含義安全；需要不相容變更時，應規劃新的 version 與 conversion，而不是讓 Operator 猜舊資料。平台 API 的使用者是所有服務團隊，對待它的謹慎程度應接近對待公開 API。

## 測試與驗證

CRD 與 Portal 均未實作。後續會先驗證「合約能拒絕什麼」與「誰可以寫 status」，而不是只用一份合法 YAML 證明它存在：

```text
預期演練：
1. 提交缺少 image 或 port 為 0 的 CR，確認 API Server 在 admission 時拒絕；另提交含未知 `spec` 欄位的 CR，確認該欄位依 pruning 規則不會被保存。
2. 提交合法的 reminder-api CR，確認它可保存，但尚未有 Operator 時不會神奇產生 Deployment。
3. 以服務團隊身分嘗試更新 status，確認權限被拒絕。
4. 以 Operator 身分更新 Ready condition，確認 observedGeneration 和條件內容被保存。
```

這四項結果能驗證我們不是只做了一份漂亮 YAML，而是建立了使用者意圖、API validation 與 controller observation 的真正界線。

有了合約，API Server 能先擋下明確的結構錯誤；它仍不會自動建立任何 Kubernetes resource。下一篇進入 Operator 模式與 Kopf：controller 要如何把這份意圖持續翻譯成 Deployment、Service 與可回報的 `status`。
