# Day 19 - Operator 模式與 Kopf：怎麼處理 CRD 事件

## CR 已經建立，Deployment 在哪裡？

Day 18 的 `Microservice` 可以把 `todo-api` 的 image 與 port 存進 Kubernetes，但 API Server 不會因此替它建立工作負載。有人修改 `spec.image`、手動刪除受管 Service，或讓 Pod 卡在 image pull 時，誰要發現並處理差異？

這是 Operator 要做的事。它讀取 `Microservice.spec`，決定應有的 Deployment、Service 等資源，觀察目前狀態後執行一次 `reconcile`。持續接收事件、反覆處理差異的整體模式是**控制迴路（Control Loop）**。現有專案只有 CRD 和範例 CR，尚未實作 Operator；以下先把它的責任與驗收條件說清楚。

## Kopf 接到事件後要做什麼？

本系列規劃使用 Python 的 Kopf（Kubernetes Operator Pythonic Framework）實作 controller。對一筆 `todo-api` CR，一次處理可依照這個順序思考：

```text
讀取 Microservice 的名稱、namespace、UID 和 spec
  -> 計算受管 Deployment 與 Service 的目標設定
  -> 建立或更新資源，保留明確的 ownership
  -> 觀察 Deployment 是否對應最新 spec 且已可用
  -> 更新 Microservice.status
```

Kopf 可用 handler 處理資源建立與 `spec` 變動。handler 不能假設事件只會送一次：API 呼叫可能暫時失敗、process 可能重啟，同一筆 CR 也可能再次被處理。建立與更新資源要有可重試的行為；已存在的 Deployment 應更新成目標狀態，而不是再建立第二份或把「已存在」當成整次失敗。

只監看 CR 的建立與 `spec` 修改，還不夠宣稱能修正 drift。若 Service 被人刪除，CR 的 `spec` 沒有變，Operator 不一定會收到新的 CR 事件。要守住「Service 會被補回」的承諾，必須另外監看受管 child resources，或設定有明確頻率與成本的重新檢查機制。啟動後重新讀取既有 CR，也比只等新事件可靠。

## 為什麼選 Kopf？

Go 的 controller-runtime、Kubebuilder 提供成熟的強型別 API 與 controller 工具；本系列想先把重點放在 `Microservice` 的欄位所有權、重試和健康狀態，因此規劃以 Kopf 表達事件處理。選 Python 能減少一些框架樣板，但不會代替 Kubernetes RBAC、部署方式、錯誤處理或自動測試。

| 觀察到的事 | Operator 應如何處理 | 不能誤報成什麼 |
| --- | --- | --- |
| 第一次建立 CR | 建立受管 Deployment 與 Service | CR 通過 schema 就等於服務就緒 |
| 更新 `spec.image` | 更新同一個 Deployment，等待新 Pod ready | 舊版 Pod 已可用，所以新版也成功 |
| Service 遭刪除 | 重新建立受管 Service，並留下可觀察原因 | 因沒有 CR 更新就忽略 |
| image 無法拉取 | 維持尚未就緒，回報明確原因 | API 已接受資源，所以 `Ready=True` |

現有 CRD 的 `status` 只有 `phase`、`observedGeneration` 與受管資源名稱；表中的 `Ready` condition 是規劃中的擴充，不是目前能由 Kopf 回寫的既有欄位。

## Ownership 與失敗重試

Deployment、Service 這類專屬 child resources 應指向所屬 `Microservice` 的 UID，避免刪除 CR 時誤刪同 Namespace 的其他資源。若有外部 DNS 或資料庫需要額外清理，再評估 finalizer；不能只因為框架支援，就讓刪除卡在無法完成的外部呼叫。

API Server 暫時不可用時，handler 應留下明確錯誤並依重試策略再試；輸入若已確定不合規，則回報可診斷的失敗，不要用廣泛的 `except` 把它吞掉。status 也要誠實：送出建立 Deployment 的請求，不等於 Deployment 已 available。

## 怎麼驗證它是一個 controller？

目前沒有 Kopf 原始碼或測試，不能執行 Operator 演練。實作後至少要反覆測四件事：同一 CR 重送只留下同一組 child resources；修改 image 更新的是同一份 Deployment；刪除 Service 後能由明確事件或重新檢查補回；新 Pod 無法啟動時 status 不會回報健康。要證明的是收斂，不是第一次建立成功的畫面。
