# Day 29 - 把 Gatekeeper 政策放進平台交付流程

前一篇說明 Gatekeeper 如何檢查資源內容。但把一條規則切成拒絕模式之前，還要回答：既有工作負載符合嗎？Operator 產生的設定會不會被擋？開發者從哪裡知道怎麼修正？

今天延伸 Todo API 的資源額度與 image，說明政策導入和交付回饋。Gatekeeper 政策仍未實作，也沒有對應的叢集測試結果；以下的允許／拒絕與錯誤流向都是導入時要確認的情境。

## limits 與 image 要檢查到什麼程度？

前一篇用 `privileged` 說明機制，這裡再看兩種常見要求。寫政策前，要先把「符合要求」定義到能判斷的程度。

| 政策情境 | 要說清楚的規則與回饋 | 通過後仍沒有保證什麼 |
| --- | --- | --- |
| 必須設定 CPU／memory limits | 哪些 container 要設定、缺哪個欄位，是否還要限制數值範圍 | 額度適合這個服務、效能足夠，或 Namespace 總額受到限制 |
| image 只能來自核准來源，並以 digest 指定版本 | 核准的 registry／repository 邊界、digest 格式，以及違規欄位 | image 由受信任 CI 建置、沒有漏洞，或已獲准部署到這個環境 |

目前 Operator 為 Todo API 設定了 requests 與 limits，但這不代表 BFF、Web 或其他工作負載都有相同設定。CPU limit 可能造成 throttling，memory 超限可能導致容器被終止；「欄位存在」與「額度合理」要分開看。Namespace 的總資源預算仍要由 `ResourceQuota` 等機制處理。

image 來源不能只比對是否包含 `ghcr.io/yrw9281`。規則需要辨識完整的 registry 與 repository 邊界，避免相似字串或其他 repository 混進允許範圍。digest 固定內容版本，卻不是建置來源證明；若要證明來源，還需要 CI 紀錄、簽章或其他供應鏈驗證機制，不能只靠 image 字串。

Backstage 模板已限制 digest 輸入，但目前自訂資源定義（Custom Resource Definition，CRD）的 `spec.image` 仍接受 tag。有人可以不經模板直接提交自訂資源（Custom Resource，CR），因此表單限制不能取代 API 端政策。若要全面要求 digest，也要先盤點既有 tag 設定與其他 image 使用方式。

## audit 盤點既有資源，執行模式決定如何回應

Gatekeeper 的 audit 會定期評估符合範圍的既有資源，回報違規，不會替它們修改設定。它與 admission 處理的是不同時間點：一個看已儲存的資源，一個處理新的 API 請求。

`Constraint.spec.enforcementAction` 則決定違規請求的處理方式：

| 模式 | 對違規請求的作用 | 導入時怎麼使用 |
| --- | --- | --- |
| `dryrun` | 不阻擋，也不以 `warn` 模式回傳警告 | 配合 audit 盤點違規，確認規則與範圍是否合理 |
| `warn` | 回傳警告，不阻擋 | 提醒提交者；仍需確認呼叫端是否呈現 API 警告 |
| `deny` | 拒絕符合違規條件的請求 | 修正與例外流程準備好後，再啟用強制限制 |

Gatekeeper 的 `dryrun` 不等於 Kubernetes server-side dry-run。後者是在不儲存資源的情況下執行 API 請求檢查，不是這份 Constraint 的執行模式。

既有不合規資源不會因切換 `deny` 就消失，但後續落在檢查範圍內的更新可能被拒絕。即使只是換 image，整份更新後的設定仍可能違規。因此盤點時要確認的不只有目前能不能跑，還包括下一次更新能不能提交。

## 導入前，把預期結果列出來

假設規則選到正確的資源與 container、webhook 正常，且已啟用 `deny`，至少要確認下列情境。這些是待驗證的要求，不是已有的通過紀錄：

| 情境 | 預期結果 |
| --- | --- |
| 一般或 init container 缺少政策要求的 limit | 拒絕，指出 container 與缺少的欄位 |
| image 來自未核准 repository，即使帶有 digest | 拒絕，指出來源不符 |
| image 來自核准 repository，但仍使用 tag | 若政策要求 digest，拒絕並說明版本格式要求 |
| 設定符合全部適用政策 | 不因這組政策拒絕；仍需通過其餘 API 檢查 |
| 既有資源違規 | audit 回報，資源不會被自動修正或刪除 |

例外要有適用資源、理由、負責人與重新檢討時間。若任何提交者都能自行加 label 跳過政策，那個 label 就不是可信的例外審查。誰能修改 Constraint、排除 Namespace 或調整例外標記，也必須由授權與管理流程限制。

webhook 無法連線或逾時時，要另外確認 webhook 設定的 `failurePolicy` 與其他影響範圍的設定。放行可能讓違規設定進入叢集，拒絕則可能阻擋正常交付；這與 Constraint 的 `deny` 是不同層的取捨。

## 沿著 CR、`Deployment` 與 Pod 找拒絕位置

平台交付不只有一次資源寫入。規劃中的路徑是 Argo CD 同步 `Microservice`，Operator 依 CR 建立 `Deployment`，再由 Kubernetes controller 建立 Pod。Gatekeeper 拒絕哪一層，決定錯誤先回到誰手上。

| 拒絕位置 | 第一個收到或能觀察錯誤的元件 | 要往哪裡找 |
| --- | --- | --- |
| Argo CD 提交 `Microservice` | Argo CD | 同步操作的錯誤與政策訊息；新 CR 設定未成功寫入 |
| Operator 提交 `Deployment` | Operator | Kubernetes API 回應與 Operator log；CR 已寫入，不代表工作負載更新成功 |
| ReplicaSet controller 建立 Pod | ReplicaSet controller | ReplicaSet 事件與 Deployment 進度；Deployment 可能已存在，卻沒有新版 Pod |

這是政策導入後的預期錯誤路徑，尚未完成整合驗證。目前 Operator 遇到 Kubernetes API 錯誤時，會記錄 HTTP status 並重試，沒有把 admission 的具體拒絕原因轉成 CR 的 `Stalled` condition。不能因 Day 22 已能回報 image 拉取失敗，就認為政策拒絕也會以同樣方式顯示。

如果拒絕發生在 Pod 建立階段，甚至沒有新 Pod 可供 Operator 查詢啟動錯誤；Deployment 最後可能因進度逾時而回報阻礙，但這仍不等於直接顯示 Gatekeeper 的拒絕理由。導入時要確認事件與 API 錯誤的可見性，再決定如何補上狀態回饋。

同一筆換版需求會經過這三層 API 請求，各層的拒絕回饋也不同。CR 同步成功後，工作負載仍可能被擋，不能把所有失敗都當成 Argo CD 同步失敗。

## 讓政策與平台預設一起演進

如果缺少 limits 是 Operator 的預設問題，應修正產生邏輯；如果 image 不合規，則要回到 CR 與設定 PR 修正需求。不要要求開發者直接修改 Operator 管理的 `Deployment`，下一次 `reconcile` 又可能把它還原。

Backstage 表單與 Git 檢查可以提早回饋，Gatekeeper 則負責叢集入口的檢查。規則變更要一起確認模板、CR 合約、Operator 產物與既有資源，不能只改 admission 政策，讓原本可交付的設定突然卡住。
