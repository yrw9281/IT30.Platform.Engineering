# Day 29 - mTLS 與 AuthorizationPolicy 各擋什麼

Day 28 的 Sidecar 說明了流量可能經過 Envoy，但經過 proxy 不等於「只有該來的服務能進來」。若 `todo-api` 只應接受 `todo-bff` 的特定呼叫，至少要分清楚兩件事：如何辨識連線兩端的工作負載，以及辨識後是否允許它存取。

Istio 的雙向傳輸層安全性（mutual TLS，mTLS）處理第一件事；`AuthorizationPolicy` 處理第二件事。現有 Todo 工作負載沒有 Istio Sidecar、專屬 `ServiceAccount` 或 mesh 政策；本篇只討論它們的責任與導入條件，不提供宣稱已生效的設定。

## mTLS 驗證工作負載，不判斷業務權限

在已正確加入 mesh 的服務間，Envoy 可使用工作負載憑證相互驗證身分，並加密傳輸。要求接收端只接受 mTLS 的 `STRICT` 模式，能擋下不符合要求的 plaintext 連線；但這只回答「對方能否以受信任的工作負載身分建立連線」，沒有回答「這個身分是否應該呼叫 `todo-api`」。

身分設計還有一個容易漏掉的前提：若 `todo-bff` 和其他服務共用預設的 `ServiceAccount`，只靠 ServiceAccount principal 無法把它們區分成兩個允許對象。規劃白名單前，得先替需要區分的工作負載建立各自的 `ServiceAccount`，確認 Pod 真正使用它，再核對 mesh 所見到的來源身分。目前的原生 Todo manifests 沒有這項設定。

## `AuthorizationPolicy` 才決定誰能呼叫

以 `todo-api` 為目標，可以規劃一個只選取其 Pod 的 `ALLOW` 政策，依來源工作負載 principal 限制只有 `todo-bff` 可呼叫。若進一步限制 HTTP method 與 path，還得確保 proxy 正確辨識協定，以及 BFF 實際呼叫的路徑與預期一致。有相符 `ALLOW` 政策時，沒有命中允許規則的請求才會遭拒；**單純沒有建立任何 `ALLOW` 政策，不能稱為預設白名單保護**。

這仍不取代應用程式的使用者授權。Istio 可辨認是哪個工作負載送來請求，卻不知道某位登入使用者是否有權讀取另一人的 Todo。Kubernetes RBAC 限制的是 API 動作，也不會替 HTTP 端點做業務權限判斷。

## 切到強制模式之前先盤點依賴

若一開始就要求 `STRICT` mTLS，沒有 sidecar 或還沒取得有效身分的必要 client 可能斷線；若 `ALLOW` 清單漏掉健康檢查、監控或背景工作，也可能讓服務看似正常啟動，實際上功能卻無法使用。導入時應先列出呼叫 `todo-api` 的來源，逐個確認專屬身分、proxy 注入、必要的 HTTP／gRPC 操作及例外路徑，再於隔離環境驗證允許與拒絕兩側。

預期至少能回答：合格的 `todo-bff` 請求是否成功且使用 mTLS？其他工作負載能否被拒絕？未注入的 client 切到 `STRICT` 後會發生什麼？拒絕原因能否從 proxy 與應用程式的觀測資訊追查？這些是**尚未執行的驗收問題**；目前沒有 Istio 設定、測試 client 或結果，也不能把規劃中的白名單說成已保護 Todo 服務。
