# Day 29 - Istio 怎麼管理微服務流量

Day 28 處理 workload 進入叢集前的設定，但 Pod 開始運行後，仍可能任意連到其他 Service。NetworkPolicy 能處理部分 L3/L4 allow/deny；若還需要 workload identity、流量 telemetry、mTLS 與 L7 授權，就需要一個共同的流量控制點。

本日用 Istio 的 Sidecar 模式說明 Service Mesh 如何接管微服務流量。Istio 尚未安裝，`src/` 也沒有安裝、`Namespace` 或流量設定檔；以下內容全為**概念設計**，不是已導入或已驗證的設定。

## Sidecar 將資料平面與控制平面分開

已注入的 Pod 會多一個 Envoy proxy。application container 維持原本的 HTTP/gRPC 呼叫方式，但每筆流量先經過本地 proxy：

```text
todo-bff application
      │
      ▼
todo-bff Envoy sidecar
      │ mTLS, identity, policy, telemetry
      ▼
network
      ▼
reminder-api Envoy sidecar
      │
      ▼
reminder-api application

istiod control plane
  └── 將憑證、服務發現與流量／安全設定發布給 Envoy
```

Envoy sidecar 是**資料平面（data plane）**，處理實際流量；`istiod` 是**控制平面（control plane）**，發布設定與工作負載憑證。Ingress Gateway 可作為叢集外流量進入 mesh 的邊界。這些能力在 application code 之外提供，但 proxy、control plane 和升級週期也都需要容量規畫與監控。

## 「無侵入」只是不必改業務程式碼

Sidecar injection 可以不修改 `todo-bff` 或 `reminder-api` 的 HTTP client code，就攔截流量。下列概念 `Namespace` 設定日後應新增為 `src/security/istio/todo-dev-namespace.yaml`：

```yaml
# 規劃片段：只讓 Todo Dev Namespace 進入 sidecar mesh
apiVersion: v1
kind: Namespace
metadata:
  name: todo-dev
  labels:
    platform.example.io/team: todo
    istio-injection: enabled
```

加入 label 不會改變已運行的 Pod；workload 必須重新建立，才會注入 `istio-proxy`。導入前還要確認：

- 每個 container 的 CPU/memory request 能否承受 sidecar 額外成本。
- readiness、startup、liveness probe 能否和 proxy 啟動順序共存。
- HTTP/gRPC port 是否有清楚協定，避免 Envoy 錯誤分類流量。
- 對外 egress、第三方 API、資料庫或未注入 workload 是否需要例外路徑。
- 加入 proxy 後，Day 10–14 的 log、metric、trace correlation contract 是否仍成立。

因此，「無侵入」指的是業務程式碼不必為 mTLS 重寫，不代表可以略過容量、相容性、除錯與 rollout 設計。若採用 Istio revision-based upgrade，`Namespace` 應依安裝方式改用指定 revision 的 `istio.io/rev` label，不能同時混用 `istio-injection`。

## 從一個可觀察的 `Namespace` 開始

不應直接替所有 cluster `Namespace` 開啟 injection。Todo Dev 已具備 GitOps、OTel、health feedback 與 policy 設計，是適合先驗證的範圍。導入時一次只改一個可觀察的變因：

```text
1. Install / upgrade Istio control plane，先檢查版本相容性與資源預算。
2. 將 todo-dev 標記 injection enabled，僅重新部署 reminder-api。
3. 確認 Pod 有 application + istio-proxy 兩個 container，且 proxy 已連上 control plane。
4. 讓 todo-bff 也加入 mesh，檢查既有 Create Todo 呼叫與 telemetry。
5. 最後才在小範圍導入流量與安全策略。
```

若同時注入所有服務、啟用 STRICT mTLS、加入 `AuthorizationPolicy`，連線失敗時很難判斷原因是 injection、憑證、protocol 還是 policy。

## 用 Service DNS 設計流量規則

mesh 中的規則應指向 Kubernetes Service DNS，不該指向 Pod IP。以下 `DestinationRule` 只示範 connection/load-balancing 策略；概念檔日後應新增為 `src/security/istio/reminder-api-destination-rule.yaml`。mTLS 與 authorization 留到 Day 30。

```yaml
# 規劃片段：reminder-api 的 service-level traffic policy
apiVersion: networking.istio.io/v1
kind: DestinationRule
metadata:
  name: reminder-api
  namespace: todo-dev
spec:
  host: reminder-api.todo-dev.svc.cluster.local
  trafficPolicy:
    loadBalancer:
      simple: LEAST_REQUEST
```

不要隨意同時修改這類規則與其他會改寫流量的設定。同一條流量若由多個 controller 改寫，部署後發生問題時很難追查生效的策略。實作前要決定 Istio 的流量規則、service naming 與 owner boundary，再透過 GitOps 一起 review。

## Mesh 的範圍

Istio 能替 mesh 內 workload 提供 transport encryption、workload identity、traffic policy 與 proxy telemetry；它不能取代 application 層的使用者 authentication 與業務 authorization、Kubernetes RBAC、admission policy、Secret 管理、image supply chain，也不會取代 timeout、retry、circuit breaking 與 idempotency 設計。

下一步要把身分與允許的服務對象寫成規則。Day 30 將以 `todo-bff` 是否能呼叫 `reminder-api` 為例，設定 mTLS 與 `AuthorizationPolicy`。

## 後續驗證

以下指令是完成 Istio 安裝與上述 `src/security/istio/` 設定檔後才可執行的**概念驗證指令**，目前沒有結果可供宣稱：

```bash
# 規劃中的 mesh 設定靜態分析
istioctl analyze -n todo-dev

# 確認重新部署後的 Pod 有 application 與 Envoy sidecar
kubectl get pods -n todo-dev

# 檢查已注入 proxy 是否已取得 control plane 設定
istioctl proxy-status
```

驗證範圍應包含 sidecar 注入、proxy ready、既有健康檢查、Create Todo request，以及 Day 14 trace/log correlation。也要從尚未進入 mesh 的 client 發出測試請求，記錄它在啟用 STRICT mTLS 後預期受到的影響。
