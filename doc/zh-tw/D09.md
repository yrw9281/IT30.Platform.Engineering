# Day 09 - 用 Argo Rollouts 做 Canary 部署

## 前一日主題回顧

ApplicationSet 已讓 `todo-api` 依 Git 路徑一致地出現在各環境，也讓版本更新的風險更明顯。當 PR 將 `todo-api:0.1.0` 改成 `todo-api:0.1.1`，一般 `Deployment` 的 `RollingUpdate` 會逐步替換副本，但不會判斷建立待辦事項的 5xx rate 是否突然上升。它能替換 container，卻無法判斷這次替換對使用者是否安全。

假設 `0.1.1` 有一個只會在特定待辦清單名稱觸發的序列化錯誤。等所有副本替換完才發現，雖然仍可能 rollback，影響範圍已大得多。Canary 的做法是先讓少量流量走新版本，觀察明確訊號後再決定是否擴大。

## Canary 不只是慢慢更新

**Canary deployment（金絲雀發布）** 將風險拆成數個可判斷的步驟。舊版稱為 stable，新版稱為 canary；每個階段都有流量比例、停留時間與 promotion 條件。

```text
stable 0.1.0: 100% ──> 90% ──> 50% ──> 0%
canary 0.1.1:   0% ──> 10% ──> 50% ──> 100%
                         │
                         └── 不符合訊號時停止並維持 stable 路徑
```

這不同於單純逐步增加新 ReplicaSet 的副本數。若沒有 traffic routing integration，canary 的 Pod 比例不一定等於使用者實際收到的流量比例；長連線、session affinity 或負載均衡演算法都會造成差異。要精準控制 HTTP 流量，Rollout 必須整合支援它的 traffic router。

## 用 `Rollout` 表示發布步驟

Argo Rollouts 以 `Rollout` 取代 `Deployment` 管理版本切換。以下是 `todo-api` 的概念片段：`stableService` 與 `canaryService` 會分別指向穩定與候選 ReplicaSet；實作時還必須依實際選用的 Ingress controller 或 Service Mesh 補上 `trafficRouting` provider。本專案的 `src/` 尚無此 manifest，複製前必須先建立對應檔案，並完成 Argo Rollouts、兩個 Service 與 traffic router 的設定。

```yaml
# 規劃片段：todo-api Rollout 的 Canary steps
apiVersion: argoproj.io/v1alpha1
kind: Rollout
metadata:
  name: todo-api
  namespace: todo-staging
spec:
  replicas: 6
  selector:
    matchLabels:
      app.kubernetes.io/name: todo-api
  template:
    metadata:
      labels:
        app.kubernetes.io/name: todo-api
    spec:
      containers:
        - name: todo-api
          image: ghcr.io/yrw9281/todo-api:0.1.1
  strategy:
    canary:
      stableService: todo-api-stable
      canaryService: todo-api-canary
      steps:
        - setWeight: 10
        - pause:
            duration: 5m
        - analysis:
            templates:
              - templateName: todo-api-success-rate
        - setWeight: 50
        - pause: {}
```

`pause.duration` 讓系統停留固定時間，適合初期以人工觀察為主的流程；空的 `pause: {}` 則要求人工 promotion。差別在風險承擔方式：還沒有可靠 SLI 前，不應自動跨過人尚未理解的 gate。

範例刻意不放入 `trafficRouting`。Day 03 的 `platform-ingress` 只是抽象的入口名稱，尚未選定可由 Argo Rollouts 控制的 provider。沒有 controller 支援的 YAML 不能當成可執行設定。

## 將發布判斷寫成可檢查的分析

`AnalysisTemplate` 定義發布 gate。完成 Prometheus 與 application telemetry 後，可用這類查詢檢查 `todo-api` 在最近窗口的成功率。`src/` 尚無對應檔案與 metrics pipeline，以下同樣只能作為概念示意，必須先建立相符設定後才能複製執行：

```yaml
# 規劃片段：尚待 Day 10–14 定義並建立的 metrics contract
apiVersion: argoproj.io/v1alpha1
kind: AnalysisTemplate
metadata:
  name: todo-api-success-rate
  namespace: todo-staging
spec:
  metrics:
    - name: successful-requests
      interval: 1m
      successCondition: result[0] >= 0.99
      failureLimit: 2
      provider:
        prometheus:
          address: http://prometheus.monitoring.svc:9090
          query: |
            todo_api_http_success_ratio{
              environment="staging"
            }
```

`todo_api_http_success_ratio` 是本文先命名的指標合約，不是已存在的 Prometheus metric。Day 10–14 會決定它由哪些 counter 或 histogram 計算、哪些 label 可安全使用，再把查詢接回此處。`0.99` 不是通用答案：成功率門檻、觀察時間、failure limit，以及是否納入 latency、business metric，都要依 Todo 系統的 SLO 與流量特性決定。低流量服務在兩分鐘內可能沒有足夠樣本；只看 HTTP 200 也可能漏掉待辦事項被接受但未真正寫入的業務失敗。

## Canary 不能處理所有發布風險

Canary 能降低單一新版的 blast radius，卻不能自動處理資料庫相容性、background worker、副作用重複執行或壞 migration。若 `0.1.1` 寫入舊版讀不懂的資料，即使流量切回 stable，問題仍可能留在資料層。

每個可發布版本都需要維持向前／向後相容的策略，例如 expand-and-contract migration；發布分析也要同時看技術訊號與業務訊號。Rollout 只是風險控制的一層。

## 測試與驗證

目前沒有 Argo Rollouts、traffic router 或 Prometheus，以下指令尚不能執行。先在 `src/` 建立相符的 manifests 與 metrics pipeline；首次驗證應在 Staging 建立可預期的失敗情境，不應直接在 Production 嘗試：

```bash
# 觀察 Rollout 目前位於哪個 step、stable/canary revision 與暫停原因
kubectl argo rollouts get rollout todo-api -n todo-staging --watch

# 有人工 gate 時，明確促進下一個 step
kubectl argo rollouts promote todo-api -n todo-staging

# 在受控情境觸發錯誤率，確認 AnalysisRun 停止發布
kubectl get analysisrun -n todo-staging
```

驗收分為成功與失敗兩條路：成功時確認每個流量比例、暫停與 promotion 符合設計；失敗時確認 analysis 能阻止後續 promotion、穩定版仍可服務，並記錄需要人為介入的 rollback 步驟。metrics pipeline 建好前，不能宣稱這些驗證已完成。

Canary 將是否繼續發布變成需要訊號支撐的決策，但目前還沒有足夠可靠的訊號。Day 10 轉入可觀測性：從一次 Todo 請求變慢的事件開始，建立 Metrics、Logs 與 Traces 的共同語言，讓後續的發布分析有資料可用。
