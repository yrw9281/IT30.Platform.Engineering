# Day 06 - GitOps 怎麼用 Git 管理部署狀態

## 前一日主題回顧

Day 05 的 `Microservice` CRD 讓我們能用「我要一個服務」表達意圖，但這份意圖要由哪裡保存與審查？假設某個週五晚上，Todo 團隊為了修正建立待辦事項的逾時問題，直接在 Production 執行了 `kubectl set image`。修正暫時生效，但 Git 裡仍是舊 image。下週重建環境時要部署哪個版本？又是誰基於什麼原因改了 Production？

問題不在工程師是否小心，而在於系統允許部署事實散落在終端機、CI 腳本與叢集。GitOps 將環境的期望狀態集中到一份團隊能查看、review 與重建的 Git 歷史。

## Git 裡有 YAML，還不算 GitOps

把 YAML 放進 Git 是好的開始，但還不構成 GitOps。要稱為 GitOps，至少要有三件事：

1. Git repository 保存的是環境的**期望狀態**，不是一份從未被使用的備份。
2. 每個環境變更透過 commit 與 review 進入這份期望狀態。
3. 叢集內有 agent 持續讀取 Git，將實際狀態收斂到已核准的內容。

「單一真實來源（Single Source of Truth）」指的是**我們希望系統變成什麼樣子**，不代表 Git 與叢集會在每個瞬間完全相同。Kubernetes 保存實際觀察到的狀態；GitOps controller 比對兩者，並依政策決定是否修正回 Git 宣告的目標。

```text
Git: desired state
Kubernetes: observed state
GitOps controller: compares and reconciles the difference
```

## Push 與 Pull 的差別在信任邊界

傳統做法通常是 Push-based：CI 在 build 成功後持有 kubeconfig 或 cloud credential，直接對叢集 API 執行部署。這條路雖然直接，卻可能讓每條 CI pipeline 都接觸 Production 的高權限憑證。

```text
Push-based

Source repository -> CI -> GHCR
                         │
                         └── cluster credential -> Kubernetes API
```

GitOps 則改為 Pull-based。CI 的工作是驗證原始碼並產出 image；它之後建立或更新 GitOps configuration 的 commit。部署 controller 在叢集端主動拉取已核准的 repository 內容，再使用它受限的叢集權限同步資源。

```text
Pull-based GitOps

Source repository -> CI -> GHCR
                         │
                         └── configuration commit / pull request -> Git
                                                                    │
Kubernetes API <- Argo CD <- Git repository <──────────────────────┘
```

兩種方式都能部署服務。Pull-based 將「誰能改變期望狀態」和「誰能對叢集執行 reconcile」拆成兩組可分別治理的權限。CI 不必持有廣泛的 `cluster-admin` 權限，部署也不依賴某台 runner 當下是否仍在執行。

## 先分開原始碼與環境設定的責任

先用兩個邏輯 repository 釐清責任。未來即使採用 mono-repo，也不應混淆它們：

```text
todo-microservices
  └── Account、Todo、BFF、Web 的原始碼、測試與 Dockerfile

todo-platform-config
  └── 各環境的 Kubernetes manifest、Kustomize overlay、Argo CD 宣告
```

`todo-microservices` 的 commit 表示程式碼變更；`todo-platform-config` 的 commit 表示某個已知 image 應由哪個環境使用。兩者分開後，application review 與 environment promotion 可以採用各自的審查規則；事故發生時，也能先判斷是程式碼還是部署設定變更。

以下是 config repository 的規劃目錄，延續 Day 04 的 Kustomize 邊界。本專案目前的 `src/` 沒有這些檔案，因此這個目錄與後面的 YAML 都是概念示意；要複製執行前，必須先在 `src/` 建立對應檔案，並依實際 repository、叢集與權限完成設定：

```text
apps/
  todo-api/
    base/
    overlays/
      dev/
      staging/
      prod/
platform/
  argocd/
```

升級 `todo-api` 時，最小變更可能只有一行 image reference。Git diff 讓 reviewer 直接看見環境會改什麼，不必從部署腳本推測 side effect。

```yaml
# 規劃片段：apps/todo-api/overlays/staging/kustomization.yaml
images:
  - name: ghcr.io/yrw9281/todo-api
    newTag: "0.1.1"
```

Day 16 會把這個可變 tag 改成 immutable digest。現在先記住一項原則：**部署版本必須是 configuration 的明確資料，不能由 CI 腳本執行當下隱含決定。**

## 遇到 drift 時，先看清楚再決定是否修正

假設 Git 宣告 `todo-api` 在 `todo-prod` 應有三個副本，但有人為了暫時排查問題手動把它 scale 到五個。這時候 GitOps controller 會看見差異：

```text
Git desired replicas:     3
Cluster observed replicas: 5
Drift:                     yes
```

自動修正 drift 有助於維持一致性，也可能覆蓋事故處理中的臨時操作。因此團隊要先約定哪些環境啟用 self-heal、緊急操作如何寫回 Git，以及誰能暫停同步。GitOps 不會替團隊做治理決定，只會一致地執行已選定的政策。

Git 也不是存放密鑰的地方。config repository 可以保存 External Secret 的 reference、Secret name 或加密後內容，但不應提交明文 password、token 或 private URL；這些值應由專門的 Secret 管理機制在部署階段解析。

## 測試與驗證

目前沒有 GitOps repository 或 controller，以下指令尚不能執行。完成前一節所述的 `src/` 對應檔案與控制器設定後，應以可控的 drift 情境驗證模型，而不只確認 Git 有 commit：

```bash
# 先檢查變更只影響預期的環境設定
git diff -- apps/todo-api/overlays/staging

# GitOps controller 導入後，觀察 Application 與資源是否出現差異
argocd app diff todo-api-staging

# 建立受控 drift 後，觀察是否依該環境的同步政策收斂
kubectl scale deployment todo-api --replicas=5 -n todo-staging
```

驗證時確認三件事：Git commit 能完整說明期望變更、叢集端差異可被看見，以及是否自動回復符合該環境的明確 policy。

GitOps 將部署從一次性命令改為可追溯的期望狀態，但 Git 不會自行把內容送進 Kubernetes。Day 07 導入 Argo CD，讓這條 Pull-based 控制迴路有執行者，並分清楚 `Synced` 與 `Healthy` 代表的狀態。
