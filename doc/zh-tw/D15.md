# Day 15 - 用 GitHub Actions 建立 CI 工作流程

## 前一日主題回顧

Day 14 規劃了從 `todo-api` 的錯誤率、Trace 到 Log 的調查路徑，也讓 Canary 有訊號可判斷是否停止。可是，如果 image 是工程師在本機建置後手動推進 registry，出了問題時，我們很難確認它跑過哪些測試，更難重建同一個版本。

GitOps 會依 Git 宣告的 image 收斂環境，但不負責判斷原始碼是否能建置、測試是否通過。這是持續整合（Continuous Integration，CI）要處理的事：在變更進入 registry 前，留下可重複執行、能回查來源的檢查紀錄。

## CI 的邊界：證明可交付，不直接決定部署

CI 和 CD 很常出現在同一條 pipeline 中，但權限與問題不該混在一起：

| 階段 | 要回答的問題 | 不該擁有的權限 |
| --- | --- | --- |
| CI | 這份原始碼能 restore、build、test 嗎？產物來自哪個 commit？ | Production Kubernetes 寫入權限 |
| GitOps CD | 已核准的設定是否應收斂到目標環境？資源是否健康？ | 任意修改 application source 的權限 |

先切開這條界線，Day 16 才能讓 image 可追溯，Day 17 才能把環境變更交給 Git review。CI 可以建置 `todo-api` image，也可以建立 configuration repository 的 Pull Request；不過它不需要拿著 kubeconfig 對 Production 執行 `kubectl apply`。

## 先決定 PR 要檢查什麼

上一系列以 .NET 8 建構 Todo、Account 與 BFF 服務。這裡以規劃中的 `Todo.Grpc` 工作負載說明 PR 驗證的骨架；其中的目錄與 solution 名稱沿用前作。不過目前 repository 沒有對應的 source、solution 或 workflow，所以這不是可直接執行的設定檔，而是實作時要對照實際目錄調整的設計。

```text
pull request
  │
  ├── restore：依 lock file 還原相依套件
  ├── test：執行單元或整合測試
  ├── build：以 Release 設定編譯
  └── 回饋：將失敗留在 PR，而不是留到 image 或叢集
```

一開始不用把所有檢查塞進同一個 job。像 restore、test 這類失敗後不值得繼續跑的步驟應該提早執行；container build、SBOM 產生與安全掃描的成本較高，可以排在來源品質檢查之後。這樣 PR 作者會先收到最接近問題原因的結果。

## GitHub Actions workflow 的最小權限

下列片段描述 PR workflow 應有的行為。`permissions` 只給 `contents: read`，因此它能讀取 repository，卻不能推送 image、寫入設定 repository 或碰 Kubernetes。Day 16 和 Day 17 再為需要寫入的 release job 給予獨立且受限的身分。

```yaml
# 規劃片段：.github/workflows/todo-api-ci.yaml
name: todo-api-ci

on:
  pull_request:
    paths:
      - "src/Todo/**"
      - ".github/workflows/todo-api-ci.yaml"

permissions:
  contents: read

jobs:
  validate:
    runs-on: ubuntu-latest
    steps:
      - name: Check out source
        uses: actions/checkout@v4

      - name: Set up .NET
        uses: actions/setup-dotnet@v4
        with:
          dotnet-version: 8.0.x
          cache: true
          cache-dependency-path: "src/**/packages.lock.json"

      - name: Restore locked dependencies
        run: dotnet restore src/TodoMicroservices.sln --locked-mode

      - name: Run tests
        run: dotnet test src/TodoMicroservices.sln --configuration Release --no-restore

      - name: Build release artifacts
        run: dotnet build src/TodoMicroservices.sln --configuration Release --no-restore
```

`--locked-mode` 需要專案採用並提交 `packages.lock.json`。有了 lock file，CI 才不會在同一份 source commit 下解析到不同的相依版本。若團隊尚未建立 lock file，不能只複製這一行命令，必須先訂出相依版本管理策略。`cache: true` 也只是在加速還原；`restore` 仍是 workflow 的必要步驟。

這裡的 `@v4` 是為了閱讀方便。高信任的 Production workflow 應將第三方 action 固定到審查過的 immutable commit SHA，並另外管理升級。否則 action tag 改變時，workflow 可能在沒有改動 repository 的情況下執行不同程式碼。

## 綠燈涵蓋的範圍有限

CI 顯示成功，只能表示指定的 checks 已通過，不能延伸成所有風險都已排除：

- 測試真的涵蓋使用者會遇到的所有情境。
- build 的 container image 沒有已知漏洞或不安全設定。
- migration 可以和舊版服務相容。
- Staging 或 Production 的外部依賴表現相同。

CI 先把原始碼層的失敗擋在前面。Canary、可觀測性與 Policy 則分別處理發布後行為、問題調查與資源規則；它們不是 CI 成功後就可以省略的關卡。

## 讓 PR 看得出失敗原因

比起只有「workflow failed」，PR 作者需要知道是哪一層失敗。restore 失敗時要看得到 lock file 或 private package source 的訊息；test 失敗要能對應測試名稱與結果；build 失敗則應直接看見 compiler error，不要被後續 Docker step 的長輸出淹沒。

因此，不要用 `|| true` 把每個命令接成永遠成功的 pipeline。測試失敗後讓 job 停止，才不會讓未驗證的 image 取得看似正式的版本。

## 測試與驗證

目前尚未有 source、solution 或 workflow，無法在此執行驗證。建立對應檔案後，可刻意製造下列失敗來檢查 job graph，而不是只看第一個綠燈：

```text
預期演練：
1. 讓一個 Todo unit test 失敗，確認 PR 顯示失敗測試名稱。
2. 確認 build 不會在 test job 失敗後繼續產出 artifact。
3. 修改 package lock 內容，確認 restore 以 locked mode 回報不一致。
4. 從成功的 CI run 找回 source commit、runner、測試結果與 build log。
```

驗收時也要確認 PR workflow 沒有 `packages: write`、GitHub config repository 寫入權，以及任何 Kubernetes credential。這些權限不會因為 workflow 暫時沒有使用就變得安全。
