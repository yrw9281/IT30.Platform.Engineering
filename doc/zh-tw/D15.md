# Day 15 - 在 CI 建置 Docker Image，並管理 Tag

## 前一日主題回顧

Day 14 把 restore、test 與 build 放進 PR 的 CI 檢查。通過後，服務還得封裝成 Container Image，才能由 GitOps 引用。這時如果有人說「Production 跑的是 `todo-api:v1.2.0`」，資訊其實還不夠。

tag 可以被覆寫。同一個 `v1.2.0`、`staging`，甚至常見的 `latest`，在不同時間可能指向不同 image bytes。事故發生時，若無法回答執行中的 container 精確來自哪個 source commit，就無法將 CI 紀錄與部署後的觀測結果串起來。

## Container Image 要能被回查

Container Image 是 CI 交給 GitOps 的交付物。它至少要留下以下資訊：

1. 這個 image 是由哪個 source commit 建立？
2. 建置時是否通過指定的 test 與 scan？
3. 這個 image 的精確內容識別是什麼？
4. GitOps configuration 指向的是不是同一份內容？

為了回答這些問題，先區分三種常被混用的名稱：

| 識別方式 | 主要用途 | 能否保證內容不變 |
| --- | --- | --- |
| Release tag，例如 `v1.2.0` | 人類溝通、release note、產品版本 | 否，GHCR 的 tag 可以重新指向 |
| Git SHA tag，例如 `a1b2c3d` | 由 image 回查 source revision | 否，仍是可變 reference |
| Digest，例如 `sha256:...` | 部署時精確指定 image bytes | 是，內容位址識別 |

Tag 很適合閱讀 release history，卻不是不可變的內容識別。Production 的 GitOps 宣告應使用 digest；release tag 和 Git SHA 則保留作為人能讀懂的追蹤索引。

## Multi-stage Dockerfile 只帶 runtime 所需內容

上一系列的 Todo 服務以 .NET 8 為基礎。以下片段規劃日後如何將 `Todo.Grpc` 封裝成 `todo-api` image：SDK image 負責 restore 與 publish，runtime stage 只複製服務執行所需的檔案。此 Dockerfile 尚未存在於目前 repository，實作時不能原樣假定路徑可用。

```dockerfile
# 規劃片段：src/Todo/Todo.Grpc/Dockerfile
FROM mcr.microsoft.com/dotnet/sdk:8.0 AS build
WORKDIR /src

COPY ["Common/Common.Library/Common.Library.csproj", "Common/Common.Library/"]
COPY ["Todo/Todo.Domain/Todo.Domain.csproj", "Todo/Todo.Domain/"]
COPY ["Todo/Todo.Application/Todo.Application.csproj", "Todo/Todo.Application/"]
COPY ["Todo/Todo.Infrastructure/Todo.Infrastructure.csproj", "Todo/Todo.Infrastructure/"]
COPY ["Todo/Todo.Grpc/Todo.Grpc.csproj", "Todo/Todo.Grpc/"]
RUN dotnet restore "Todo/Todo.Grpc/Todo.Grpc.csproj"

COPY . .
WORKDIR "/src/Todo/Todo.Grpc"
RUN dotnet publish "Todo.Grpc.csproj" \
    --configuration Release \
    --output /app/publish \
    /p:UseAppHost=false

FROM mcr.microsoft.com/dotnet/aspnet:8.0 AS runtime
WORKDIR /app
USER app
COPY --from=build /app/publish .
ENTRYPOINT ["dotnet", "Todo.Grpc.dll"]
```

實作時要依 repository root、project reference 與 base image 的 non-root user 確認所有路徑。SDK、source 與 NuGet cache 等 build-time 內容不應自動進入 runtime image；它們不需要隨服務一起發布。

Dockerfile 也不是安全保證。`.dockerignore` 要排除 `.git`、本機設定、測試輸出與任何 secret；secret 不能透過 `ARG` 或 `ENV` 烘進 image layer。base image 升級、scan、SBOM 與 runtime 使用者權限都需要另外納入交付規則。

## 在 CI 中產生可追溯的 tags 與 digest

本系列選擇 GitHub Container Registry（GHCR）存放 image。CI 應在 test、build 成功後才取得 GHCR push 權限。下列 workflow 是概念片段，沒有對應檔案或 GHCR package 可供執行。它使用 repository 的 `GITHUB_TOKEN` 與 `packages: write` 登入 `ghcr.io`，再把 build output digest 帶進後續 GitOps 變更。

```yaml
# 規劃片段：僅在 release tag 建立後執行的 image build job
on:
  push:
    tags:
      - "v*"

permissions:
  contents: read
  packages: write

steps:
  - name: Log in to GHCR
    uses: docker/login-action@v3
    with:
      registry: ghcr.io
      username: ${{ github.actor }}
      password: ${{ secrets.GITHUB_TOKEN }}

  - name: Build and push todo-api
    id: image
    uses: docker/build-push-action@v6
    with:
      context: ./src
      file: ./src/Todo/Todo.Grpc/Dockerfile
      push: true
      tags: |
        ghcr.io/yrw9281/todo-api:${{ github.sha }}
        ghcr.io/yrw9281/todo-api:${{ github.ref_name }}
      provenance: true
      sbom: true

  - name: Record immutable image reference
    id: digest
    run: |
      echo "value=${{ steps.image.outputs.digest }}" >> "$GITHUB_OUTPUT"
```

後續 promotion 應帶走 `steps.image.outputs.digest` 的值。`provenance` 與 `sbom` 可以提供供應鏈證據，但能不能產生、存在哪裡、由誰驗證，仍要看 GHCR 與使用工具的實際能力。workflow 有這些 flag，不代表供應鏈就已經安全。

Production image push 不應沿用 PR workflow 的權限。GHCR 發佈可使用 repository 的短期 `GITHUB_TOKEN`，只在 release job 設定 `packages: write`；再透過 protected tag、Environment protection 與 package access control 限制誰能觸發發佈及存取 private image。不要為了推送 GHCR 改用長期 Personal Access Token。

若 GHCR package 設為 private，Kubernetes cluster 也需要自己的唯讀拉取身分。這份憑證屬於部署端，不是 CI 的 `GITHUB_TOKEN`；平台應將範圍限縮為目標 package 的 `read:packages`，存成目標 Namespace 的 image pull Secret，再由受管 ServiceAccount 或 workload 的 `imagePullSecrets` 引用。Day 25 會處理這類 Namespace 與工作負載身分的邊界。

## Promotion 引用既有內容，不重建 tag

假設 CI 已建立下列對應：

```text
source commit: a1b2c3d
release tag:   v1.2.0
image tag:     ghcr.io/yrw9281/todo-api:a1b2c3d
image digest:  ghcr.io/yrw9281/todo-api@sha256:******
```

Promotion 到 Staging 或 Production 時，GitOps config 應引用最後一行，而不是請 GHCR 再解析 `v1.2.0`。即使 tag 被錯誤覆寫，已 merge 的 deployment config 仍會指向 review 過的 image bytes。rollback 也只是將 digest 改回已知正常的值。

## 測試與驗證

目前沒有 Dockerfile、GHCR package 或 image workflow，因此下面命令無法在這個 repository 執行。建立相應的 source layout 與 GHCR package 後，可用它們檢查 image 的內容和追溯性，而不只確認 `docker push` 是否成功：

```bash
# 規劃中的本機 build；實際路徑會依 source layout 確認
docker build -f src/Todo/Todo.Grpc/Dockerfile -t todo-api:trace-test ./src

# CI 推送後，以 GHCR metadata 檢視 digest，而非只讀 tag
docker buildx imagetools inspect ghcr.io/yrw9281/todo-api:v1.2.0
```

驗收時，從一個部署中的 digest 反向查回 image manifest、CI run、source commit 與 scan／SBOM 證據，並檢查 runtime image 不含 SDK、repository metadata 或明文 secret。若只能從 tag 猜測版本，這條交付鏈仍然不可追溯。
