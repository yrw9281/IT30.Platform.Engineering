# Day 31 - 30 篇後：把微服務交付流程變成平台

## 前言

Day 01 的問題很單純：微服務能跑，之後誰負責讓它穩定地被建置、部署、觀察與維護？

這 30 篇沒有試圖替每個團隊找一套萬用工具。系列做的是把交付流程拆開，辨認每個環節該由誰負責、要留下什麼宣告，以及失敗時該從哪裡回查。最後留下的是一份平台設計：開發者能交付服務、平台能執行規則、團隊能看見狀態。

## 這個系列設計了哪些能力

先從 Kubernetes 開始，是因為平台後面的自動化都建立在宣告式介面上。`Deployment`、`Service` 與 `Ingress` 定義服務如何執行與被找到；Helm、Kustomize 和 CRD 則處理環境差異與團隊自己的服務語言。這些資源讓 Controller 有一份可持續收斂的期望狀態。

接著，GitOps 把部署意圖放回 Git。CI 負責建置、測試與產出可追溯的 Container Image；GitOps Controller 負責讀取已審查的設定並同步到 Kubernetes。把兩者分開後，部署不再依賴某個 CI Job 手上的叢集權限，回復版本也回到 Git 歷史處理。

服務進入叢集後，Metrics、Logs 與 Traces 提供不同角度的觀察。OpenTelemetry 讓應用程式與後端工具之間有共同的遙測資料格式；Collector 則提供接收、處理與轉送資料的管道。可觀測性不是為了塞滿儀表板，而是讓版本部署後的調查、日常除錯和事故處理有可依循的證據。

Day 18 之後把這些元件收斂成 Internal Developer Platform（IDP）的控制流程。開發者送出少量、可驗證的服務意圖；後端把它轉成 `Microservice` CRD 的 Git 變更；Argo CD 同步它；Operator 再展開成 Kubernetes 工作負載。最後，Health Check 與 Webhook 把部署狀態投影回 Portal，讓「送出申請」和「服務健康」不再是兩個斷開的畫面。

最後幾天補上自服務必須有的邊界。RBAC 與 Namespace 限定誰能操作哪些資源；Gatekeeper 和 Rego 在資源進入叢集前檢查規則；Istio、mTLS 與 `AuthorizationPolicy` 把服務間的流量、身分與存取權限放進可宣告、可審查的設定。

## 平台不是把責任集中到一個團隊

平台團隊不應代替每個產品團隊寫 Deployment 或處理每一次發布。它的工作是定義一條安全、可觀察且足夠好用的預設路徑：哪些欄位由開發者決定，哪些細節由平台收斂；哪些變更需要 Pull Request，哪些風險要在 Admission 階段拒絕。

這個界線需要持續調整。若 `Microservice` CRD 把所有 Kubernetes 欄位都暴露出去，平台只是在 Portal 後面放了一份更難用的 YAML。反過來說，若合約太窄，團隊碰到合理例外時只能繞過平台。好的平台合約會從常見服務的需求開始，明確保留擴充與例外處理的路徑。

## 從這裡繼續演進

系列中的設定與流程是設計範例，不是可直接套用到 Production 的完整實作。目前專案的 `src/` 尚未提供對應的可執行範例；要把它變成可運作的平台，應先選一個服務與一個非 Production 環境，為每個宣告、Workflow、Operator 與 Policy 建立可測試的來源檔案，再逐步接上 GHCR、Git repository、Kubernetes cluster 和觀測後端。

完成最小路徑後，下一輪問題通常會落在這幾個方向：

- **可靠性**：定義 SLO、錯誤預算與發布門檻，讓版本部署的判斷依據來自團隊同意的服務目標。
- **成本**：將 Namespace 配額、資源需求與實際用量放進回饋流程，避免平台只會提供資源、不會顯示代價。
- **開發者體驗**：觀察 Portal 申請、PR 審查與部署等待中最常卡住的步驟，再改善合約、錯誤訊息或自助文件。
- **AI 輔助開發**：讓 AI 協助產生初稿、查詢文件或整理事故資訊，但仍把 CRD Schema、Policy、測試與 PR Review 留在可驗證的交付流程中。

## 思考問題

如果明天要讓另一個團隊把服務交給這個平台，他們需要手動理解哪些 Kubernetes 細節？哪些資訊又無法從目前的 `Microservice` 合約、Git 歷史或 Portal 狀態找到？

這兩個問題會決定平台下一個該補的能力。
