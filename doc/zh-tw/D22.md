# Day 22 - IDP API：從表單產生 YAML 並寫入 GitOps 儲存庫

## 前一日主題回顧

Day 21 定義了 Kubernetes 端的 Operator 如何把 `Microservice/reminder-api` 展開成 Deployment 與 Service。若開發者還得自己複製 CR YAML、記住 repository 目錄規則、開 branch、處理 commit，最後再到 Argo CD 找結果，CRD 只是另一套更進階的操作文件。

Portal 後端要補上這段落差，但不該拿著 cluster credential 直接建立 `Microservice`。那會繞過 Day 06–17 建立的 Git review、交付追溯性與權限分工。API 的責任是把已驗證的服務意圖轉成 Git 變更請求，讓 GitOps 接手後續部署。

## 先定義 API 的信任邊界

當使用者在 Portal 按下「建立 `reminder-api`」，request 裡哪些資料可以信任？答案通常比直覺少：

| 資料 | 能否由瀏覽器自由提供 | 正確來源 |
| --- | --- | --- |
| `serviceName`、image digest、port、非敏感 env | 可以，但必須驗證 | 已驗證使用者的 request |
| team | 不應只相信 request body | Portal 身分與 team membership |
| Namespace、Git repository path、target branch | 不可以 | 後端的 server-side mapping |
| Kubernetes credential、Git long-lived token | 絕不可以 | 僅存在受限的 backend runtime |
| secret value | 不應經過這條 request | 專用 Secret management flow |

這個界線的目的不是讓 API 難用，而是防止一個看似正常的 JSON request 指向其他 team Namespace、覆蓋任意 Git 檔案，或把敏感資料寫進 commit。

## 使用者輸入要小，而且可驗證

第一版 API 不讓 caller 傳入 `namespace`、`path` 或 `branch`。team 從登入身分推導，environment 是 API 允許的列舉，image 必須是 registry 中已由 CI 建立的 immutable digest。

```json
// 規劃片段：POST /v1/microservices 的 request body
{
  "serviceName": "reminder-api",
  "environment": "dev",
  "image": "registry.example.internal/reminder-api@sha256:******",
  "port": 8080,
  "env": {
    "REMINDER_BATCH_SIZE": "50",
    "LOG_LEVEL": "Information"
  }
}
```

同一位使用者若因網路重送或連點兩次按鈕，後端也不能建立兩個不同 PR。request 應搭配由 client 產生、後端保存的 idempotency key：

```text
Idempotency-Key: 7d03a5da-<request-uuid>
```

這個 key 不是授權憑證。它只讓後端在同一使用者重送同一操作時，回傳原本的 delivery request，而不是再次寫入 Git；身分驗證仍由 Portal 的 session 或 access token 處理。

## Server-side mapping 才是平台的交付規則

以 Todo team 和 Dev 環境為例，API 在驗證身分後推導出下面這組不讓 caller 覆寫的值：

```yaml
# 規劃片段：IDP backend 的受控 team/environment mapping
teams:
  todo:
    environments:
      dev:
        namespace: todo-dev
        repository: todo-platform-config
        basePath: apps
      staging:
        namespace: todo-staging
        repository: todo-platform-config
        basePath: apps
```

因此，`reminder-api` 的服務請求才會被渲染到預期位置：

```text
team from identity:      todo
requested environment:   dev
derived namespace:       todo-dev
derived repository path: apps/reminder-api/overlays/dev/microservice.yaml
derived branch:          idp/todo/reminder-api/dev/<request-id>
```

這讓同一份 Portal API 可以服務多個 team，同時仍能限制每個 team 的可用環境。若未來要加入 Production approval、區域 cluster 或成本中心，也應先擴充這份受控 mapping，而不是在前端多加一個可任填的 `namespace` 欄位。

## 渲染 YAML 時，資料模型比字串拼接更重要

後端應先將 request 轉成強型別或結構化的 `Microservice` model，再用受控 serializer 渲染 YAML。不要用 string concatenation 把使用者輸入插進 YAML；換行、特殊字元、anchor 或不當縮排都可能讓一個正常表單變成意外的 manifest。

```yaml
# 規劃片段：由已驗證 model 產生的 GitOps 文件
apiVersion: platform.example.io/v1alpha1
kind: Microservice
metadata:
  name: reminder-api
  namespace: todo-dev
  labels:
    app.kubernetes.io/owner: todo-team
spec:
  image: registry.example.internal/reminder-api@sha256:******
  port: 8080
  env:
    REMINDER_BATCH_SIZE: "50"
    LOG_LEVEL: Information
```

render 前至少要驗證：

- `serviceName` 是否符合 Kubernetes DNS label 規則，且未與同 team 既有服務衝突。
- `port` 是否符合 Day 19 schema 範圍。
- `env` key/value 是否為允許的非敏感字串，且沒有保留平台管理的 `OTEL_*`、`KUBERNETES_*` 等名稱。
- image 是否使用核准 registry 與 `@sha256:` digest 格式，且能對應到 caller 有權使用的 CI artifact。
- 目標路徑是否由 mapping 唯一推導，而不是由輸入決定。

image digest 是否真的由 CI 發行，不能只靠正規表示式判斷；實作時還要和 registry metadata 或 CI provenance 進行可信的查詢。驗證失敗應回傳欄位級錯誤，而不是只說「Git API failed」。

## Git branch 是提交意圖的暫存區，不是直接寫入 main

Day 17 已經確立 production-like 設定不可由 automation 直接寫 protected branch。Day 22 的 API 因此只會：

```text
validate request
  -> create or reuse idempotent delivery request
  -> render one Microservice YAML document
  -> create a scoped config branch
  -> commit the expected file change
  -> return a delivery request in AwaitingReview state
```

後端對 Git provider 使用 scope 明確、可輪替的 installation token，例如僅能對 `todo-platform-config` 建 branch 與 Pull Request 的 GitHub App 身分。它不需要，也不應取得 Argo CD 或 Kubernetes 的 credential。Git provider 暫時不可用時，API 必須將 request 標記為可診斷的失敗，並讓同一 idempotency key 能安全重試；不要吞掉錯誤後回傳一個看似成功的 URL。

## 回應模型要讓 Portal 知道下一步

建立 branch 並不表示部署開始，因此 API 的回應使用非終態的 delivery status：

```json
{
  "deliveryId": "dpl_01J...",
  "serviceName": "reminder-api",
  "environment": "dev",
  "status": "AwaitingReview",
  "configBranch": "idp/todo/reminder-api/dev/dpl_01J...",
  "pullRequestUrl": null
}
```

Day 23 會為這個 branch 補上 YAML/schema validation、Pull Request 建立與 review 結果。此刻故意不假裝 `pullRequestUrl` 已存在，避免 Portal 把「request 被接受」誤顯示成「服務已部署」。

## 測試與驗證

API 與 Git integration 尚未實作。後續驗證會以輸入、權限與重送三種情境為主：

```text
預期演練：
1. Todo team 成員提交合法 reminder-api，確認只產生 todo-dev 的受控路徑與 branch。
2. 同一 idempotency key 重送，確認回傳同一 deliveryId，沒有第二個 commit 或 branch。
3. 嘗試在 request 傳入 namespace、path、secret 或未核准 registry，確認 API 拒絕且回傳欄位級錯誤。
4. 非 Todo team 成員嘗試建立 todo-dev 服務，確認沒有 Git 變更被建立。
5. Git API 暫時失敗時，確認 Portal 看見可重試的失敗狀態，而不是假的成功。
```

驗收的關鍵是：使用者只需表達服務意圖，但不可能藉此跨越 team、Git 或 Kubernetes 的信任邊界。

IDP API 能把受驗證的服務意圖寫進受控 branch，但還沒有人核准它進入 GitOps `main`。下一篇會把 branch、靜態檢查與 Pull Request 接成防呆流程，避免自動化只是更快地把錯誤送進叢集。
