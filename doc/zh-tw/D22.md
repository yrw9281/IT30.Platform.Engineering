# Day 22 - 用 Backstage 提出 GitOps 設定 Pull Request

## 表單有了，變更要送去哪裡？

`todo-api` 的 Software Template 已能描述「選一個 digest，產生 Dev 的 `Microservice` 設定」。但產生 YAML 不等於更新叢集。如果 Backstage 直接寫入 Kubernetes，Git review 就被跳過，也無法從 Git 追查是哪次設定變更讓服務換版。

這裡選擇讓模板提出 Git Pull Request。Git 裡存的是目標狀態；Argo CD 之後讀取合併的版本，再由 Operator 處理 `Microservice`。**目前只有模板來源與本地靜態檢查，沒有真正建立 PR 或串接部署。**

## 模板提出的變更

Software Template 先用 `fetch:template` 渲染固定的 Dev 設定，再交給 GitHub Scaffolder 的 `publish:github:pull-request` action：

```yaml
steps:
  - id: render
    name: Render the Microservice
    action: fetch:template
    input:
      url: ./skeleton
      values:
        digest: ${{ parameters.digest }}
  - id: propose
    name: Propose a config change
    action: publish:github:pull-request
    input:
      repoUrl: github.com?owner=yrw9281&repo=repo-config
      branchName: backstage/todo-api/dev/${{ parameters.digest }}
      targetBranchName: main
      sourcePath: .
      targetPath: apps/todo-api/overlays/dev
      title: Propose Todo API image for Dev
      description: Review the image digest and environment before merging.
```

這份模板固定 repository、目標 branch 和環境目錄；開發者不能透過表單改成 Production。`repo-config` **是規劃中的設定儲存庫，目前不存在**。這裡的 `targetPath` 只是預定的存放位置；現有 Argo CD `Application` 讀取的仍是原生 Kubernetes manifest，不會因為模板多了一個路徑就開始同步 `Microservice`。

第一次建立 Dev 目錄時，預期 diff 至少包含 `microservice.yaml` 與 `kustomization.yaml`；後續更換 image 才應只變更 `Microservice.spec.image` 的 digest。reviewer 應比對來源 CI 的 digest、目標環境與實際 diff，而不是只看 PR 標題。目前 PR description 是固定說明，**沒有**自動附上 CI run、提出者或驗證結果，不能當成已完成的稽核紀錄。

## 有 PR 還不夠，設定儲存庫得自己檢查

Backstage 表單的 regex 只擋 digest 格式；有人也可以不經表單直接向 Git 提 PR。因此 `repo-config` 建立後，受保護的 `main` 至少需要：

1. 解析 YAML、檢查變更的路徑與檔案形狀，避免藉 PR 改到別的服務或環境。
2. 依實際 CRD 驗證 `Microservice` 的 group、version、schema 與必填欄位；需要叢集端驗證時，使用已安裝相同 CRD 的隔離環境，不能拿 Production 當試驗場。
3. 檢查 image digest 是否來自受信任的 Todo API CI 輸出，並對照核准的目標環境；格式符合 `sha256` 不等於 image 可信。
4. 設定必須通過的 checks、目標分支保護與人工 review；誰能執行 Backstage action、誰能合併設定，也要在 Git 權限中分開。

這些都是要在設定儲存庫**另外實作**的規則，不是 GitHub PR action 或 Backstage Catalog `owner` 自帶的功能。`kustomization.yaml` 只是讓未來能組裝 Dev 目錄；它本身既不會檢查 CRD，也不會建立 Argo CD `Application`。

## 怎麼確認這個範例目前做到哪裡？

本地結構檢查能解析 Catalog／Template YAML、檢查 digest 的欄位限制，並以測試 digest 渲染 `Microservice`、核對現有 CRD 可接受的 spec 欄位。這個結果只能證明**範例結構與替換結果**；沒有執行 Backstage 的 `publish:github:pull-request`，也沒有驗證 GHCR digest 真實性。

等設定儲存庫、GitHub Scaffolder module、憑證、branch protection 和設定檢查都備齊，才能以一筆真實 PR 驗收：PR 只改 Todo API Dev，未通過檢查時無法合併，合併後由指向該設定來源的 Argo CD Application 觀察到 revision。在這之前，不該把模板 YAML 的存在寫成「自助部署已上線」。
