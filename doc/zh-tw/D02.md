# Day 02 - Kubernetes 為什麼能維持期望狀態：宣告式 API 與 Reconcile Loop

## 前一日主題回顧

昨天我們把上一系列的 Todo 微服務放回「團隊如何交付」的問題裡。現在先想像一個很小、但很常見的事件：`todo-api` 的其中一個 container 因為記憶體不足停止了。若是在 Docker Compose 的世界，我們可能登入主機、看 log、手動重啟；若有一百個服務、每個服務又有多個副本，這個反應方式很快就撐不住。

Kubernetes 的關鍵不是它能啟動 container，而是它改變了我們描述系統的方式：我們不再下達「幫我啟動第三個 Pod」的命令，而是宣告「我希望一直有三個健康副本」。之後，系統會持續想辦法讓現況靠近這個目標。

## 問題與設計：命令式操作為何會失控？

命令式操作很適合一次性的工作。例如你可以明確告訴某台主機執行 restart，並立刻看見結果。但命令本身沒有保存「重啟後應維持什麼狀態」：Pod 再次消失、節點失效、有人手動縮放副本時，下一步仍然要靠人想起來。

Kubernetes 採用**宣告式 API（Declarative API）**。使用者、CI 或未來的 GitOps controller 送出的不是操作步驟，而是一份資源目標。以規劃中的 `todo-api` 為例，下面的 `replicas: 3` 不是要求 API Server 此刻建立三個 Pod，而是告訴叢集：這個服務要持續維持三個副本。

目前 `src/` 尚無對應 manifest，以下 YAML 是用來說明概念的片段，不能直接當成可套用檔案。要實作時，先在 `src/` 建立對應檔案，並依目標叢集、GHCR repository、Namespace 與版本確認內容。

```yaml
# 規劃片段：todo-api 的期望狀態
apiVersion: apps/v1
kind: Deployment
metadata:
  name: todo-api
  namespace: todo-dev
spec:
  replicas: 3
  selector:
    matchLabels:
      app.kubernetes.io/name: todo-api
  template:
    metadata:
      labels:
        app.kubernetes.io/name: todo-api
    spec:
      containers:
        - name: todo-api
          image: ghcr.io/yrw9281/todo-api:0.1.0
```

這份 YAML 只是設計片段，尚未存在於 `src/`，也尚未套用至叢集。不過它已經足夠讓我們提出一個重要問題：如果實際只剩兩個健康 Pod，誰看見這個落差，又由誰補上第三個？

## Kubernetes 真正做的事：持續收斂，而非執行一次

答案是**控制迴路（Reconcile Loop）**。不同 controller 各自負責一種資源關係，重複觀察目標與現況之間的差異，採取最小必要動作，再回頭觀察結果。

```text
使用者提交 Deployment
        │
        ▼
API Server 儲存 desired state
        │
        ▼
Deployment controller 建立或更新 ReplicaSet
        │
        ▼
ReplicaSet controller 讓 Pod 數量靠近 replicas
        │
        ▼
Scheduler 為尚未排程的 Pod 選擇節點
        │
        ▼
目標節點的 kubelet 啟動 container，狀態回報 API Server
        └───────────────────────┐
                                ▼
                    controller 再次比較期望與實際
```

這個流程有兩個容易忽略的特性。

第一，控制器不是「跑完就結束」的部署腳本。Pod 被刪掉、Node 失效、Image 無法拉取、Deployment 的 `spec` 被改變時，新的事件會讓 controller 再次 reconcile。第二，控制器並不保證你的應用程式邏輯正確；它只會忠實地讓資源狀態靠近你宣告的目標。因此，錯誤的 image、錯誤的 readiness probe，或會破壞資料的 migration，一樣會被高效率地重複執行。

## `spec` 與 `status`：不要把希望和觀察混在一起

Kubernetes 資源通常將輸入與輸出分開：

- `spec` 是使用者希望系統達到的狀態，例如副本數、image、port。
- `status` 是 controller 觀察到的結果，例如有幾個副本可用、目前 revision 或失敗原因。

```yaml
# 規劃中的狀態觀察範例，不由開發者手動填寫
status:
  replicas: 3
  readyReplicas: 2
  availableReplicas: 2
  conditions:
    - type: Available
      status: "False"
      reason: MinimumReplicasUnavailable
```

這個區分會一路跟著我們走到 Day 24。未來 `Microservice` CRD 的 `spec` 是開發者提出的服務意圖，而 Operator 會根據底層 Deployment 的真實情況更新 `status`；Portal 顯示的「健康」不應該由表單送出者自己宣稱。

## 為何不是直接建立 Pod？

直接建立 `Pod` 當然可以啟動 container，但它不描述副本數、更新策略與持續維護關係。`Deployment` 將這些意圖交給 Deployment controller，再由 `ReplicaSet` 管理指定數量的 Pod。這個分層看起來多了一點資源，卻讓 rollout、rollback、水平擴展與自我修復都有一致的操作模型。

也因此，閱讀 Kubernetes YAML 時，不要只看「有沒有一個 `kind`」。更值得問的是：這個資源想維持什麼關係？哪一個 controller 會消費它？失敗時 status 要怎麼告訴我們差在哪裡？

## 測試與驗證

目前仍是設計階段。以下是建立對應 `src/` manifest 並備妥叢集後的驗證計畫，不代表這些檔案或可操作叢集已經存在：

```bash
# 先由 API Server 驗證 manifest 是否符合叢集 schema
kubectl apply --server-side --dry-run=server -f todo-api-deployment.yaml

# 部署後觀察 Deployment 的目標與可用副本是否一致
kubectl get deployment todo-api -n todo-dev -w

# 刪除其中一個 Pod，觀察 ReplicaSet 是否建立替代副本
kubectl delete pod <todo-api-pod-name> -n todo-dev
```

驗證重點不是背指令，而是能預測現象：刪除 Pod 不應永久讓 `Deployment` 停在兩個副本；它會短暫出現落差，再由 controller 補足。如果 image 拉取失敗，副本數可能存在但 `availableReplicas` 不會增加，這正是 `status` 比「資源是否建立成功」更有價值的地方。

## 結語

Kubernetes 的靈魂是讓期望狀態不斷向實際狀態收斂，而不是替我們跑一串指令。知道誰在維持這個關係後，下一篇就來拆解一個 Todo API 真正上線時，`Deployment`、`Service` 與 `Ingress` 要如何接成完整流量骨架。
