# Day 04 - Helm and Kustomize: managing configuration across environments

Yesterday, we split `todo-api` into a Deployment, Service, and Ingress. One set of YAML is usually enough for a single environment, but running a service in production usually means handling different settings for Dev, Staging, and Prod. Dev might need only one replica, Staging a test domain, and Prod three replicas. If we copy the entire directory three times, it's easy to miss an environment the next time we change a shared setting such as a probe. Copying and pasting creates more than maintenance work. As the configurations for the same service drift apart, failures may look different too. During code review, it also becomes hard to tell whether a difference reflects an environment's needs or a change someone forgot to carry over.

## Problem and design: what should stay the same, and what can differ?

Before choosing tools, we'll divide the Todo microservice's configuration into three categories:

- The service's fixed structure: container ports, label contracts, probe paths, and Service selectors.
- Environment differences: Namespace, hostname, replica count, resource sizes, and image digest.
- Reusable packaged capabilities: components such as Argo CD, Prometheus, and the OpenTelemetry Collector that multiple teams install.

The two most common choices for managing these configurations are the tools in the title, `Helm` and `Kustomize`. Both reduce duplication, but they manage configuration differently.

- Helm generates manifests from templates and values, making it suitable for publishing configurable packages.
- Kustomize layers overlays on a base of native YAML, making environment differences easy to see directly during review.

## Kustomize: putting the Todo API's shared structure in a base

For the Todo API, Kustomize divides deployment YAML into a shared base and overlays for each environment:

```text
apps/
  todo-api/
    base/
      deployment.yaml
      service.yaml
      kustomization.yaml
    overlays/
      dev/kustomization.yaml
      staging/kustomization.yaml
      prod/kustomization.yaml
```

The base's `kustomization.yaml` lists only the resources shared by the service, without any environment-specific settings:

```yaml
apiVersion: kustomize.config.k8s.io/v1beta1
kind: Kustomization
resources:
  - deployment.yaml
  - service.yaml
```

The Prod overlay describes only the differences from the base, which makes it easier to review than another complete copy of the Deployment.

```yaml
apiVersion: kustomize.config.k8s.io/v1beta1
kind: Kustomization
resources:
  - ../../base
namespace: todo-prod
replicas:
  - name: todo-api
    count: 3
```

Kustomize still produces complete Kubernetes YAML. As overlays multiply and patches override one another, though, the results can become hard to predict. At that point, we should revisit the boundaries of the base or split functionality into clearly defined components instead of adding more logic to the overlays.

## Helm: packaging installable capabilities as a parameterized Chart

Helm is a package manager for Kubernetes. The Chart author decides the template structure, while users adjust the settings the Chart exposes through values. I don't plan to go into creating a Helm Chart specifically for `todo-api` in this series. The values and template below only illustrate how a Chart turns configuration into Kubernetes manifests; they are not a project example you can run directly.

```yaml
replicaCount: 3

image:
  repository: ghcr.io/yrw9281/todo-api
  tag: "0.1.0"

ingress:
  enabled: true
  className: nginx
  host: todo.example.internal

resources:
  requests:
    cpu: 250m
    memory: 256Mi
```

The template reads `Values` to generate a Deployment. Only the essential image and replica lines are shown here.

```yaml
spec:
  replicas: {{ .Values.replicaCount }}
  template:
    spec:
      containers:
        - name: todo-api
          image: "{{ .Values.image.repository }}:{{ .Values.image.tag }}"
```

Helm is suitable for packaging installation settings shared by multiple teams, such as those for Argo CD or an observability stack. If a template is full of nested `if` statements, defaults, and exceptions, users will struggle to tell from the values what it will actually generate. A Chart should therefore provide a clear values schema and documentation, without turning every Kubernetes field into a parameter.

## Why does this series use Kustomize?

In this series, applications maintained by the Todo team use Kustomize to manage environment overlays. For third-party components installed by the platform, we prefer official or maintained Helm Charts. There are two reasons:

1. Service teams need to understand their applications' environment differences directly during Git review.
2. Platform components often have extensive configuration options. Writing all that YAML ourselves would mean losing the maintenance benefits of the upstream Chart.

Both tools can be part of the same delivery workflow. Whichever we choose, Git should hold configuration that can be reviewed, and we should be able to reproduce the rendered output.

## Testing and validation

We can use the following command to render manifests before committing, without applying them:

```bash
# View the complete manifest Kustomize assembles for Prod
kubectl kustomize apps/todo-api/overlays/prod
```

Validation needs to go beyond checking that YAML was produced. Check that Prod uses the `todo-prod` Namespace, the image is the expected version, the replica count is three, and the base's readiness probe and Service selector are still present. If we adopt third-party Helm Charts later, we should run `helm template` according to the Chart's documentation and the actual values file, then inspect the rendered output.

Also, if changing one value means copying a large chunk of a Deployment into every environment, the current configuration layers still need adjustment.

## Conclusion

Kustomize keeps shared application settings and environment differences in YAML that we can review directly. Helm lets us reuse third-party components' installation methods and the work that goes into maintaining them. Choosing a tool doesn't remove Kubernetes' complexity. Service teams still need to understand the relationships between `Deployment`, `Service`, and `Ingress` to judge whether the rendered configuration meets their expectations.

As the number of services keeps growing, expecting every developer to handle these underlying details becomes a problem that the configuration layers above cannot solve on their own. The next article introduces CRDs, starting by adding a resource called `Microservice` to Kubernetes. Developers will only need to specify the image and port their service uses, with the platform handling the required resources afterward.
