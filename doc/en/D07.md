# Day 07 - Sync YAML from Git to Kubernetes with Argo CD

The previous article established Git as the source of the environment's desired state, but a repository cannot read commits or call the Kubernetes API on its own. We still need a controller running in the cluster that knows which Git repository to read, syncs differences to the cluster, and reports whether the resources are actually ready.

Argo CD handles this work. It adds a GitOps control loop around Kubernetes controllers such as `Deployment`, without replacing them: it reads manifests from Git, compares them with the current cluster state, and performs `reconcile` according to the sync policy.

## How does Argo CD sync Git and Kubernetes?

When you first encounter Argo CD, it is easy to see it as `kubectl apply` with a Web UI. The main difference is that `kubectl apply` is a one-time command, while Argo CD continuously tracks the Git revision and cluster state.

An `Application` is Argo CD's deployment contract. It specifies the Git source, manifest path, target cluster, and namespace so the controller knows where a set of resources should come from and where to deploy them.

```text
Git commit
    │
    ▼
Repo Server fetches and renders Kustomize, Helm, or YAML
    │
    ▼
Application Controller compares the desired state from Repo Server with the current K8s cluster state
    │
    ├── OutOfSync: differences exist; wait for or perform synchronization
    └── Synced: managed resources have been applied at the specified revision
             │
             ▼
       Health assessment: are the resources ready?
```

Argo CD's API Server and Web UI let people or automation tools create and query an `Application`. The Repo Server reads and renders Git content, while the Application Controller compares and syncs resources. Repository credentials should grant read-only access, and both `AppProject` and Kubernetes RBAC must restrict which namespaces and resources Argo CD can operate on.

## Install Argo CD and create a deployment contract

Today's example puts the existing Todo Kubernetes manifests under Argo CD's management. The `AppProject` restricts which repositories it can read and where it can deploy. The `Application` specifies the Git path to the Todo manifests and syncs the resources to the `todo` namespace.

First, install Argo CD using the official Helm chart:

```bash
helm repo add argo https://argoproj.github.io/argo-helm
helm repo update
helm upgrade --install argocd argo/argo-cd \
  --namespace argocd \
  --create-namespace
```

Once installation is complete, save the `AppProject` and `Application` mentioned above as `project.yaml` and `todo.yaml`, respectively, and apply them:

```bash
kubectl apply -f project.yaml -f todo.yaml
```

The `AppProject` first defines the allowed scope. Here, `sourceRepos` allows only this repository, and `destinations` allows only the `todo` namespace in the cluster. The `clusterResourceWhitelist` also permits the `Namespace` resource in the Todo manifests; other cluster-scoped resources are outside this project's permissions.

```yaml
apiVersion: argoproj.io/v1alpha1
kind: AppProject
metadata:
  name: todo
  namespace: argocd
spec:
  sourceRepos:
    - https://github.com/yrw9281/IT30.Platform.Engineering.git
  destinations:
    - namespace: todo
      server: https://kubernetes.default.svc
  clusterResourceWhitelist:
    - group: ""
      kind: Namespace
  namespaceResourceWhitelist:
    - group: "*"
      kind: "*"
```

The `Application` then binds a Git path within this scope to a deployment target:

```yaml
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: todo
  namespace: argocd
  finalizers:
    - resources-finalizer.argocd.argoproj.io
spec:
  project: todo
  source:
    repoURL: https://github.com/yrw9281/IT30.Platform.Engineering.git
    targetRevision: main
    path: src/1-kubernetes/kind
  destination:
    server: https://kubernetes.default.svc
    namespace: todo
  syncPolicy:
    automated:
      prune: true
      selfHeal: true
```

Both `source` and `destination` define deployment boundaries. The `source` specifies which repository, revision, and path Argo CD trusts; the `destination` limits which cluster and namespace the resources can be synced to. The `finalizers` ensure that when an `Application` is deleted, Argo CD first deletes the resources it manages. You must decide whether to retain managed resources before creating the Application.

## `Synced` does not mean the service is usable

Argo CD's sync status and health status answer different questions:

- `Synced`: The resource declarations for the specified Git revision have been successfully applied, with no differences from the current managed resources.
- `Healthy`: Argo CD's health assessment determines that the resources have reached a usable state.

For example, a `Deployment` may have been created even if its image cannot be pulled. The Application can therefore be `Synced` while its Pods cannot become ready, leaving the overall health at `Progressing` or changing it to `Degraded`. When you see `Synced`, you still need to check the health status.

A normal sync progresses through these changes:

```text
Git revision changes
  -> Application detects the new revision
  -> OutOfSync
  -> Resources have been applied
  -> Synced + Progressing
  -> Pod ready
  -> Synced + Healthy
```

## Confirm resource boundaries before enabling automatic sync

The `automated.prune` setting deletes managed resources that have been removed from Git, while `selfHeal` reverts manual changes to match the Git declarations. They prevent drift from persisting in the cluster, but they also increase the impact of incorrect changes.

For example, if you rename a Deployment or move resources to another Application's folder with automatic pruning enabled, Argo CD treats this as "old resources removed, new resources created." This can inadvertently delete and restart a live service. Argo CD does not know the intent behind your architectural changes, so before enabling automatic sync, you must plan which Application should manage each resource and which resources can be deleted.

## Testing and verification

After applying the Application, use the Argo CD CLI to confirm the source it reads, its deployment destination, and its current status:

```bash
# Before using the argocd CLI, get the initial password with argocd admin initial-password, set up port-forwarding, and sign in with argocd login.
argocd app get todo --refresh
argocd app wait todo --sync --health --timeout 300
kubectl get application todo -n argocd
```

During verification, distinguish at least three cases: Git has a new revision that has not yet been synced, resources have been applied but the Pods are not yet healthy, and all managed resources are healthy. If `argocd app wait` times out, first check the Application's events, then follow up on the corresponding Deployment or Pod:

```bash
kubectl describe application todo -n argocd
kubectl get deployment,pod -n todo
```
