# Day 14 - Create a CI workflow with GitHub Actions

## Introduction to CI/CD

Platform engineering provides Kubernetes, GitOps, and observability tools, but it also needs to make the steps after a code change clear to the team: who checks that the code compiles, whether tests have passed, which commit a container image was built from, and who decides when it enters an environment? These questions define the work of continuous integration and continuous delivery (CI/CD).

CI repeats restore, test, and build on every change so it can catch unmergeable source code early. CD deploys approved container images to the specified environments according to each environment's rules. The two do not have to use the same tool or job, but the handoff needs to be clear: CI records check results that can be traced back to their source, and CD decides which version to deploy.

This article starts by setting up CI checks for the Todo services with GitHub Actions. GitOps reconciles the cluster with approved environment configuration in Git; it does not determine whether source code compiles or run tests. Every pull request (PR) that changes a service therefore needs CI to produce repeatable check results.

## CI validates source code without deploying it directly

CI and CD often share a pipeline, but they address different questions and need different permissions:

| Stage | Questions to answer | Permissions it should not have |
| --- | --- | --- |
| CI | Can this source code pass restore, test, and build? Which commit produced the artifacts? | Write access to production Kubernetes |
| GitOps CD | Should the approved configuration be reconciled to the target environment? Are the resources healthy? | Permission to modify application source code arbitrarily |

Establish this boundary first. CI can build container images and open PRs to update GitOps configuration, but it does not need a kubeconfig to run `kubectl apply` against production. Leaving cluster write access to a GitOps controller with restricted permissions inside the cluster keeps responsibility for source validation and environment deployment separate and traceable.

## Start with the checks the Todo services can run today

The current Todo example has two .NET 8 projects: `Todo.Api` provides the to-do API, and `Todo.Bff` forwards API requests from the browser. Each project has its own `.csproj` and Dockerfile. There is no solution file, and no unit test project has been created yet.

PR checks should not pretend to cover tests that do not exist. The workflow still runs `dotnet test` at this stage so that each project goes through the same test entry point, but without a test project, this step does not validate any unit tests. Once tests are added, CI can surface test failures in the PR instead of leaving problems to be discovered in an image or the cluster.

```text
pull request
  │
  ├── restore: fetch NuGet dependencies for the specified project
  ├── test: run the project's test entry point
  ├── build: compile with the Release configuration
  └── feedback: report failures on the PR
```

## Run the same checks with a project matrix

The workflow puts `Todo.Api` and `Todo.Bff` in a matrix. Both jobs use the same .NET SDK and restore, test, and build steps. If one fails, the other continues, so the PR can show results for both projects in one run.

```yaml
name: todo-ci

on:
  pull_request:
    paths:
      - "src/0-todo-microservices/**"
      - ".github/workflows/todo-ci.yaml"

permissions:
  contents: read

jobs:
  validate:
    runs-on: ubuntu-latest
    strategy:
      fail-fast: false
      matrix:
        project:
          - src/0-todo-microservices/Todo.Api/Todo.Api.csproj
          - src/0-todo-microservices/Todo.Bff/Todo.Bff.csproj
    steps:
      - name: Check out source
        uses: actions/checkout@v4

      - name: Set up .NET
        uses: actions/setup-dotnet@v4
        with:
          dotnet-version: 8.0.x

      - name: Restore NuGet packages
        run: dotnet restore ${{ matrix.project }}

      - name: Run tests
        run: dotnet test ${{ matrix.project }} --configuration Release --no-restore

      - name: Build release artifacts
        run: dotnet build ${{ matrix.project }} --configuration Release --no-restore
```

`permissions` grants only `contents: read`, so the workflow can read the repository but cannot push images, write GitOps configuration, or operate Kubernetes. Any future job that publishes images should have its minimum required permissions configured separately. Do not add `packages: write` or Kubernetes credentials simply because the PR workflow needed to read the source code.

`fail-fast: false` preserves check results for both projects; it does not ignore failures. If any matrix job fails, the entire workflow still fails. The PR does not get a green light to merge as a result.

The repository currently has no `packages.lock.json`, so this workflow does not enable the NuGet cache in `actions/setup-dotnet`. A lock file needs to be adopted before it can be used as the cache key to avoid inconsistent results from different dependency resolutions for the same commit. Enabling a cache alone does not guarantee reproducible dependency versions.

## A green check has limited scope

CI success means only that the specified checks have passed. It does not mean that all risks have been ruled out:

- There is currently no unit test project, so a successful `dotnet test` does not mean functionality has been tested.
- A successful build does not mean the container image has no known vulnerabilities or unsafe configuration.
- CI does not validate whether migrations are compatible with older versions of the services.
- CI does not prove that external dependencies in staging or production match those in the local environment.

CI catches source-level problems that can be detected immediately. Observability data after deployment supports investigation, while resource policies enforce resource rules. Both remain necessary even when CI is green.

## Reproduce PR checks locally

The GitHub Actions runner executes the following commands. You can run the same commands from the repository root before submitting a PR:

```bash
dotnet restore src/0-todo-microservices/Todo.Api/Todo.Api.csproj
dotnet test src/0-todo-microservices/Todo.Api/Todo.Api.csproj --configuration Release --no-restore
dotnet build src/0-todo-microservices/Todo.Api/Todo.Api.csproj --configuration Release --no-restore

dotnet restore src/0-todo-microservices/Todo.Bff/Todo.Bff.csproj
dotnet test src/0-todo-microservices/Todo.Bff/Todo.Bff.csproj --configuration Release --no-restore
dotnet build src/0-todo-microservices/Todo.Bff/Todo.Bff.csproj --configuration Release --no-restore
```

To verify the workflow, deliberately make one project fail to compile. Confirm that the corresponding matrix job shows a compiler error and that the overall workflow fails. After creating a unit test project, deliberately make a test fail as well. Check that the job stops at the test step instead of treating unvalidated code as a deliverable artifact.
