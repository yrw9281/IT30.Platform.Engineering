# Day 21 - Let the Operator manage the Todo API Deployment and Service

In the previous article, `accept` recorded the `image` and `port` it received and wrote back `Accepted`, but the Todo API deployment did not change with them. Today we add resource management so the Operator creates or updates a `Deployment` and `Service` according to the CR.

This time, the Operator will recreate the Todo API workload. We will first walk through how `reconcile` creates resources, checks ownership, and updates configuration. Then we will delete a test `Service` to check that it can restore a missing resource.

## Turn service inputs into a workload

The service team still supplies only `image` and `port`; the platform supplies the rest. `desired_resources(cr)` reads the CR and generates the `Deployment` and `Service` configuration. This function does not call the API Server directly. Other functions write the configuration to the cluster later:

| Source | Generated content |
| --- | --- |
| CR name and Namespace | A `Deployment` and `Service` with the same name and in the same Namespace |
| CR UID | `ownerReferences` pointing to the CR, and a UID label on managed Pods |
| `spec.image` | The container image, preserving its tag or digest as supplied |
| `spec.port` | The container's `http` port, the `Service` port, and `ASPNETCORE_URLS` |
| Platform defaults | Two replicas, probes, requests/limits, and OpenTelemetry (OTel) configuration |

For example, if `spec.port` is `8080`, the Operator sets the container port and `Service` port to `8080` and uses `ASPNETCORE_URLS` to make the Todo API listen on the same port. These settings need to change together because changing the container port alone does not automatically change where ASP.NET Core listens.

These defaults are designed for the existing Todo API: the probes use `/health/ready` and `/health/live`, the OTel endpoint points to the existing Collector, and the application must already include the SDK or instrumentation. There is currently no support for supplying `env` or `Secret` references, so you cannot swap in an arbitrary image and expect it to work with the same configuration.

`OTEL_SERVICE_VERSION` uses the full image reference so we can compare telemetry with the deployment configuration. It does not parse out a separate release version. The CPU request of `25m` and memory request of `128Mi` retain the settings from the small test environment for now. Actual resource needs still have to be checked against the workload.

## How does one `reconcile` handle differences?

Suppose we change `spec.image` in the `todo-api` CR. The Operator first calculates the new resource configuration, then reads the `Deployment` and `Service` from the cluster. It writes the differences only after confirming that it can modify both resources. This is the part of `reconcile` that handles that work:

```python
desired_deployment, desired_service = desired_resources(cr)
deployment = read_child("Deployment", namespace, name)
service = read_child("Service", namespace, name)
# Check both names before modifying either resource.
for resource in (deployment, service):
    if resource is not None:
        check_owner(resource, cr)
ensure(desired_deployment, deployment, cr, logger)
ensure(desired_service, service, cr, logger)
write_phase(cr, logger, "ResourcesApplied", managed=True)
```

`desired_deployment` and `desired_service` are the target configurations generated from the CR. `deployment` and `service` are the current resources read from the cluster, or `None` if a resource does not exist. What happens next depends on two things: whether the resource belongs to this CR, and whether its current configuration matches the target.

| Current resource state | Action |
| --- | --- |
| Does not exist | Create the target resource |
| Belongs to this CR and the configuration matches | Do not write |
| Belongs to this CR and the configuration differs | Update the same object |
| Exists but does not belong to this CR | Report `OwnershipConflict`; do not overwrite |

### `read_child`: read the current `Deployment` or `Service`

Although both operations read resources, the Kubernetes Python client provides different methods for `Deployment` and `Service`. With `read_child`, the caller only needs to supply the Kind, Namespace, and name to get the dictionary needed for subsequent comparisons:

```python
def read_child(kind: str, namespace: str, name: str) -> Json | None:
    read = apps.read_namespaced_deployment if kind == "Deployment" else core.read_namespaced_service
    try:
        return api.sanitize_for_serialization(read(name, namespace, _request_timeout=TIMEOUT))
    except ApiException as error:
        if error.status == 404:
            return None
        raise
```

This handles only `Deployment` and `Service`. `apps`, `core`, and `api` are API clients created when the Operator starts; `Json` is a type alias for `dict[str, Any]`. The Python client returns a resource object. `sanitize_for_serialization` converts it to a dictionary so later code can read fields through `resource["metadata"]` and `resource["spec"]`. `TIMEOUT` is set to `(5, 20)`, limiting the connection and read wait times respectively, in seconds.

If the API returns `404`, the function returns `None` so `ensure` knows it needs to create the resource. The final `raise` propagates other `ApiException` errors, and connection errors are not swallowed here either. Insufficient permissions and a missing resource require different handling. A failed read is not a reason to try creating a new resource.

### `check_owner`: a matching name does not grant permission to modify

After reading `todo-api`, we still need to confirm that it is managed by this CR. `check_owner` checks `ownerReferences` for a controller reference pointing to the current CR:

```python
def check_owner(current: Json, cr: Json) -> None:
    owners = current["metadata"].get("ownerReferences", [])
    if not any(owner.get("uid") == cr["metadata"]["uid"]
               and owner.get("apiVersion") == API_VERSION
               and owner.get("kind") == "Microservice"
               and owner.get("controller") is True for owner in owners):
        raise OwnershipConflict(
            f'{current["kind"]}/{current["metadata"]["name"]} is not owned by this CR')
```

`API_VERSION` is `platform.example.io/v1alpha1`. This code checks the CR's UID, API version, Kind, and `controller: true` together; checking the name alone is not enough. Even if a CR is deleted and recreated with the same name, its UID will differ, so it cannot directly modify resources owned by the old CR. If no reference meets the conditions, the function raises `OwnershipConflict`, and the handler records the reason and reports failure.

The earlier `for` loop checks both existing resources before writing, so it does not modify the `Deployment` only to discover that the `Service` belongs to someone else. This is just a preliminary check. The two API writes are still separate operations; it does not make them succeed or roll back together.

### `ensure`: create missing resources and update only when settings differ

The periodic check runs every ten seconds, but we do not want to write the same configuration every time. If `todo-api` already matches the CR, this run should skip the write. API calls are needed only when a resource is missing or its configuration differs. `ensure` receives the target configuration `desired`, the current resource `current`, and `cr`, which supplies the name, Namespace, and basis for ownership checks:

```python
def ensure(desired: Json, current: Json | None, cr: Json, logger: logging.Logger) -> None:
    kind = desired["kind"]
    namespace, name = cr["metadata"]["namespace"], cr["metadata"]["name"]
    if current is None:
        create = (apps.create_namespaced_deployment if kind == "Deployment"
                  else core.create_namespaced_service)
        create(namespace, desired, _request_timeout=TIMEOUT)
        logger.info("Created %s/%s", kind, name)
        return
    check_owner(current, cr)
    if contains(current, desired):
        return
    replacement = deepcopy(current)
    replacement["metadata"]["labels"] = {
        **current["metadata"].get("labels", {}), **desired["metadata"]["labels"]}
    if kind == "Deployment":
        replacement["spec"] = desired["spec"]
        replace = apps.replace_namespaced_deployment
    else:
        replacement["spec"].update(desired["spec"])
        replace = core.replace_namespaced_service
    replacement.pop("status", None)
    replace(name, namespace, replacement, _request_timeout=TIMEOUT)
    logger.info("Updated %s/%s", kind, name)
```

When `current is None`, the function selects the appropriate create method, submits the target configuration, logs `Created`, and returns. If the resource already exists, it calls `check_owner` again so that `ensure` itself checks ownership rather than relying solely on the caller.

Next, `contains(current, desired)` compares the content listed in the target configuration. Extra fields in a dictionary do not count as differences; lists are checked for length and content at each position. Default fields that the API Server adds to a dictionary therefore do not necessarily need to be overwritten. Differences in the image, port, or a platform-specified label do trigger an update. If the configuration matches, the function immediately executes `return`. Processing the same CR repeatedly does not create extra resources or send an update every time.

For an update, `deepcopy` first copies the current resource. The function then merges the metadata labels, preserving other labels while setting platform-specified values to match the target. For a `Deployment`, it replaces the entire `spec` with the target configuration rather than preserving externally added settings field by field. For a `Service`, it uses `update` to change the fields listed in the target configuration, preserving fields such as `ClusterIP` that the API Server has already allocated. This `update` is not a recursive merge; `ports`, for example, is still replaced in full.

`replacement.pop("status", None)` removes the copied status because we are submitting resource configuration, not declaring our own observations of the workload. The final `replace` updates the same object rather than deleting and recreating it. The copy also retains the `resourceVersion` from the read. If someone modifies the resource after that read, the API Server rejects this stale write, and the Operator must read it again and retry.

### Report results or errors after submitting configuration

Only after both `ensure` calls finish does `write_phase` write `ResourcesApplied` and record the names of the managed resources. This means only that the configuration has been submitted. The code has not yet checked whether the image can be pulled or the Pods are ready. Before writing status back, it also reads the CR again and checks its UID, generation, and deletion state to avoid writing the result of an old request onto a new one.

If the input violates the rules, `desired_resources` raises `InvalidSpec`. If a resource does not belong to the CR, `check_owner` raises `OwnershipConflict`. The following excerpt shows how the handler handles these two errors after catching them. `error` is the caught exception:

```python
logger.error("%s: %s", type(error).__name__, error)
write_phase(cr, logger, "Failed", managed=False)
raise kopf.PermanentError(str(error)) from error
```

It first logs the error type and reason, then sets the CR to `Failed` and clears the names previously recorded in `status.managedResources`. This does not delete the workload. `PermanentError` tells Kopf not to keep retrying the same operation for this handler failure. It does not stop the entire Operator; a later `spec` update or periodic check may trigger processing again.

For insufficient API permissions, version conflicts, or connection failures, the outer error handler logs the error and uses `TemporaryError` to request a retry later. It reads the resources again before deciding what to do. This version does not fix permissions for the administrator. It leaves an explicit error record and must not treat a failure as `ResourcesApplied`.

As in the previous article, the handler runs when a CR is created, when its `spec` changes, and when the Operator reads an existing CR after restarting. This time, the handler runs `reconcile`. There is also a check every ten seconds: even if the CR has not changed, the check can handle a managed `Deployment` or `Service` that has been deleted or had its configuration changed. API latency and retries affect the timing, so recovery within ten seconds is not guaranteed.

## Confirm configuration was submitted, then watch resources being restored

Before enabling the resource-management version for the first time, make sure there is no `todo-api` Deployment or Service with the same name in the `todo` Namespace, so the Operator can recreate them from the existing CR. If Argo CD or another controller manages the resources, remove them from its management first as well, so they are not recreated after deletion.

The operations below use a test environment where an AI-built Operator creates the resources. The code excerpts above only explain the processing flow; they cannot run on their own as a complete Operator.

```bash
kubectl get microservice todo-api -n todo -o yaml
kubectl get deployment,service -n todo -l app=todo-api
kubectl rollout status deployment/todo-api -n todo --timeout=180s
```

The CR should report `ResourcesApplied`, and both `deployment` and `service` in `managedResources` should record the name `todo-api`. This means the Operator has submitted the configuration for both resources. You still need to check the rollout separately to see whether the Pods are ready. If the CR reports `Failed`, check the Operator log for `InvalidSpec` or `OwnershipConflict`. Do not treat that run as a completed deployment.

We use temporary test resources to check whether the periodic check (timer) can restore a `Service`, without deleting the original Todo `Service`. First, confirm that no CR, `Deployment`, or `Service` is named `operator-repair-check`. Then copy the Day 18 `Microservice` configuration, `todo-api.yaml`, to `operator-repair-check.yaml`. Change only `metadata.name`, keeping Todo's image and port. This temporarily adds a test workload, so reserve enough capacity:

```bash
kubectl apply -f operator-repair-check.yaml
kubectl wait microservice/operator-repair-check -n todo \
  --for=jsonpath='{.status.phase}'=ResourcesApplied --timeout=60s
```

In the screenshot below, the test CR has reported `ResourcesApplied`, and the `Deployment` and `Service` with the same name have been created. The log shows that `reconcile` successfully handled the create event. However, the Deployment's `READY` was still `0/2` at the time: the configuration had been submitted, but the Pods were not ready yet.

![operator-repair-check reports ResourcesApplied and the Deployment and Service have been created, but the Deployment's READY is still 0/2](../assets/day-21-operator-resources-applied.png)

After confirming that the configuration has been submitted, record the test `Service`'s UID and delete it:

```bash
kubectl get service operator-repair-check -n todo -o jsonpath='{.metadata.uid}{"\n"}'
kubectl delete service operator-repair-check -n todo
kubectl get service -n todo -l app=operator-repair-check --watch
```

The Operator's timer should restore a `Service` with the same name. Once it reappears, press `Ctrl+C` to stop the watch, then run the earlier UID query again and compare the UIDs before and after deletion. The new object's UID should differ, and its `ClusterIP` is not guaranteed to stay the same either. This test only checks that the resource can be restored; it does not require the test Pods to complete their rollout.

The screenshot below shows a `Service` with the same name appearing again after deletion, but with a different UID. This means the Operator created a new resource; the original object was not still in the cluster.

![After the operator-repair-check Service is deleted, the Operator restores a resource with the same name and a different UID](../assets/day-21-service-repair-uid.png)

After the test, keep the Operator running and delete the test CR:

```bash
kubectl delete microservice operator-repair-check -n todo --wait=true
kubectl get deployment,service -n todo -l app=operator-repair-check
```

Garbage collection may not finish immediately after deleting the CR. Wait until both the `Deployment` and `Service` disappear. Kopf's timer uses a finalizer to prevent the CR from being deleted before the related processing finishes. If you stop the Operator first, it may be unable to finish handling the finalizer, leaving CR deletion stuck. Do not clear the finalizer directly to skip this step.

Once we confirm that the `Service` with the same name has been restored, we can see that the Operator handles resource differences even when the CR has not changed. However, `ResourcesApplied` does not yet answer, "Is this update usable?"
