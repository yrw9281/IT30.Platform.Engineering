# Day 22 - Have the Operator report whether the new version is ready

The Operator from the previous post can create and update `Deployment` and `Service` resources, and recreate deleted resources. However, `ResourcesApplied` only means the configuration has been submitted. After the Todo API's image changes, new Pods might fail to pull it while old Pods continue to respond to requests. Those responses do not mean the update succeeded.

Today we add health checks to the existing `reconcile` to check the updated replicas and `Service` endpoints, then write the results back to the CR. Resource creation and ownership checks stay as they are, and service teams still only provide `image` and `port`.

## Which states tell us the new version is ready?

`health(deployment, slices, pods, image)` takes the current `Deployment`, `EndpointSlice` resources, managed Pods, and target image, and returns `ready`, `stalled`, `reason`, and `message`. It only evaluates the data passed to it and does not call the API Server directly. The following two snippets run in order within this function.

First, check that the Deployment controller has observed the current configuration. Then check whether Pods using the target image have startup errors or whether the rollout has gone too long without progress:

```python
status = deployment.get("status", {})
if status.get("observedGeneration", 0) < deployment["metadata"]["generation"]:
    return False, False, "Reconciling", "Deployment controller has not observed this version"
for pod in pods:
    for container in pod.get("spec", {}).get("containers", []):
        if container["image"] != image:
            continue
        for observed in pod.get("status", {}).get("containerStatuses", []):
            if observed["name"] != container["name"]:
                continue
            waiting = observed.get("state", {}).get("waiting", {})
            if waiting.get("reason") in {
                "ErrImagePull", "ImagePullBackOff", "InvalidImageName",
                "CrashLoopBackOff", "CreateContainerConfigError",
            }:
                return False, True, waiting["reason"], "Inspect managed Pod events and logs"
if any(condition.get("type") == "Progressing"
       and condition.get("status") == "False"
       and condition.get("reason") == "ProgressDeadlineExceeded"
       for condition in status.get("conditions", [])):
    return False, True, "ProgressDeadlineExceeded", "Deployment rollout exceeded its deadline"
```

For example, if a new Pod reports `ImagePullBackOff`, the function returns `ready=False` and `stalled=True`, along with the error reason. Old Pods remaining available cannot cancel out an error in the new version. `ProgressDeadlineExceeded` uses the Deployment's own assessment of progress. The platform's `progressDeadlineSeconds: 120` setting is not a fixed deployment time limit measured from CR submission, nor does it trigger an automatic rollback.

If there is no explicit blocker, check the updated replicas and endpoints:

```python
replicas = deployment["spec"]["replicas"]
complete = all(status.get(key, 0) == replicas for key in
               ("replicas", "updatedReplicas", "readyReplicas", "availableReplicas"))
pod_uids = {pod["metadata"]["uid"] for pod in pods
            if any(container["image"] == image
                   for container in pod.get("spec", {}).get("containers", []))}
endpoints = any(endpoint.get("conditions", {}).get("ready") is True
                and endpoint.get("addresses")
                and endpoint.get("targetRef", {}).get("uid") in pod_uids
                for item in slices for endpoint in (item.get("endpoints") or []))
if complete and endpoints:
    return True, False, "RolloutComplete", "All updated replicas and Service endpoints are ready"
return False, False, "RolloutPending", "Waiting for updated replicas and ready Service endpoints"
```

The Todo API's target is two replicas, so `replicas`, `updatedReplicas`, `readyReplicas`, and `availableReplicas` must all be `2`. This checks both that replicas are available and that they have been updated to the current Pod template. Old replicas still serving requests do not count as a successful rollout of the new version.

The `EndpointSlice` resources must also contain at least one endpoint with an address and `ready: true`, whose `targetRef.uid` matches a managed Pod using the target image. Readiness is reported only when both the replica and endpoint checks pass; otherwise, the Operator keeps waiting. This check does not call the business API or guarantee data consistency or a working external Ingress.

## Write observations back to the CR

The results from `health` go to `make_status`, which produces two conditions, `Ready` and `Stalled`, along with a `phase` that summarizes the processing stage:

| Observation | `Ready` | `Stalled` | `phase` |
| --- | --- | --- | --- |
| Update incomplete, with no explicit error | `False` | `False` | `Progressing` |
| Updated replicas ready, with an endpoint that meets the criteria | `True` | `False` | `Ready` |
| Image or startup error, or rollout progress deadline exceeded | `False` | `True` | `Failed` |

Below, `Json` is a type alias for `dict[str, Any]`, and `datetime` and `timezone` come from the Python standard library. `make_status` includes this assessment and the CR generation in the report:

```python
def make_status(cr: Json, ready: bool, stalled: bool, reason: str,
                message: str, managed: bool) -> Json:
    generation = cr["metadata"]["generation"]
    previous = {item["type"]: item for item in cr.get("status", {}).get("conditions", [])}
    conditions = []
    for kind, value in (("Ready", ready), ("Stalled", stalled)):
        state = "True" if value else "False"
        old = previous.get(kind, {})
        transition = old.get("lastTransitionTime") if old.get("status") == state else None
        conditions.append({
            "type": kind, "status": state, "observedGeneration": generation,
            "reason": reason, "message": message,
            "lastTransitionTime": transition or datetime.now(timezone.utc).isoformat(
                timespec="seconds").replace("+00:00", "Z"),
        })
    name = cr["metadata"]["name"]
    return {
        "phase": "Ready" if ready else "Failed" if stalled else "Progressing",
        "observedGeneration": generation, "conditions": conditions,
        "managedResources": {"deployment": name, "service": name} if managed else {},
    }
```

`Ready=False` does not necessarily mean failure. Read it together with `Stalled` and `reason` to distinguish waiting from a problem that needs investigation. `Stalled=True` does not mean the Operator has stopped processing either; it will observe again after the image is corrected. When a condition's `status` has not changed, the code preserves the original `lastTransitionTime` instead of refreshing it on every check.

The results must correspond to the current configuration. The CR's `metadata.generation`, its `status.observedGeneration`, and each condition's `observedGeneration` must match. Otherwise, `Ready=True` may be left over from a previous version. The Deployment's generation is observed by its own controller, and its number cannot be compared with the CR's generation.

The CRD's `status` schema must also allow `conditions` and their fields for the API Server to retain the report. Before writing, `report` checks the CR's UID, generation, and deletion state again, skips stale results, and protects the write with `resourceVersion`. These conditions record the current state, not an event history of every update.

## Where do health observations fit?

After both `ensure` calls finish, the Operator reads the `Deployment` again, queries managed Pods by the CR UID label, and retrieves the same-named `Service`'s `EndpointSlice` resources. The Operator needs the corresponding read permissions. API errors are still logged and retried through the existing error handling. Once it has the data, `reconcile` calls the health check and reports the results:

```python
ready, stalled, reason, message = health(deployment, slices, pods, cr["spec"]["image"])
report(cr, logger, ready=ready, stalled=stalled, reason=reason,
       message=message, managed=True)
```

A single `reconcile` does not wait until the rollout finishes. It reports what it observes at that moment. A CR event, resume, or the timer that runs every ten seconds then triggers another pass. The relationship between resource submission, health checks, and status writes is shown below:
