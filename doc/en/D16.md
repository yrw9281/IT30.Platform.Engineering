# Day 16 - Handing image updates to GitOps after CI finishes

## CI builds the image; GitOps handles deployment

The release workflow from Day 15 is triggered by a `todo-api-v*` or `todo-bff-v*` tag. It validates the corresponding service, pushes the image to GHCR, and outputs its digest. This tells us which source commit the image was built from, but does not yet decide whether to deploy it to Staging or Production.

If CI deploys directly, it needs write access to the cluster. A workflow error could then change the environment, and the team would lose a chance to check whether this version should enter this environment.

So CI produces the image digest, and the deployment process proposes a GitOps configuration change. Only after the team reviews and merges it does Argo CD sync the change to the cluster. CI does not need to hold a kubeconfig or run `kubectl apply`. The current release workflow only outputs the digest; it does not yet create a configuration Pull Request.

## Handing off from CI to GitOps through a config Pull Request

Below, `repo-app` represents the application source code, and `repo-config` represents environment configuration. This is a planned division of responsibilities, not two repositories that already exist. CI hands a digest to CD rather than deploying directly to the cluster:

```text
repo-app (CI: produce images)
  source commit
    -> Create and push a todo-api-v* or todo-bff-v* release tag
    -> The tag triggers the release workflow: validate, build, and push to GHCR
    -> Image digest (handed to the deployment process; no direct deployment)

repo-config (GitOps CD: choose the version to deploy)
  Use the digest produced by CI to update the target environment configuration on a temporary branch
    -> Pull Request -> review -> merge into the protected branch
    -> Argo CD reads the merged revision and synchronizes resources
    -> Kubernetes controllers reconcile
```

This flow leaves evidence at each handoff:

- Application CI records the mapping between the source commit and the image digest.
- The config Pull Request records which environment will use which digest, and who approved it.
- Argo CD records which config revision was synced; Kubernetes then reports the state actually observed for the resources.

This also preserves the GitOps trust boundary. CI can create a config Pull Request, but only Argo CD's restricted identity can reconcile the approved configuration to the cluster.

## Change only the target environment's image digest when updating a deployment version

Suppose we want Staging to use a new image for `todo-api`. The configuration change should update only that environment's digest, without also changing `Service`, `Ingress`, or other environments. This lets the Pull Request reviewer see clearly which version is changing and which environment is affected. Kustomize overlays can separate environments, but they are not required for the CI-to-GitOps handoff.

The current Argo CD `Application` reads native Kubernetes resource configurations and does not sync `Microservice` resources. The `Deployment` that uses a GHCR image also still specifies a tag such as `ghcr.io/yrw9281/it30-todo-api:0.1.0`. The project does not yet have a separate environment configuration repository, environment overlays, or a workflow that automatically updates digests. This discussion describes how configuration changes should be reviewed; CI, Argo CD, and the `Microservice` CRD have not yet been connected.

Deploying the same image to Production should require a separate configuration change that affects only Production. Using this image in Staging does not mean it has been approved for Production. Having both environments use the same digest should still be an explicitly recorded decision.

## Separate permissions along the data flow

The following is a permissions design for the handoff process. It does not mean that every identity and configuration repository already exists. Least privilege involves more than a `permissions` line in a workflow; we also need to distinguish who can read or change what:

| Identity | Should be able to | Should not be able to |
| --- | --- | --- |
| PR CI | Read source, run tests | Push images, write to the config repository, write to the cluster |
| Release CI | Read the selected source revision, push the specified image, create a config Pull Request | Merge directly into a protected branch, write to Kubernetes |
| Config reviewer | Approve or reject environment changes | Modify image bytes, obtain GHCR push credentials |
| Argo CD | Read approved config, perform `reconcile` in the specified Namespace | Modify application source, write to arbitrary clusters |

The identity that creates config Pull Requests should use a GitHub App installation token with a clearly defined scope and support for rotation, or an equivalent short-lived credential. Do not put a long-lived Personal Access Token (PAT) in a workflow secret. The protected branch must also enforce the required checks and reviews. CI's ability to create Pull Requests automatically does not give it permission to merge changes into Production on its own.

## Trace deployments back to their source

When a deployment has a problem, the team should be able to trace it from the cluster back to the delivery source:

```text
Argo CD Application revision
  -> config repository merge commit
  -> image digest in environment configuration
  -> CI run that emitted the digest
  -> source commit and Pull Request
```

In the other direction, this chain can also tell us whether a given source commit has reached Production. Relying only on manually copied tags, or bypassing Git with unrecorded `kubectl` operations, breaks traceability in both directions. Emergency fixes must also be written back to Git once complete; otherwise, Argo CD self-heal or an environment rebuild may overwrite the fix.

## Config Pull Requests need their own checks

A passing source CI run does not guarantee that the environment configuration is correct. At a minimum, a configuration Pull Request should check that the YAML parses, that the image reference belongs to an approved `ghcr.io/yrw9281/` repository and uses digest format, and that the Kubernetes schema is valid without accessing Production. If Kustomize is used, also check that the rendered resources match expectations.

These checks address different layers of problems. A successful Kustomize render does not mean the Kubernetes API will accept the resources. Passing schema validation does not mean the controller has completed `reconcile`, much less that the workload is healthy. Config checks should not receive broadly permissive Production cluster credentials just to make validation convenient.
