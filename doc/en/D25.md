# Day 25 - Let Argo CD determine whether a `Microservice` is healthy

In the previous post, we could submit a pull request (PR) from Backstage to update the Todo API version, but Argo CD was not yet configured to read those deployment settings. Even once we connect it and can sync the merged settings to the cluster, that does not mean the Operator has finished the update: the new `spec.image` may already be written to the `Microservice` while the new Pod is still starting, or cannot even pull the image. Where can we check the outcome of this version update?

This brings us back to the distinction between `Synced` and `Healthy` in Day 07. `Synced` means the declarations in Git match the managed configuration in the cluster. `Healthy` depends on whether the resources meet their readiness conditions. At the time, Argo CD was syncing native resources such as `Deployment`, so it could use its built-in health checks. But `Microservice` is our custom resource, and Argo CD does not know when to consider it ready.

The Operator from Day 22 already observes the new version's rollout, Pods, and `Service` endpoints, then writes the results back to the custom resource (CR)'s `status`. Today, we can use a custom health check to turn that report into an Argo CD health status without building another set of workload checks. We will write the health check and explain how to add it to the Argo CD configuration.

## Have Argo CD read the Operator's assessment

After Argo CD syncs `Microservice.spec`, the Operator creates or updates the `Deployment` and `Service` as needed, then observes the workload. These two stages do not finish at the same time. Even when the CR exists and its configuration is correct, we still need to read the `status` written by the Operator to know how the update is progressing. The custom resource definition (CRD) currently supports the following status fields, and the Kopf Operator reports them:

| Field or condition | Purpose |
| --- | --- |
| `metadata.generation` | The current configuration version of the CR, not the image's release version |
| `status.observedGeneration` | The CR version to which the Operator's observations apply |
| `Ready=True` | The replicas for that version have finished updating and are ready, with a `Service` endpoint that meets the requirements |
| `Stalled=True` | That version has a problem requiring investigation, such as an image or startup error, or a rollout that has exceeded its progress deadline |

For example, when updating the Todo API version, changing `spec.image` increments the CR's `metadata.generation`. Before the Operator processes it, however, `status` may still contain `Ready=True` from the previous version. To avoid mistaking the previous version's readiness for a successful update, the health check must first compare `status.observedGeneration` with `metadata.generation`. Only when they match should it read the conditions to determine the new version's status.

Once the versions match, we also need to distinguish an update in progress from an error. While the new Pod is not yet ready, the Operator reports `Ready=False` and `Stalled=False`. The health check should show `Progressing` so we know we are still waiting for a result. If the Operator reports `Stalled=True`, it should show `Degraded` and retain the reason for the error. It should show `Healthy` only when the new version meets the readiness conditions and no blocking issue has been reported.

This assessment also depends on the Operator reporting the version correctly. The `make_status` function from Day 22 sets `status.observedGeneration` and the `observedGeneration` of both conditions to the same CR version, then checks the version again before writing. The Lua below relies on this contract: it compares only the outer generation, without checking each condition's version. If another writer advances only the version number while leaving an old `Ready=True` in place, the check could still incorrectly report a healthy status.

## Use Lua to turn `status` into Argo CD health

`argocd-cm` is the ConfigMap Argo CD uses to store its configuration, in the `argocd` namespace. The YAML below adds an entry to its `data`: the key specifies the resource type to assess, and the value is the complete Lua program. Once this setting is written to `argocd-cm` in the cluster, Argo CD will use this Lua code when assessing the health of a `Microservice`.

The configuration key has the format `resource.customizations.health.<group>_<kind>`. The API group for `Microservice` is `platform.example.io`, and its Kind is `Microservice`, so the key here is `resource.customizations.health.platform.example.io_Microservice`.

This is shared Argo CD configuration. It applies to all resources with the matching group and Kind in the same Argo CD installation, not just the Todo API. Preserve the ConfigMap's other settings when adding it. If Helm manages the configuration, also put the change in the Helm configuration source so an upgrade does not overwrite it.

When Argo CD runs the script, it passes this CR through `obj`. The program reads `obj.metadata` and `obj.status`, puts the assessment in `hs.status` and the explanation in `hs.message`, then returns `hs`. Only the `data` block to add to the ConfigMap is shown below:

```yaml
data:
  resource.customizations.health.platform.example.io_Microservice: |
    hs = {}

    if obj.status == nil or
       obj.status.observedGeneration ~= obj.metadata.generation then
      hs.status = "Progressing"
      hs.message = "Waiting for the operator to observe this generation"
      return hs
    end

    for _, condition in ipairs(obj.status.conditions or {}) do
      if condition.type == "Stalled" and condition.status == "True" then
        hs.status = "Degraded"
        hs.message = condition.message or condition.reason or "Reconciliation stalled"
        return hs
      end
    end

    for _, condition in ipairs(obj.status.conditions or {}) do
      if condition.type == "Ready" and condition.status == "True" then
        hs.status = "Healthy"
        hs.message = condition.message or "Managed resources are ready"
        return hs
      end
    end

    hs.status = "Progressing"
    hs.message = "Waiting for managed resources to become ready"
    return hs
```

The opening `if` handles a missing `status` or a version mismatch by returning `Progressing` immediately, without using the old conditions. After the version check passes, the two `for` loops look for `Stalled=True` and `Ready=True`, respectively, and return a result when they find a match. We deliberately check `Stalled` first: even if the report contains both `Stalled=True` and `Ready=True`, the result is `Degraded`, so a readiness signal cannot hide an error. The returned `message` comes from the condition's explanation, letting us see the reason in the health status.

If neither `Stalled=True` nor `Ready=True` is present, the program reaches the final `Progressing` result. This means `Ready=False`, `Ready=Unknown`, and missing conditions are never treated as healthy. However, `Progressing` only means there is no readiness result yet; it does not guarantee that the Operator is running normally. If the status never updates, we need to check the Operator's logs instead of continuing to wait for the screen to turn green.

## What states should we see during a version update?

Suppose we are updating the Todo API's image. When the new `spec.image` is written to the CR, the Operator's report may still refer to the previous version. The health check should show `Progressing` at this point. Even if the old version has `Ready=True`, that cannot count as the new version being ready. Only after the Operator reports results for this configuration version can we tell whether the update is still in progress, is ready, or has encountered an error requiring investigation.

Mapping these cases to the Lua logic gives the following results:

| CR observations | Expected health | Why |
| --- | --- | --- |
| No `status`, or `status.observedGeneration` differs from `metadata.generation` | `Progressing` | There are no observations for the current configuration version yet, so the old `Ready=True` cannot be used |
| The current configuration version has `Ready=True` and no `Stalled=True` | `Healthy` | The Operator has confirmed that the managed resources are ready |
| The current configuration version has `Stalled=True` | `Degraded` | The Operator has reported a problem requiring investigation |
| The current configuration version has both `Ready=True` and `Stalled=True` | `Degraded` | The error signal takes precedence |
| The current configuration version has neither `Ready=True` nor `Stalled=True` | `Progressing` | There is no readiness result yet, and no explicit error report |

For Argo CD to use this logic, remember to add the setting to `argocd-cm` in the cluster and have the `Application` sync the Todo API's `Microservice`. Writing the YAML alone will not change Argo CD's health assessment.

## What do `Synced` and `Healthy` each guarantee?

| Status | What it confirms | What it does not mean |
| --- | --- | --- |
| `Synced` | The declarations in Git match the managed configuration in the cluster | The new version has started or the service is available |
| The CR's `Healthy` | The Operator reports that the new version's replicas and endpoints meet the readiness conditions | The entire `Application` is healthy; business operations work correctly |
| The `Application`'s `Healthy` | Resources included in the health assessment meet their respective health conditions | Actual operations, such as creating a Todo, are guaranteed to succeed |

If the image cannot be pulled, the configuration may still be `Synced` while the CR is `Degraded`. The health check only presents status and does not automatically roll back. We still need to change the configuration to fix the problem.
