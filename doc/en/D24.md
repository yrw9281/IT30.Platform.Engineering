# Day 24 - Propose GitOps configuration changes through a Backstage pull request

In the previous post, we had a Software Template collect a digest, then use `fetch:template` to generate the Todo API's `Microservice` YAML. But the files are still in the Backstage task's working directory. They have not entered Git or updated the cluster. How do we hand off this configuration?

Day 16 explained that once an image is built, we should hand it over to GitOps through a configuration pull request (PR) instead of deploying it directly. Today, we will add a PR action after the rendering step from the previous post. It writes the files to a proposal branch so reviewers can see which version we want to use and which environment will change. The changes are merged into `main` only after approval.

## Add a PR step after rendering

The form and the `render` generation logic stay the same as in the previous post. Each task still starts by generating `microservice.yaml` and `kustomization.yaml`. This time, we just replace the preview step, `inspect`, with `propose` to send the output to GitHub using `publish:github:pull-request`.

The following excerpt shows the Template's `spec.steps` and `spec.output`. The form still collects only the digest, while the Git destination is fixed in the template. Configuration can share a repository with the code. Here, we send the Todo API's Dev configuration to a separate directory in the same repository:

```yaml
steps:
  - id: render
    name: Render Todo API Dev configuration
    action: fetch:template
    input:
      url: ./skeleton
      values:
        digest: ${{ parameters.digest }}
  - id: propose
    name: Create configuration Pull Request
    action: publish:github:pull-request
    input:
      repoUrl: github.com?owner=yrw9281&repo=IT30.Platform.Engineering
      branchName: backstage/todo-api/dev/${{ parameters.digest }}
      targetBranchName: main
      sourcePath: .
      targetPath: src/5-config/apps/todo-api/overlays/dev
      title: Propose Todo API image for Dev
      description: Review the image digest and environment before merging.
output:
  links:
    - title: Review the config change
      url: ${{ steps.propose.output.remoteUrl }}
```

`propose` takes the two files generated by `render` from the current task's working directory (`sourcePath: .`) and commits them to `targetPath` in the target repository. The user does not have to download and commit them manually.

The files are written to the branch specified by `branchName`, and a PR is opened against `targetBranchName: main`. This does not modify `main` directly. Here, the branch name includes the digest to help identify which version change it proposes.

After creating the PR, the action returns `remoteUrl`. `output.links` uses `steps.propose.output.remoteUrl` to put the link in the task results, so developers can open the PR directly from Backstage.

To run this action, the Backstage backend needs the GitHub Scaffolder module installed and permission to create PRs in the target repository. This example uses a GitHub Personal Access Token (PAT). The backend uses the token; users do not need to enter it in the service form.

## View the PR changes from the task results

On the `Create` page, select `Todo API Dev Config Pull Request (D24)`. The form still asks only for an `Image digest`. Enter the 64-character digest produced by Todo API CI, then click `Review` to confirm the input and create the task:

![The Backstage Todo API Dev Config Pull Request D24 form, which only requires an Image digest before proceeding to Review](../assets/day-24-backstage-digest-form.png)

This task runs `Render Todo API Dev configuration` followed by `Create configuration Pull Request`. Once both steps succeed, the results show a `Review the config change` link that opens the PR we just created:

![Both the rendering and PR creation steps in Backstage have completed, and the task results provide a Review the config change link](../assets/day-24-backstage-pr-result.png)

Following the link shows `Propose Todo API image for Dev` with an `Open` status and `main` as the target branch. The proposal branch name includes the digest from the form. The PR has one commit and changes to two files, and has not been merged yet:

![The Todo API Dev configuration PR on GitHub, proposing two file changes against main from a branch whose name includes the digest, with an Open status](../assets/day-24-github-pull-request.png)

Switch to `Files changed` to see the configuration diff proposed by the template. Since this is the first time we are creating the Dev configuration, the PR adds `microservice.yaml` and `kustomization.yaml`. The former specifies `todo-api`, the `todo` Namespace, port `8080`, and an image that includes the digest. The latter tells Kustomize to include this `Microservice` in its output:

![GitHub Files changed shows the newly added kustomization.yaml and Microservice YAML, with the digest from the form included in the image](../assets/day-24-github-config-diff.png)

Once these two files exist, a PR that only changes the version should change only the digest in `spec.image`. There is no reason to change the service name, Namespace, or port, and the PR should not also change other services or environments. The template fixes the destination, but review still needs to confirm that the actual diff matches this request.

If the PR step fails, check the log for `Create configuration Pull Request`. A task that has only completed rendering does not count as having submitted a PR.

If you need to trace the image's origin, you can also attach a link to the Todo API CI run that produced this digest. The template's PR description currently contains only fixed explanatory text and does not yet include this information automatically.

## Require configuration checks and review before merging

A PR lets us see the changes, but it does not automatically guarantee that the content is correct. The form from the previous post can only check the digest's format. Someone might also open a PR directly without going through Backstage, so we still need independent configuration checks on the Git side:

1. Can the YAML be parsed, and are the changes limited to the allowed scope for Todo API Dev?
2. Does the `Microservice` match the current CRD's API group, version, and schema, including required fields, types, and ranges?
3. Does the image come from an approved Todo API repository, and can the digest be matched to trusted CI output?

These checks confirm whether the configuration follows the rules. Human review decides whether to deliver this version to Dev. Backstage only proposes the PR. It does not merge it on its own or bypass the merge requirements.

This demonstration has not yet run automated configuration checks, and the PR has no review record either. The `Ready to merge` message on screen therefore does not mean that configuration checks have passed or that a reviewer has approved the changes.

Once the merge requirements are configured, failed checks or review requests for changes are handled in the PR. The changes enter `main` only after passing those requirements. The diagram below shows this handoff:

![Backstage renders configuration and creates a PR; config checks and review gate merging to main, with Argo CD reading the merged revision after the GitOps source is connected](../assets/day-24-gitops-pr-flow.png)

## Hand off to Argo CD after merging

To deploy the merged configuration to the cluster, the Argo CD `Application` must also read the same repository, branch, and configuration directory. That source is not connected yet, so neither creating nor merging a PR will automatically update the Todo API's version.

Once it is connected, the responsibilities remain the same: Argo CD syncs the `Microservice`, and the Operator manages its `Deployment` and `Service`. Their respective controllers handle the deployment work that follows.

Today, we added a PR step for the YAML generated by the template, giving version change requests a diff that can be reviewed. But syncing the configuration to the cluster does not mean the new version is ready to use. In the next post, we will have Argo CD read the status reported by the Operator to determine whether the `Microservice` is healthy.
