# Day 17 - From Backstage to Kubernetes: the IDP control flow

## Introduction

Day 16 separated CI from deployment: the Todo API's release workflow produces an image digest, and the deployment process proposes a version change through a GitOps configuration pull request (PR). Only after review and merging does Argo CD synchronize it. The workflow does not yet create configuration PRs automatically, but the information the two sides need to hand off is now clear.

Suppose the Todo team wants to deploy a new version of `todo-api` to Dev. Developers still have to find the environment configuration, change the right fields, ask someone with permission to review it, and check the results in Argo CD and Kubernetes. Tools can handle each of these tasks, but developers still have to remember how the tools fit together. This article uses Backstage as the entry point to lay out the control flow from submitting a request to checking its status. The complete path is still a design and has not yet been connected.

Dev here uses the existing `todo` Namespace. The templates, Operator, and Catalog discussed below all point to it. Dev describes the environment's purpose. It does not require an environment suffix in the Namespace name, nor does connecting the entry point require a separate set of Todo workloads.

## What should developers decide through an IDP?

Returning to the question from Day 01, service teams want to specify which service should use which image, which port it should serve on, and which environment it should be deployed to. The platform should provide consistent rules for `Deployment` labels, `Service` selectors, health checks, and OpenTelemetry configuration. Teams should not have to decide these again for every version update.

An Internal Developer Platform (IDP) is a set of capabilities that lets teams deliver, inspect, and maintain services under these rules. It includes the entry point developers use, along with the configuration checks, review, synchronization, and status reporting behind it. This series uses Backstage for the service catalog and forms, Git to store reviewed deployment configuration, and Argo CD and an Operator to handle their respective resources in the cluster.

Installing Backstage gives you an entry point. You still need to connect each part: where the form sends its input, who can approve changes, which controller handles them, and where the status shown on screen comes from.

## What do Backstage's service catalog and forms do?

Backstage's Software Catalog organizes service names, owners, and related information. Developers can find `todo-api` in the catalog and see which team maintains it. A `Component` here is a service record stored by Backstage, a different kind of resource from a Kubernetes `Microservice`. Registering a service in the Catalog does not create a workload in the cluster.

![Backstage Software Catalog lists three Components, todo-api, todo-bff, and web, each with an owner and lifecycle](../assets/day-17-backstage-catalog-components.png)

The Catalog can also use Catalog Graph to draw relationships between resources. For example, the diagram below shows the `todo` Group connected to its three Components through `ownerOf` / `ownedBy` relationships. These graphs help developers quickly find the services a team owns, but they still show only metadata registered in the Catalog, not the live state of resources in the cluster.

![Backstage Catalog Graph shows the ownerOf/ownedBy relationships between the todo Group and the three Components todo-api, todo-bff, and web](../assets/day-17-backstage-catalog-graph.png)

Software Templates collect input and run the steps defined in a template. For an update to the Dev version of `todo-api`, the service and environment are already fixed, so the form only needs to collect the digest produced by CI. The template writes the input into the `Microservice` configuration and opens a Git PR so reviewers can see which version the change will use.

This requires installing and configuring Backstage's GitHub Scaffolder module so the template can run an action that opens a PR. This is a different execution mechanism from the GitHub Actions workflow that builds the image. Git credentials should stay in a restricted backend. The browser should not receive a token or be allowed to choose arbitrary Git paths, target branches, or Kubernetes Namespaces. These values should come from platform-controlled configuration and a verified team identity.

Fixing the form fields only narrows the range of possible input. The backend still needs to check whether the submitter is authorized to update the Todo team's services. A correctly formatted digest does not prove that authorized CI produced it. The configuration repository still needs independent checks, review, and protected branches; it cannot rely solely on the form's validation.

## How does a version update pass through Git, Argo CD, and the Operator?

For the request to update the Dev version of `todo-api`, the planned delivery flow has four stages:

1. A developer submits a digest in Backstage. The Software Template generates a configuration change and opens a PR. This submits a deployment request; it has not changed the cluster yet.
2. Configuration checks and a reviewer verify the image source, target environment, and scope of the change. Once approved, the change is merged into a protected branch. The merged configuration is the version Dev should use.
3. An Argo CD `Application` reads this configuration and synchronizes the `Microservice` custom resource (CR) to the target Namespace according to its synchronization policy. The API Server validates it against the custom resource definition (CRD) schema and stores it.
4. The Operator reads `Microservice.spec`, creates or updates the `Deployment` and `Service` according to platform rules, and writes its observations back to `status`. Native Kubernetes controllers still handle version updates and Pod replica maintenance under the `Deployment`.

This follows the division of responsibilities from Day 05: the CRD defines what data Kubernetes accepts, while the Operator determines what to do once that data arrives. For a `Microservice`, Argo CD does not generate a `Deployment`, and the Operator does not decide who can approve Git changes. Both run control loops, but each `reconcile` compares the configuration and resources that its own controller is responsible for.

This configuration change path carries the developer's request into Kubernetes. Backstage's status queries read observations from Kubernetes so developers can see how far processing has progressed. A query does not submit another deployment; these are separate flows.

The diagram below shows the planned control flow. Solid lines mark the path for handing off configuration and resources, while dashed lines mark the status query path. Kubernetes in the diagram represents the processing that involves the `Microservice` CR, the Operator, and the `Deployment`/`Service`/Pods it creates.

Backstage's Catalog and Kubernetes plugin can already query the existing Todo workloads, and there is an example Template that collects a digest and generates configuration. However, the Git configuration repository, the Argo CD `Application` that reads it, and the Operator have not yet been connected. The complete delivery path is still unfinished.

## Where should you check the result after submitting the form?

After you click "Create" in Backstage, completion of the template task only means that its specified steps have finished. If the last step is opening a PR, a successful task means the PR was created. It cannot be shown directly as "deployment successful." Each handoff has its own observations:

| What to check | Results to look at |
| --- | --- |
| Has the version change been proposed and approved? | The Git PR's configuration diff, check results, reviews, and merge history |
| Has the approved configuration been synchronized to the cluster? | The Argo CD `Application` revision and `Synced` status |
| Has the Operator processed this service configuration? | The processing progress and managed resources reported by `Microservice.status` |
| Is the workload ready? | The `Deployment` rollout progress, available replica count, and Pod `Ready` status |

For example, Argo CD may have synchronized the new image configuration, but if a Pod cannot pull the image, the service update still cannot finish. `Synced` and `Ready` answer different questions. Even when Pods are ready, you still need actual requests and Metrics, Logs, and Traces in Grafana to verify the application's behavior.

To view workloads in Backstage, you need to install the Kubernetes frontend and backend plugins, configure an identity that can read the cluster, and associate the Catalog service with the target resources. This lets developers query the current state of resources from the service entry point, but it does not automatically preserve a complete event timeline from PR review through every health change. Querying current state and preserving delivery history require different data.

## Which parts are still unconnected?

The existing release workflow can push images and output digests, and the Argo CD `Application` has an explicit source configuration. However, it reads native Kubernetes resources and does not synchronize `Microservice` resources. The CRD defines `image`, `port`, and an initial `status`. Without an Operator, the API Server's acceptance of a CR does not create a workload, and no controller writes observations back.

Backstage is deployed, and the Catalog and Kubernetes plugin can query the existing resources in the `todo` Namespace: `todo-api`, `todo-bff`, and `web`. The Software Template also targets `todo`, but the permissions to open Git PRs and the delivery integration are not finished. These are not yet part of a single connected delivery path. The separate configuration repository, the Argo CD `Application` that reads it, and the Operator have not been created either.

To validate this flow, you must be able to trace a `todo-api` PR to the revision synchronized by Argo CD, the `Microservice` in the cluster, and the workloads managed by the Operator. The resources queried through Backstage must also correspond to the same service and environment. A template that can generate configuration alone is not enough to confirm that all these handoffs work.
