# Day 20 - Handling `Microservice` events with Kopf and deploying the Operator

In the previous post, we chose Kopf to implement our Operator. Today, we'll start with event handling: when a `Microservice` is created or its configuration changes, how does Kopf call the function we wrote? We'll have this function log the `image` and `port` it receives and set the CR's `status.phase` to `Accepted` to confirm that the request has reached our code.

This step only confirms that the Operator can receive requests. It won't modify the Todo API's `Deployment` or `Service` to match them yet. Separating event handling from resource management lets us troubleshoot event handling first if the expected log or status is missing, without having to inspect the workload at the same time.

## Registering event handlers with Kopf decorators

We need to handle three situations: a CR being created, its `spec` being changed, and the Operator reading an existing CR after a restart. Kopf uses decorators to register handler functions for the corresponding triggers. Below, we register the same `accept` function for all three situations. Whichever one triggers it, the function logs the input and writes back `Accepted`:

```python
@kopf.on.create("platform.example.io", "v1alpha1", "microservices")
@kopf.on.update("platform.example.io", "v1alpha1", "microservices", field="spec")
@kopf.on.resume("platform.example.io", "v1alpha1", "microservices")
def accept(name, namespace, spec, logger, patch, **_):
    logger.info("Accepted %s/%s: image=%s port=%s", namespace, name,
                spec.get("image"), spec.get("port"))
    patch.status["phase"] = "Accepted"
```

When Kopf calls `accept`, it passes the CR's name, namespace, and desired configuration fields as `name`, `namespace`, and `spec`, respectively. The function logs these inputs with `logger` and uses `patch.status` to specify the status to write back. Kopf writes these status changes back to the API Server, so we don't need to send a status patch ourselves inside the function.

| Decorator | Trigger | Purpose |
| --- | --- | --- |
| `on.create` | A CR is created | Receive the initial request |
| `on.update`, restricted to `field="spec"` | `spec` changes | Handle new requests without being triggered again by writes to `status` |
| `on.resume` | The Operator finds an existing CR at startup | Resume processing after a restart without asking someone to change the configuration again |

If we register only `on.create`, this function won't run when an existing CR's `spec` is updated, and there will be no entry point to resume processing after the Operator restarts. That's why we also register `on.update` and `on.resume`, using `field="spec"` to restrict update handling to the desired configuration fields. Without that restriction, the handler's scope would no longer be limited to `spec`.

`Accepted` only means the handler has received the input. This code doesn't create Pods and doesn't know whether the image can be pulled, so we can't use it to determine whether deployment succeeded.

## How does the Operator run in the cluster?

With the handler written, we use a `Deployment` to run the Operator in the existing `todo` namespace. This example uses Kopf `1.38.0` and the Kubernetes Python client `34.1.0`, with the code mounted into the Pod through a `ConfigMap`. When the Pod starts, an init container installs the packages from PyPI. The main container then starts Kopf, which calls the registered handlers.

This section explains the deployment approach without listing the full installation configuration. Here's an excerpt showing the `Deployment` replica count and update strategy:

```yaml
spec:
  replicas: 1
  strategy:
    type: Recreate
```

When starting Kopf, `--namespace=todo` limits its watch scope to the `todo` namespace, while `--standalone` means it won't coordinate multiple replicas. We therefore keep a single replica and use `Recreate` to stop the old Pod before starting a new one during updates, preventing the old and new Operators from running at the same time. The trade-off is that watching stops during updates, so this is not a highly available deployment. Existing Todo Pods, however, won't stop just because the Operator is paused.

The Operator uses the Pod's `ServiceAccount` to access the API, so there's no need to put a kubeconfig in the Pod. Besides reading CRs and writing back `status`, it needs permission to modify annotations because Kopf stores processing progress and input snapshots in them. Keeping this internal data out of `status` prevents it from being pruned by the CRD's status schema.

Putting a `Role` in the `todo` namespace doesn't mean its permissions apply only to the CR named `todo-api`. The ownership checks in the next post are rules the code uses to decide whether it may modify a resource. They cannot replace RBAC authorization for the API.

Kopf's other settings also match the scope of this example: dynamic namespace and CRD scanning are disabled, as is Kubernetes Event emission. Errors are still recorded in the logs.

Recreating the Operator Pod requires a connection to PyPI every time. This approach suits a teaching environment; for production, build the code and dependencies into the image beforehand.

## Confirming event handling with logs and status

An Operator Pod starting and passing its health probe only proves that the Kopf process can respond. It doesn't prove that `accept` has processed a CR. We'll check the logs and `status.phase` next to confirm that the request reached the function.

The following commands require the `Microservice` CRD to be installed and the Operator that only logs inputs and writes back `Accepted` to be deployed. Before running them, confirm that you're connected to the test cluster, then inspect the relevant resources and logs:

```bash
kubectl config current-context
kubectl get namespace todo
kubectl get crd microservices.platform.example.io
kubectl logs deployment/microservice-operator -n todo -c operator
kubectl get microservice todo-api -n todo -o yaml
```

For example, the `todo-api` CR has `spec.image` set to `ghcr.io/yrw9281/it30-todo-api:0.1.0` and `spec.port` set to `8080`. After `accept` runs, we expect the following log:

```text
Accepted todo/todo-api: image=ghcr.io/yrw9281/it30-todo-api:0.1.0 port=8080
```

The CR's `status.phase` should also become `Accepted`. If the corresponding log or status is missing, first check whether the Operator started normally, whether it has sufficient API permissions, and whether the handler reported an error. Don't assume an event has been processed just because the Pod is `Running`.

Once written, though, `Accepted` may remain on the CR indefinitely. After changing `spec` or restarting the Operator, that status alone can't tell us whether the handler ran again. We need to check each of the three situations registered earlier and look at the logs for that particular operation:

| Situation | What to verify |
| --- | --- |
| Create a CR | The logs show that CR's input, and its status becomes `Accepted` |
| Modify `spec` | The logs show the updated values; the existing `Accepted` status doesn't prove this change was processed |
| Restart the Operator | The new Pod's logs show the existing CR again; don't rely only on the status from before the restart |

Next, test `on.update`: temporarily change the CR's `spec.port` from `8080` to `9090` and check whether the logs record the new value. This version only logs inputs and won't modify the Todo API workload.

Do not run this port test on a version with resource management enabled, or it will actually change Todo's listening port and traffic configuration.

```bash
kubectl patch microservice todo-api -n todo --type=merge \
  -p '{"spec":{"port":9090}}'
kubectl logs deployment/microservice-operator -n todo -c operator --tail=20
```

The handler may not have finished running immediately after you submit the patch. If `port=9090` hasn't appeared in the logs yet, check again shortly. Once you see the new value, restore `spec.port` to `8080` and check the logs again for `port=8080`:

```bash
kubectl patch microservice todo-api -n todo --type=merge \
  -p '{"spec":{"port":8080}}'
```

Finally, test `on.resume`: restart the Operator without modifying the CR, and confirm that it still processes the existing `todo-api`. The commands below wait for the Operator rollout to complete before checking the logs. This time, verify that the new Pod's logs show that CR's input, rather than relying only on the `Accepted` left over from before the restart:

```bash
kubectl rollout restart deployment/microservice-operator -n todo
kubectl rollout status deployment/microservice-operator -n todo --timeout=300s
kubectl logs deployment/microservice-operator -n todo -c operator --tail=20
```

Putting these steps together: creating a CR, changing `spec`, or reading an existing CR after an Operator restart all trigger `accept`, which logs the input and writes back `Accepted`:
