# Day 19 - Operators and Kopf: from a service contract to a control loop

The previous article introduced `Microservice` to Kubernetes: service teams can express their deployment requirements through `image` and `port`, and the API Server can validate the data format. But even if this custom resource (CR) passes validation, the existing `todo-api` will not update to match it. We still need a program that reads the requirements and modifies the workload.

We will implement that program as an Operator. Before we start, there is a question to answer: with Helm and Argo CD already in place, why write our own program to manage deployments?

## Do we need an Operator if we already have Helm and Argo CD?

If all we need is to supply an image, generate a `Deployment` and a `Service`, and deploy them after a Git review, Helm and Argo CD can do that. A Backstage form can also generate Helm values; it does not have to submit a CR. Building an Internal Developer Platform (IDP) does not necessarily require writing an Operator.

This series uses `Microservice` so that Kubernetes also holds a service contract. Developers submit an image and a port. The platform uses those requirements to maintain the replica count, health checks, and OpenTelemetry (OTel) configuration, then writes the processing results back to the same CR. Tools that query it later can tell whether the service is updating, ready, or encountering an error.

The cost is another controller to maintain, including its API permissions, error retries, and status reporting. If we only need to parameterize a few YAML files, that cost may not be worthwhile. This series takes this approach to implement the process of reading requirements from a CR, maintaining resources, and reporting status.

## How does an Operator differ from a deployment script?

A deployment script usually exits when it finishes. Suppose a script creates a `Service` and someone deletes it the next day. The script will not run again on its own. An Operator is a controller with application management rules that continuously watches resources and handles differences between the requirements and the current state.

For the Todo API, one `reconcile` reads the `Microservice` and the current `Deployment` and `Service`, works out their desired configuration, and creates missing resources or updates fields that differ. It then observes the results again. This is the control loop introduced earlier. The same request may be processed multiple times, so each run must converge on the same set of resources. Running it again must not create another `Deployment`.

The Operator does not need to create Pods itself. Once it submits a `Deployment`, Kubernetes' built-in controllers still handle the rollout, Pod creation, and replica maintenance. Our program is responsible only for the service contract and the resources generated from it.

## What does an Operator development framework handle for us?

We can write a controller without a framework, but beyond the deployment rules, we would also have to handle Kubernetes API event watches, recovery after disconnections, processing progress, and retries. Operator development frameworks provide these shared mechanisms so we can focus our code on what to do when an event arrives.

There are two terms to distinguish here. "Operator development framework" is a general term for this kind of tool. "Operator Framework" is a specific project that includes tools such as Operator SDK and Operator Lifecycle Manager (OLM). Kopf is a separate Python framework, not a component of that project.

The common choices are:

- Kubebuilder / controller-runtime: Development tools and libraries in the Go ecosystem. Kubebuilder helps create the project, API types, and related files, while controller-runtime provides the mechanisms needed to run a controller.
- Operator SDK: The development tools in Operator Framework. It supports development with Go, Ansible, Helm, and other approaches, and also covers packaging and lifecycle management.
- Kopf: Kubernetes Operator Pythonic Framework. It uses Python decorators to register handlers, specifying which function to run when a CR is created, a field changes, or the program starts.

This series uses Kopf mainly to make the implementation easy to follow. In the next article, one Python function and a few decorators will be enough to understand how CR events enter the program, without learning Go project scaffolding and code generation tools at the same time.

That does not make Kopf suitable for every team. If the existing controllers are all written in Go, staying with controller-runtime may be easier to maintain. Choosing Python does not remove the need to understand the Kubernetes API, either. We still have to write the code to create resources, check ownership, and observe rollouts.

## How do Kopf handlers process the Todo API?

We will first register a handler for CR creation and `spec` change events. When the Operator restarts, we will also have Kopf run a resume handler for existing CRs so processing can continue without waiting for someone to change the image again.

These events only tell the program that there is a request to process. Kopf does not know how many replicas the Todo API needs, which Pods the `Service` should select, or when it can report readiness. The Python code that follows will define those rules:

| Task | Todo API approach |
| --- | --- |
| Generate workloads | Put `spec.image` and `spec.port` into the `Deployment` and `Service`, applying platform defaults |
| Avoid modifying resources owned by others | Use `ownerReferences` to confirm that resources belong to this CR, and report a conflict if an external resource has the same name |
| Handle deleted resources or configuration changes | Periodically read the current state and restore missing resources and platform-managed settings |
| Determine the outcome of an update | Observe the new version's rollout and the `Service` endpoints, and write the results to the CR's `status` |

When a `Service` is deleted, the CR's `spec` does not change. A Pod becoming ready does not trigger a CR configuration update, either. This example handles both cases with a periodic check every ten seconds, without separately watching each type of child resource for now. This approach is easier to follow, but it adds API calls and a delay. It cannot guarantee a repair within ten seconds.

When an API call fails temporarily, a handler can use Kopf's `TemporaryError` to request a retry later. When input violates the service rules, it records the reason and reports an error to avoid repeatedly submitting the same operation. The framework provides the retry mechanism, but the program still decides which errors to retry.

This Operator will initially support only the existing Todo API. It will reuse Todo's health endpoints and OTel configuration, so it cannot deploy arbitrary images as a general-purpose service deployment tool. Existing resources with the same names must also be explicitly handed over first; the Operator cannot simply overwrite them. After a version update, the status must identify the corresponding generation so that available old Pods are not mistaken for a successful rollout of the new version. We will implement these details when we cover resource management and health reporting, respectively.

The next article will leave the Todo workload unchanged. We will first have Kopf receive a CR in the `todo` Namespace, log it, and write back `Accepted`. Once we confirm that this works, we will add resource creation and updates.
