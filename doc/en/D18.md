# Day 18 - Designing the `Microservice` CRD: bringing Kubernetes configuration into the platform contract

The previous post used Backstage to lay out the path for updating the Dev version of `todo-api`: a developer enters the digest produced by CI, the template proposes a configuration change in Git, and after review and merge, Argo CD syncs the `Microservice` to Kubernetes. This path is not connected yet, but we first need a shared definition of the data the form should produce and the configuration the Operator should read.

The `Microservice` Custom Resource Definition (CRD) from Day 05 already has `image`, `port`, and an initial `status`. This time, we will use that contract to see which input errors it can catch, then address two requirements: which settings should we expose when a service needs environment variables, and how can we tell whether the status reflects the new version after changing the image? `env` and `conditions` are still designs; this post will not treat them as fields that are already available.

## Which errors can the existing CRD catch?

The existing `Microservice` is a namespaced resource, with the API group `platform.example.io` and version `v1alpha1`. This series puts `todo-api` in the existing `todo` Namespace. Different Namespaces can each have a resource with the same name, so when querying deployment requirements and status, you must check both the Namespace and the name. The following excerpt shows the CRD's version and schema configuration; it is not a complete installation manifest:

```yaml
spec:
  group: platform.example.io
  scope: Namespaced
  versions:
    - name: v1alpha1
      served: true
      storage: true
      subresources:
        status: {}
      schema:
        openAPIV3Schema:
          type: object
          properties:
            spec:
              type: object
              required:
                - image
                - port
              properties:
                image:
                  type: string
                  minLength: 1
                port:
                  type: integer
                  minimum: 1
                  maximum: 65535
```

Within `spec`, `image` must be a nonempty string, and `port` must be an integer from `1` to `65535`. `port: 65536` is valid YAML syntax, but the API Server should reject it based on the schema. The string `"8080"` also fails the type check.

However, `minLength: 1` only checks the string's length. It does not check the image source or version format. The existing `todo-api` example uses `ghcr.io/yrw9281/it30-todo-api:0.1.0`, and this tag passes validation. A nonexistent image name might also pass. Although the previous post's template fixes the repository and collects a digest, the CRD itself still accepts tags. The form's restrictions cannot be treated as rules the Kubernetes API already enforces.

Restricting input to an approved GHCR repository and digest format requires corresponding rules at the input layer, in Git configuration checks, and in cluster policies. This schema cannot confirm whether a digest was produced by authorized CI or whether the submitter belongs to the Todo team.

## Which settings should service teams control?

Having `port` in the CRD does not mean developers need to enter it again for every version update. In the Dev template for `todo-api`, for example, the service name is fixed at `todo-api`, the Namespace is `todo`, and `port` is `8080`. The developer only enters the digest. Even though these values do not appear on the form, the generated `Microservice` must still include them.

We can separate the responsibilities of the service contract and the interface used to submit changes as follows:

| Setting or result | Who decides | How it is expressed |
| --- | --- | --- |
| Service name, image, port | The service team specifies its requirements; the template can fix values that do not need to change | `metadata.name`, `spec.image`, `spec.port` |
| Namespace, target environment, and Git location | The platform restricts these based on team identity and environment rules | Controlled templates and deployment configuration, with no arbitrary input |
| Replica count, labels, probes, resource limits, and OpenTelemetry defaults | The platform defines the rules, which the Operator is planned to apply | Resources such as `Deployment` and `Service` that the Operator should create or update |
| Processing progress and availability of managed resources | The Operator is planned to observe and report these | `status`, not filled in by the service team |

Environment variables require the same decisions. Suppose `todo-api` supports reading its log level from `LOG_LEVEL`. The service team then has a reason to adjust it through the contract. The application must support that name first; adding a value to YAML alone will not automatically tell the application how to use it.

If we add `spec.env`, a string map can express nonsensitive settings without exposing the entire Kubernetes `PodSpec`. The design also needs to decide which names can be overridden, whether values must always be strings, and which defaults apply when values are omitted. For `todo-api`, the existing `Deployment` already sets environment variables such as `OTEL_SERVICE_NAME` and `OTEL_EXPORTER_OTLP_ENDPOINT`. If the platform manages these values, ordinary input should not be allowed to overwrite them. Otherwise, telemetry from the same service might be sent to different destinations.

Tokens, passwords, and connection strings must not go into this map or Git either. Sensitive values need a separate design for Secret references and access permissions. The current CRD has neither `spec.env` nor a Secret reference field, so this section only determines how much the contract should expose. It does not provide YAML that is not yet supported.

The contract's boundary is as follows: the service team submits `spec`, the API Server validates and stores it, and the Operator then handles workloads according to platform rules and writes its observations back to `status`. `env`, `conditions`, and the Operator have not yet been implemented.

## Which resource version should `status` report on?

The existing `status` defines `phase`, `observedGeneration`, and `managedResources`. `phase` summarizes the processing stage, while `managedResources` records the names of the managed `Deployment` and `Service`. Those two fields alone, however, cannot tell us which update the status corresponds to.

Suppose `todo-api` was ready, and the team has just changed `spec.image` to a new digest. The old Pods may still be serving requests while the new Pods have not yet started. If the interface simply keeps showing the previous ready status, developers will mistakenly think this update is complete.

This is what `status.observedGeneration` is for. Kubernetes maintains `metadata.generation` and increments it when `spec` changes. The Operator should write the generation corresponding to its current observations into `status.observedGeneration`. When the two differ, the status does not yet reflect the latest service configuration and cannot be used to determine that the new version is ready.

Matching values only mean that the status corresponds to the new version; they do not guarantee that the workload is available. The planned contract will therefore add `status.conditions` to express readiness and its reasons. For example, when the `Deployment` has been updated but is still waiting for new Pods, it should report `Ready=False`. An image pull failure also needs a reason that helps with diagnosis. Acceptance of an update by the API must not be treated as service readiness.

Based on the actual processing results for the same version of `spec`, the Operator must update `status.observedGeneration` and `status.conditions`. It cannot simply read the new configuration and retain the old `Ready=True`. Tools reading the status can then distinguish between "the new configuration has not been processed yet" and "it has been processed, but the workload is not ready yet."

The CRD's `subresources.status` shown earlier gives `status` a separate update interface, allowing the platform to grant the Operator write access separately through RBAC. Enabling this interface alone does not automatically restrict all users or produce observations. There is currently no Operator implementation that handles `Microservice`, so having the API Server store a resource will not create a `Deployment` or populate its status.

## Have the API Server validate input for `todo-api`

The steps in Day 05 already included installing this CRD and checking the example CR with a dry run. If you are using the same cluster, the `Microservice` resource type should already exist, so there is no need to reinstall it here. Before proceeding, still confirm that the currently connected cluster has this CRD and the `todo` Namespace, and that you have permission to submit a `Microservice` in that Namespace:

```bash
kubectl get crd microservices.platform.example.io
kubectl get namespace todo
```

If the CRD returns `NotFound`, the currently connected cluster does not have this resource type, and you need to complete the full CRD installation steps from Day 05. Running only a dry run on the CRD definition will not make the API Server start accepting `Microservice` resources either. The inputs below were tested with server-side dry runs on a cluster with this CRD installed. No CRs were stored.

Save the following as `todo-api.yaml`. This uses the tag example in the `todo` Namespace to check the existing contract. The template also targets the same Namespace, but uses CI-produced digests for version updates:

```yaml
apiVersion: platform.example.io/v1alpha1
kind: Microservice
metadata:
  name: todo-api
  namespace: todo
  labels:
    app.kubernetes.io/owner: todo-team
spec:
  image: ghcr.io/yrw9281/it30-todo-api:0.1.0
  port: 8080
```

Use a server-side dry run to send the data to the API Server for validation without storing the resource:

```bash
kubectl apply --server-side --dry-run=server -f todo-api.yaml
```

This input passes validation, and the command returns exit code `0`. To test rejection, make a copy named `invalid-todo-api.yaml`, change `metadata.name` to `invalid-todo-api`, and change `port` to `65536`, leaving everything else unchanged:

```bash
kubectl apply --server-side --dry-run=server -f invalid-todo-api.yaml
```

The API Server rejects this input, stating that `spec.port` must be less than or equal to `65535`, and the command returns exit code `1`. You can test other fields the same way, changing one value at a time so you know which restriction rejected the data. All of the following cases were tested this way:

| Input change | Observed result with the current schema |
| --- | --- |
| Use the original image with `port` set to `8080` | Accepted |
| Set `port` to `1` and `65535`, respectively | Accepted; both boundary values are included in the range |
| Set `port` to `0` or `65536` | Rejected; outside the range |
| Set `port` to the string `"8080"` | Rejected; the type is not an integer |
| Set `image` to an empty string | Rejected; does not meet the minimum length |
| Keep `spec`, but remove either `image` or `port` from it | Rejected; a required field within `spec` is missing |
| Remove the entire `spec` | The current schema does not reject input for a missing `spec` |

The last row exposes a gap in the existing contract: `required` is defined inside the schema for `spec`, but the root does not list `spec` as required. When `spec` is present, it must contain `image` and `port`. When the entire `spec` is omitted, however, this rule does not require it to appear. To require every resource to have deployment requirements, the root must also list `spec` as required. Before changing the contract, you also need to check whether existing CRs satisfy the new restriction.

A successful dry run only means that the API accepts the data. It cannot verify whether the Operator creates workloads. The `env` extension needs tests for nonstring values and the handling of platform-reserved names. `conditions` needs tests with the Operator to check whether the old ready status persists when the new version is not ready yet. A single schema validation cannot confirm these scenarios.
