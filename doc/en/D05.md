# Day 05 - What is a CRD? Teaching Kubernetes about custom resources

Yesterday, we separated shared settings from environment-specific differences for `todo-api` and `web`. Both services still need their own `Deployment` and `Service`, though, and their authors need to know which labels, probes, and selectors they must get right. Documentation can explain the rules, but it cannot stop a noncompliant YAML file from entering the cluster.

Consider the existing `todo-api` and `web` services. All they may need to express is which image to use and which port to serve on. The remaining Kubernetes details should not have to be decided from scratch every time. A Custom Resource Definition (CRD) lets us add this team-specific language to the Kubernetes API, starting with a service contract that can be validated.

## Problem and design: teaching Kubernetes the team's language

Kubernetes knows about native resources such as `Deployment`, `Service`, and `ConfigMap`, but it does not know what a "deliverable microservice" means. Once a CRD is installed, the API Server accepts a new resource type, such as `Microservice`. It also checks incoming data against the schema defined in the CRD.

Four closely related terms describe different responsibilities:

- CRD: the API definition of a resource type, including its group, version, names, and schema.
- Custom Resource (CR): an actual resource instance created by a developer, such as `todo-api`.
- Controller/Operator: watches CRs, turns their intent into native resources such as Deployments and Services, and reports `status`.
- API Server: validates and stores CRs according to the CRD schema, but does not automatically create any workloads.

That last distinction matters. A CRD defines what data Kubernetes recognizes; a Controller/Operator decides what to do when that data arrives. Being able to run `kubectl get microservices` after installing a CRD does not mean that `todo-api` or `web` has been deployed through a CR. Without a controller, a CR is just a record stored by the API Server.

## Start with a minimal contract, not a copy of PodSpec

When defining a platform-specific contract resource, avoid putting the entire Kubernetes `PodSpec` into the CRD unchanged. This may appear to preserve flexibility, but it simply gives native YAML another name. The platform cannot provide reliable defaults, and developers still have to learn every low-level option.

The first version for the Todo system lets service owners choose only the image and service port. The platform handles replica strategy, managed labels, health checks, default resource policy, and telemetry injection. The core schema for this CRD is:

```yaml
apiVersion: apiextensions.k8s.io/v1
kind: CustomResourceDefinition
metadata:
  name: microservices.platform.example.io
spec:
  group: platform.example.io
  scope: Namespaced
  names:
    plural: microservices
    singular: microservice
    kind: Microservice
    shortNames:
      - ms
  versions:
    - name: v1alpha1
      served: true
      storage: true
      subresources:
        status: {}
      schema:
        openAPIV3Schema:
          type: object
          properties:
            spec:
              type: object
              required:
                - image
                - port
              properties:
                image:
                  type: string
                  minLength: 1
                port:
                  type: integer
                  minimum: 1
                  maximum: 65535
            status:
              type: object
              properties:
                phase:
                  type: string
                observedGeneration:
                  type: integer
                managedResources:
                  type: object
                  properties:
                    deployment:
                      type: string
                    service:
                      type: string
```

`v1alpha1` means the contract may still evolve, but it does not give us license to break existing CRs arbitrarily. Even during alpha, we need to consider whether new fields are compatible, how older data will be read, and the cost of future version conversion.

## Express `todo-api` and `web` as service intent

After the CRD is installed, the service team can submit `todo-api` without a long `Deployment` definition:

```yaml
apiVersion: platform.example.io/v1alpha1
kind: Microservice
metadata:
  name: todo-api
  namespace: todo
  labels:
    app.kubernetes.io/owner: todo-team
spec:
  image: ghcr.io/yrw9281/it30-todo-api:0.1.0
  port: 8080
```

`web` uses the same contract, differing only in its image and port:

```yaml
apiVersion: platform.example.io/v1alpha1
kind: Microservice
metadata:
  name: web
  namespace: todo
  labels:
    app.kubernetes.io/owner: todo-team
spec:
  image: ghcr.io/yrw9281/it30-todo-web:0.1.0
  port: 80
```

`spec` is the intent submitted by the service owner: which image to use and which port to serve on. The platform writes back the following status after observing the resource. Service owners should not declare it manually:

```yaml
# Example status written back after the Operator observes the resources
status:
  observedGeneration: 4
  phase: Progressing
  managedResources:
    deployment: todo-api
    service: todo-api
```

With the `status` subresource enabled, the platform controller can receive permissions specifically for updating `status`, while ordinary service submitters manage only `spec`. This boundary prevents "the resource has been submitted" from being mistaken for "the service is healthy."

Early status designs often used phase to enumerate states directly, such as Progressing and Ready. Modern Kubernetes APIs recommend combining observedGeneration with a standard conditions array. This expresses detailed health information and lets users tell whether the controller has processed the latest spec.

## CRDs are not a universal abstraction

Turning a concept into a CRD has a cost. Every field is an API commitment that needs ongoing maintenance. Abstract too early, and you may lock in deployment details that have not stabilized. Wait too long, and each team will invent its own YAML. Capabilities that make good CRDs generally recur across multiple services, require a controller to maintain them continuously, and have clear domain semantics.

A CRD does not replace RBAC, Policy, or Git review either. It can constrain only structure and field ranges. Governance rules still need to define who can create resources, whether images come from a trusted GHCR repository, and when something can enter Production.

## Testing and validation

Apply the CRD to the cluster first, then use a server-side dry run to check whether the API Server accepts the CRs:

```bash
# Install the resource type; this step writes to the cluster
kubectl apply -f src/1-kubernetes/crd/microservice-crd.yaml

# Both valid CRs should pass schema validation, but no Deployment is created
kubectl apply --server-side --dry-run=server \
  -f src/1-kubernetes/crd/todo-api.yaml \
  -f src/1-kubernetes/crd/web.yaml

# A port of 65536 should be rejected by the schema before being stored
kubectl apply --server-side --dry-run=server \
  -f src/1-kubernetes/crd/invalid-todo-api.yaml
```

The CRs for `todo-api` and `web` can pass validation, but they will not automatically produce Deployments because the Operator has not been implemented yet. In `invalid-todo-api.yaml`, `port: 65536` exceeds the schema's upper limit, so the API Server should reject the write. If an undefined field is supplied, the API Server rejects the write by default because it fails structural validation. Even if a configuration that allows pruning ignores the field, that must not be mistaken for successful validation.

These results confirm that the CRD is a contract, not the automation itself. To turn a `Microservice` CR into native Kubernetes resources, a controller still needs to watch CRs continuously and run `reconcile`.

## Conclusion

A CRD lets Kubernetes begin to understand the platform's domain-specific language, but it defines only the shape of service intent. Every `Microservice` change still needs a trusted storage location and a review mechanism. These let us identify which configuration an environment should maintain, trace its history, and rebuild it when needed. Tomorrow, we will try using Git as the single source of truth (SSoT).
