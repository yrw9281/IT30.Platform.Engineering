# Day 29 - Adding Gatekeeper policies to the platform delivery workflow

The previous article used a rule against `privileged` to explain how Gatekeeper checks settings before a resource is written. Today, we'll implement that requirement as a `ConstraintTemplate`, add rules for CPU/memory limits and images, and see how to configure the scope and enforcement mode of each of the three policies.

We'll continue using the Todo API, with complete policy YAML below. Gatekeeper must already be installed before you use these examples. For each set of configurations, create the Template first, wait for the Custom Resource Definition (CRD) it generates to be ready, then create the corresponding Constraint.

## `k8sdeploymentnoprivileged`: prohibit privileged containers

First, we'll implement the requirement from the previous article: the Todo API does not need to access host devices, so its containers must not enable `privileged`.

```yaml
apiVersion: templates.gatekeeper.sh/v1
kind: ConstraintTemplate
metadata:
  name: k8sdeploymentnoprivileged
spec:
  crd:
    spec:
      names:
        # Gatekeeper creates this Kind for the Constraint below.
        kind: K8sDeploymentNoPrivileged
      validation:
        # Define the parameters schema; this fixed rule needs no extra parameters.
        openAPIV3Schema:
          type: object
  targets:
    - target: admission.k8s.gatekeeper.sh
      # The multiline text below | is Rego, not YAML fields.
      rego: |
        package k8sdeploymentnoprivileged

        # Report msg for each violating container; the Constraint determines whether to reject it.
        violation[{"msg": msg}] {
          input.review.kind.kind == "Deployment"
          # Deployment containers are in the Pod template, not spec.containers.
          pod_spec := input.review.object.spec.template.spec
          # := binds variables; [_] iterates over array elements. Check both container types.
          field := ["containers", "initContainers"][_]
          container := pod_spec[field][_]

          # Unset or false is allowed; report only true.
          container.securityContext.privileged == true

          msg := sprintf(
            "container <%v> must not enable securityContext.privileged",
            [container.name]
          )
        }
```

The Template only defines how to check. Next, use a Constraint to specify that it should check `Deployment` resources in `todo`:

```yaml
apiVersion: constraints.gatekeeper.sh/v1beta1
kind: K8sDeploymentNoPrivileged # Matches the Kind defined by the Template.
metadata:
  name: todo-no-privileged
spec:
  # Demonstrate enforcement; start with dryrun to inventory violations when first adopting the policy.
  enforcementAction: deny
  match:
    namespaces:
      - todo
    kinds:
      - apiGroups: ["apps"]
        kinds: ["Deployment"]
```

This `deny` rule is expected to reject containers that enable `privileged`. Containers that do not enable it will not be blocked by this rule, but they still need to pass other checks.

## `k8sdeploymentrequiredlimits`: require CPU and memory limits

The Operator already sets limits for the Todo API, but other workloads in `todo` may not have them. This rule also checks container settings in `Deployment` resources:

```yaml
apiVersion: templates.gatekeeper.sh/v1
kind: ConstraintTemplate
metadata:
  name: k8sdeploymentrequiredlimits
spec:
  crd:
    spec:
      names:
        kind: K8sDeploymentRequiredLimits
      validation:
        openAPIV3Schema:
          type: object
  targets:
    - target: admission.k8s.gatekeeper.sh
      rego: |
        package k8sdeploymentrequiredlimits

        # The field must exist and be nonempty; this does not assess whether the limit is appropriate.
        has_limit(container, resource) {
          value := container.resources.limits[resource]
          value != null
          value != ""
        }

        violation[{"msg": msg}] {
          input.review.kind.kind == "Deployment"
          pod_spec := input.review.object.spec.template.spec
          field := ["containers", "initContainers"][_]
          container := pod_spec[field][_]

          # Check CPU and memory separately and report each missing limit.
          resource := ["cpu", "memory"][_]
          # Omitting resources or limits entirely also counts as a missing field.
          not has_limit(container, resource)

          msg := sprintf(
            "container <%v> is missing resources.limits.%v",
            [container.name, resource]
          )
        }
```

This time, start with `dryrun` to inventory violations without immediately blocking updates to existing services:

```yaml
apiVersion: constraints.gatekeeper.sh/v1beta1
kind: K8sDeploymentRequiredLimits
metadata:
  name: todo-required-limits
spec:
  # Do not block violating requests; use audit results to identify workloads that need fixes.
  enforcementAction: dryrun
  match:
    namespaces:
      - todo
    kinds:
      - apiGroups: ["apps"]
        kinds: ["Deployment"]
```

When a memory limit is missing, the violation message is expected to include the container name and `resources.limits.memory`. The Todo API currently has CPU `500m` and memory `256Mi` configured, so it meets this rule. That does not mean these limits are necessarily appropriate, or that total usage across the Namespace is limited.

## `k8smicroserviceimagepolicy`: restrict image sources and require a digest

The image can be checked at the custom resource (CR) level, in `Microservice.spec.image`. Currently, the CRD only requires this field to be a non-empty string, so a value such as `ghcr.io/yrw9281/it30-todo-api:0.1.0` also passes schema validation. People who submit a CR directly bypass the Backstage form, so we cannot rely solely on restrictions at that entry point.

```yaml
apiVersion: templates.gatekeeper.sh/v1
kind: ConstraintTemplate
metadata:
  name: k8smicroserviceimagepolicy
spec:
  crd:
    spec:
      names:
        kind: K8sMicroserviceImagePolicy
      validation:
        openAPIV3Schema:
          type: object
  targets:
    - target: admission.k8s.gatekeeper.sh
      rego: |
        package k8smicroserviceimagepolicy

        valid_image(image) {
          # Fix the repository and require 64 lowercase hexadecimal characters after sha256:.
          # ^ and $ anchor the entire string, excluding other sources or trailing text.
          # Tags such as :0.1.0 can be repointed, so they do not meet the digest requirement.
          regex.match(
            "^ghcr[.]io/yrw9281/it30-todo-api@sha256:[0-9a-f]{64}$",
            image
          )
        }

        violation[{"msg": msg}] {
          input.review.kind.group == "platform.example.io"
          input.review.kind.kind == "Microservice"
          image := object.get(input.review.object.spec, "image", "")

          # Other repositories do not match this rule, even with a digest.
          not valid_image(image)

          msg := sprintf(
            "Microservice <%v> spec.image must use ghcr.io/yrw9281/it30-todo-api@sha256:<64 lowercase hex characters>",
            [input.review.object.metadata.name]
          )
        }
```

The corresponding Constraint now selects `Microservice` resources. This example uses `warn`, which warns without blocking:

```yaml
apiVersion: constraints.gatekeeper.sh/v1beta1
kind: K8sMicroserviceImagePolicy
metadata:
  name: todo-image-policy
spec:
  # Return an API warning; users see it only if the submitting tool displays warnings.
  enforcementAction: warn
  match:
    namespaces:
      - todo
    kinds:
      - apiGroups: ["platform.example.io"]
        kinds: ["Microservice"]
```

This example requires all `Microservice` resources in `todo` to use the Todo API repository, which suits the current single-service setup. The specified source with a correctly formatted digest is expected to pass. A tag, another source, or a digest of the wrong length will violate the rule. This rule does not scan for vulnerabilities or verify where the image was built.

## Differences between `enforcementAction` modes

| `spec.enforcementAction` | Rejects requests that violate the policy? | Feedback |
| --- | --- | --- |
| `dryrun` | No | Returns no policy warnings; violations can be viewed in `status.violations` from the audit |
| `warn` | No | Returns API warnings; the submission tool must be able to display them |
| `deny` | Yes | Returns the reason for rejection |

The default is `deny` when no mode is specified. Each Constraint can have its own mode, but a request that violates any applicable `deny` rule will be rejected. Other `warn`/`dryrun` rules cannot allow it through.

An audit does not modify existing resources, and switching to `deny` does not delete them. A request will be rejected on the next update if it still violates an applicable rule. Also, Gatekeeper's `dryrun` still allows writes, unlike Kubernetes `server-side dry-run`, which does not store resources.

## Where do you find the reason for a rejected request?

In the Todo platform's delivery design, Argo CD submits a `Microservice`, the Operator submits a `Deployment` based on that CR, and a Kubernetes controller then creates Pods. These are separate API requests made by different components, so errors return to different components as well. The following assumes the corresponding rules use `deny` and there is also a separate rule for checking Pods:

![Policy rejections for Microservice, Deployment, and Pod resources are reported as Argo CD sync errors, Operator API errors, and ReplicaSet events, respectively](../assets/day-29-policy-rejection-flow.png)

Use the rejected resource to locate the error:

| Rejected resource | Where to look | Result of this change |
| --- | --- | --- |
| `Microservice` | Argo CD sync errors | The CR change was not written, so the Operator will not deploy based on this change |
| `Deployment` | The Operator's API error logs | The CR was written, but the workload change was not |
| Pod | `ReplicaSet` events | The `Deployment` was written, but the rejected Pod was not created, so there are no Pod logs to check |

## Correcting settings and handling exceptions

After finding the reason for rejection, fix the configuration at its source: change `Microservice.spec.image` in the configuration Pull Request (PR) for the image, and have the platform team change the Operator defaults for limits. Do not edit a managed `Deployment` directly, since the next `reconcile` may revert the change. When adjusting policies, also check that the Backstage form and Git checks are consistent with them.

If you need an exception, change the Constraint's `spec.match` to exclude it without modifying Rego. Use `excludedNamespaces` for an entire Namespace, or `labelSelector` to exclude resources by label. For example, to exempt `Deployment` resources whose `metadata.labels.app` is `todo-api` from the limits check, change the earlier `todo-required-limits` to:

```yaml
apiVersion: constraints.gatekeeper.sh/v1beta1
kind: K8sDeploymentRequiredLimits
metadata:
  name: todo-required-limits # Update the same Constraint, not a separate rule.
spec:
  enforcementAction: dryrun
  match:
    namespaces:
      - todo
    kinds:
      - apiGroups: ["apps"]
        kinds: ["Deployment"]
    labelSelector:
      matchExpressions:
        - key: app
          operator: NotIn # Exclude app=todo-api; keep checking the others.
          values: ["todo-api"]
```

This matches `Deployment.metadata.labels`, not the labels in the Pod template. Resources without an `app` label are still checked. The exception only affects this limits Constraint; it does not skip the privileged check or other rules. It also matches labels, not resource names: anyone who can change `app` to `todo-api` can meet this exclusion condition.
