# Day 26 - Viewing services and Kubernetes deployment status in Backstage

The previous post turned the Operator's reports into Argo CD health status. Today we return to Backstage so developers can check the current image, replicas, and Pod status from the `todo-api` service page. The Software Catalog provides service information, and the Kubernetes plugin queries the related workloads. These queries do not trigger deployments.

## Mapping Catalog services to Kubernetes resources

A Catalog `Component` does not automatically map to a Kubernetes `Deployment` just because they share a name. We use two annotations to specify the Namespace and label selector:

```yaml
apiVersion: backstage.io/v1alpha1
kind: Component
metadata:
  name: todo-api
  description: Todo API service
  annotations:
    backstage.io/kubernetes-namespace: todo
    backstage.io/kubernetes-label-selector: app=todo-api
spec:
  type: service
  lifecycle: experimental
  owner: todo
```

Once this definition is registered, the plugin queries resources in the `todo` Namespace whose `metadata.labels` match `app=todo-api`. The existing Backstage instance has already loaded this service definition. For another Backstage instance, first put `catalog-info.yaml` somewhere it can read, then import it into the Catalog.

Note that `Deployment.spec.selector` and `Service.spec.selector` select Pods; they are not labels on the resources themselves. The Operator from the earlier posts has added `app=todo-api` to the `Deployment`, `Service`, and Pod template, so all of them can be found. Other resources with the same labels may also appear. Labels express an association, not ownership.

## How does the Kubernetes plugin connect to the cluster?

The plugin backend makes the actual Kubernetes API calls. The existing Backstage instance has both the frontend `@backstage/plugin-kubernetes` and backend `@backstage/plugin-kubernetes-backend` enabled, with the cluster connection configured in `app-config.yaml`:

```yaml
kubernetes:
  serviceLocatorMethod:
    type: multiTenant
  clusterLocatorMethods:
    - type: config
      clusters:
        - url: ${K8S_API_URL}
          name: it30-cluster
          authProvider: serviceAccount
          serviceAccountToken: ${K8S_BACKSTAGE_TOKEN}
          caData: ${K8S_BACKSTAGE_CA_DATA}
          skipMetricsLookup: true
```

`multiTenant` lets services query the configured clusters, while `clusterLocatorMethods` lists the connection details. `it30-cluster` is the name displayed in Backstage; it does not have to match the `kubectl` context name. The API address, token, and Certificate Authority (CA) data needed for the connection are injected from the `backstage-k8s-conn` Secret in the `backstage` Namespace:

| Secret key | Environment variable | Purpose |
| --- | --- | --- |
| `apiUrl` | `K8S_API_URL` | Kubernetes API address reachable from the Backstage backend |
| `token` | `K8S_BACKSTAGE_TOKEN` | Token for the `backstage-k8s-reader` ServiceAccount in the `todo` Namespace |
| `caData` | `K8S_BACKSTAGE_CA_DATA` | Base64-encoded CA certificate data used to verify the API Server certificate |

Keep credentials on the backend. Do not put them in the Catalog or pass them to the browser, and do not disable TLS verification. `skipMetricsLookup: true` skips the Kubernetes Metrics API, so the page does not show live CPU or memory usage. This does not affect OpenTelemetry or Grafana.

## Checking the Todo API's current status from the service page

Open the Kubernetes view for `todo-api` in the Catalog and check that the cluster is `it30-cluster` and the Namespace is `todo`. The results should include the `Deployment`, `Service`, Pods, and related `ReplicaSet` resources that match the labels. Focus on:

| What to check | Question it answers |
| --- | --- |
| Target image of the `Deployment` | Which version does the current configuration require? |
| Desired and ready replica counts | How many replicas have met the readiness conditions? |
| Pod images, readiness, and restart status | Are any Pods still running the old version, or are containers restarting repeatedly? |
| `Service` selector and port | Which group of Pods should receive traffic, and on which port? |

If no resources appear, the service may not have stopped. The query criteria or connection could be the problem:

| Display or error | What to investigate |
| --- | --- |
| No matching resources | Check the Namespace and each resource's own `metadata.labels` |
| `Unauthorized` | Check whether the query token is valid or has expired |
| `Forbidden` | Check whether the query identity is allowed to read that resource |
| Connection or certificate error | Check the connection from the backend to the API Server, the API address, and the CA |
| Pods appear but are not ready | Check Pod status and error details. A resource's existence does not mean the service is available |

Storing a token in a `Secret` does not renew it automatically. After updating it, recreate the Backstage Pod so it reads the new value. Passing Backstage's own health check does not mean it can still query Kubernetes.

## Do two ready Pods mean the rollout is complete?

The Operator's target is two replicas, but the Pod count may increase during a rollout, and old Pods may still be ready. To confirm the rollout result, compare the approved image digest, the `Deployment`'s target image, and the progress of the new replicas. Counting healthy Pods alone is not enough.

To read the results compiled by the Operator, you can separately query the `Microservice` Custom Resource (CR):

```bash
kubectl get microservice todo-api -n todo -o yaml
```

This command uses the current `kubectl` identity. The existing plugin is not configured to query `Microservice`, and its backend identity does not have permission to read it, so the page will not automatically show its conditions. Adding support requires configuring resource queries, authorization, and presentation together.

Use the same checks as on Day 22: compare the CR's `metadata.generation` with `status.observedGeneration`. Once they match, check `Ready`, `Stalled`, and the reasons. This only confirms workload status. Functions such as creating a Todo still need to be verified through actual requests and telemetry data in Grafana.

## To find out who approved a version, return to Git

The Kubernetes plugin shows the current state. It does not automatically collect PR reviews, CI results, or the history of every deployment. To trace a version's origin, you still need to check each tool's records:

| What you want to confirm | Where to look |
| --- | --- |
| Which version was proposed, who reviewed it, and has it been merged? | The Git PR's diff, checks, and review history |
| Which source commit was used to build the image? | The CI run and the image digest it produced |
| Which configuration revision has been synced to the cluster? | The revision, sync, and health of the Argo CD `Application` that reads that configuration source |
| Has the Operator processed the current request? | The CR's generation and conditions |
| Are the workloads and business requests working normally now? | Kubernetes resources, actual requests, and telemetry data |

The CR's conditions also retain only the current observations. `lastTransitionTime` is not a complete rollout history. To preserve a delivery timeline, you also need to collect events, correlate deployment results using image digests and Git revisions, and handle retention periods and missed events.

## Who is using the query permissions?

Through a `Role` and `RoleBinding`, `backstage-k8s-reader` receives `get`, `list`, and `watch` permissions for specified resources in the `todo` Namespace. It has neither deployment write permissions nor permission to read `Secret` resources. This is API authorization, separate from the Catalog selector.

The user logged in to Backstage has a separate identity. `owner: todo` is only team information; it does not restrict who can view the service. The demo uses Guest login and a Backstage permission policy that allows all operations. This is suitable only for a controlled local environment. A production portal also needs user authentication and service access rules.
