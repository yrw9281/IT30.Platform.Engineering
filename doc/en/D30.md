# Day 30 - Looking back at the platform engineering series

On day one, we asked, "Once we've written our microservices, how do we deliver them?" On the final day, we take the perspective of a developer maintaining Todo. Using an update to the Todo API's Dev image as an example, we follow how to request a version update and where to check the results.

## Check the Todo app currently in use

Open the Todo web page. It lets us add tasks, mark them complete, and delete them, and there is already one test task on the screen. After the update, we will return here to verify these functions.

![The Todo web page shows one test task, with options to add, complete, and delete tasks](../assets/day-30-todo-web.png)

The app shows the results of our actions, but if requests slow down, we need more information. Grafana's `Todo service overview` lets us compare request volumes and p95 latency for `todo-api` and `todo-bff`, and filter by route. These metrics let us observe changes over time instead of judging the service's condition from a single operation.

![Grafana compares request volumes and p95 latency for todo-api and todo-bff](../assets/day-30-grafana-service-overview.png)

Before updating, we also check `todo-full-api` in Argo CD. Its current status is `Synced` and `Healthy`. The resource tree shows the `Microservice`, along with the `Deployment` and `Service` the Operator created for it.

`Synced` means the managed configuration matches Git; `Healthy` is the result of health checks. This screenshot shows the state before the update. We still need to check the new version's status later.

![Before the update, the Argo CD Application is Synced and Healthy, and its resource tree includes Microservice, Deployment, and Service](../assets/day-30-argocd-before-update.png)

## Request an update in Backstage

After checking the service's current condition, we go to Backstage to find its entry. The Catalog lists `todo-api`, `todo-bff`, and `web`, all with the `todo` team as their `Owner`. This catalog helps us identify services and the teams responsible for them, but being listed in the Catalog does not mean a service is deployed or healthy.

![The Backstage Catalog lists todo-api, todo-bff, and web, all with todo as their owner](../assets/day-30-backstage-catalog.png)

We are updating the existing Todo API. Under `Create`, select `Update Todo API in Dev` and enter the image digest to deploy. The form accepts only the 64 lowercase hexadecimal characters after `sha256:`. The template fixes the service name, the `todo` Namespace, and port `8080`.

Developers choose which image to deliver without rewriting the entire `Deployment` each time. Although the entry point is called `Create`, this template submits an update request. It does not create another service or environment.

![The Update Todo API in Dev form in Backstage contains a new 64-character image digest](../assets/day-30-backstage-image-digest-form.png)

## Check the actual changes on GitHub

After we submit the form, Backstage generates the `Microservice` configuration and proposes a configuration change through a pull request (PR). Open `Files changed` in this PR. Only the digest in `spec.image` has changed; the service name, Namespace, and port remain the same.

![The configuration PR changes only the Microservice image digest and is still Open](../assets/day-30-github-image-update-pr.png)

Reviewers can then check exactly which version this update will deploy. However, a correctly formatted digest does not mean the image has passed testing. We still need to check the build source and test results. The screenshot shows `0` under `Checks`, so this PR is not evidence that automated configuration checks have passed.

The PR is still `Open` at this point. The update request has been submitted, but `main` has not changed. The cluster should not update directly just because we submitted the form.

## Compare deployment status before and after the update

Before merging, return to Argo CD and inspect the Todo API's `Deployment`. The image digest still starts with `46aef566`. The Operator sets `OTEL_SERVICE_VERSION` to the same image reference so that telemetry includes version information.

![Before the merge, both the Deployment image and OTEL_SERVICE_VERSION use a digest starting with 46aef566](../assets/day-30-todo-api-image-before-merge.png)

After checking the changes, someone with permission merges the PR into `main`. The status on GitHub changes to `Merged`. Only then does the new configuration reach the branch that Argo CD reads.

![GitHub shows that the Todo API configuration PR has been merged into main](../assets/day-30-github-image-update-pr-merged.png)

Argo CD then synchronizes the `Microservice`, and the Operator runs `reconcile` against the new configuration to update the Todo API workload. Backstage does not modify the cluster directly or replace either of these controllers.

Check the `Deployment` again. The image digest now starts with `28492db0`, matching the form input and the PR change. `OTEL_SERVICE_VERSION` has also been updated.

![After the merge, the Deployment image and OTEL_SERVICE_VERSION use a digest starting with 28492db0](../assets/day-30-todo-api-image-after-merge.png)

The change in the image field confirms only that the configuration has been updated. We still need to check synchronization and readiness for this update. Returning to `todo-full-api`, we see that Argo CD has synchronized to commit `2e1bc96`, which follows the PR merge, and the status is `Synced` and `Healthy`.

![After the merge, Argo CD is synchronized to commit 2e1bc96, and the Application is Synced and Healthy](../assets/day-30-argocd-after-update.png)

In the `Microservice`'s Live manifest, the `Ready` condition has a `status` of `"True"`, and `observedGeneration` is `2`, matching the `2` in `metadata.generation`. The readiness status reported by the Operator applies to the current configuration. The condition's message also says that the updated replicas and Service endpoints are ready.

![The Microservice has generation 2, with a True Ready condition and observedGeneration also set to 2](../assets/day-30-microservice-current-generation-ready.png)

Finally, inspect the Todo API Pod that is actually running. Its status is `Running`, the container's `ready` value is `true`, and both `image` and `imageID` contain a digest starting with `28492db0`, matching the version we requested.

![The Todo API Pod is Running, the container's ready value is true, and image and imageID both match the new digest](../assets/day-30-todo-api-updated-pod-ready.png)

Once the deployment is ready, we still need to return to Todo to verify that adding, completing, and deleting tasks work, and use Grafana to check for abnormal requests. Pod readiness and working functionality are separate things. These deployment statuses cannot replace functional tests.

## What did we learn over these 30 days?

### Kubernetes and deployment basics (Day 01-05)

We used `Deployment`, `Service`, and `Ingress` to understand how services run, connect, and receive external requests. Kubernetes uses a control loop to continually handle differences between the desired and current states. Helm and Kustomize help manage configuration, while Custom Resource Definitions (CRDs) extend the Kubernetes API so we can express platform contracts through custom resources such as `Microservice`.

### GitOps deployment (Day 06-08)

Git stores deployment configuration and change history. Argo CD reads the configuration and synchronizes it to the cluster, while `ApplicationSet` helps generate multiple `Application` resources. We also learned that synchronization and health are separate assessments: even after the configuration matches, we still need to check whether the workloads are ready.

### Observability (Day 09-13)

Metrics show trends, logs record events, and traces connect the same request across services. OpenTelemetry and the Collector give services a consistent way to send and process telemetry, which we then query through Prometheus, Loki, Tempo, and Grafana. When latency or errors occur, we have data to investigate the cause.

### The boundary between CI and GitOps (Day 14-16)

Continuous integration (CI) handles code checks, builds, and image publishing. A digest pins the content to be delivered. A separate Git configuration change determines whether to deploy it to a particular environment. This separates responsibility for completing a build from responsibility for approving deployment, without requiring CI to modify the cluster directly.

### The delivery workflow with Backstage and the Operator (Day 17-26)

Backstage is the entry point to the Internal Developer Platform (IDP). The Catalog helps us find services, and templates collect requirements and submit PRs. Argo CD synchronizes the `Microservice`, and the Kopf Operator manages workloads according to platform defaults and reports health. The Kubernetes plugin lets us query the current state of resources, but that state is not a complete history of delivery events.

### API permissions and resource policies (Day 27-29)

Namespaces define resource scopes, and Role-Based Access Control (RBAC) determines which identities can query or modify resources. Gatekeeper then checks `privileged`, resource `limits`, and image settings, using `dryrun`, `warn`, and `deny` to determine how to provide feedback or reject requests. This part covers API permissions and resource policies; it does not go into the design of traffic security between services.

Back in our work as developers, we still need to choose which version to deliver, review changes, and verify functionality. The platform standardizes common settings and handoffs. It also lets us know who handles a request after submission and where to check the results.
