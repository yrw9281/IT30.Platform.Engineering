# Day 09 - Metrics, logs, and traces: using observability

We first used Kubernetes to define the state a service should maintain. When a Pod stops, the Deployment controller creates a replacement replica; if someone manually changes the replica count, it can also return to the declared configuration. We then used Argo CD and `ApplicationSet` to have the cluster continuously read reviewed configuration from Git and synchronize services to the correct environments.

These mechanisms ensure that the cluster converges toward our declared intent, but they do not tell us what is happening inside the service itself. Suppose a new version of `todo-api` has been synchronized to Staging. All Pods are `Running`, and the home page loads, yet testers report that some requests to create to-do items are slow. Having a Deployment does not mean requests are working properly; Argo CD showing `Healthy` cannot tell us where the delay is, either.

The team still needs to know: When did the problem start? Does it only affect a particular version or environment? Is the request stuck in the BFF, `todo-api`, or the database? What error information was recorded at the time?

Observability (O11y) supports this investigation. It gives engineers signals they can correlate while the system is running, so they can follow symptoms back to their causes. Installing another dashboard alone will not do that.

## Monitoring and observability

Monitoring suits known risks. The team defines thresholds in advance, such as notifying the on-call engineer when the proportion of 5xx responses exceeds 1% over five minutes. It answers the question, "Do we need to intervene now?"

Observability uses the data a system emits to investigate problems that have not already been defined as alert conditions. After an alert fires, we still need to know which route, service version, or downstream dependency the errors are concentrated in. A single fixed threshold usually cannot answer these questions.

| Scenario | What monitoring answers first | What observability then clarifies |
| --- | --- | --- |
| The failure rate of `todo-api` rises | Has it exceeded the alert threshold? | Which route, version, or downstream dependency is causing it? |
| Creating to-do items becomes slow | Is p95 latency abnormal? | Is the time spent in the BFF, `todo-api`, the database, or retries? |
| A particular request fails | Was an error log recorded? | Which services did it pass through? What happened at each step? |

Neither replaces the other. Without monitoring, the team may only learn about a service problem when users report it. Without observability, an alert tells us that something has happened but leaves us without enough clues to start troubleshooting.

## Metrics, logs, and traces look at the same request from different angles

The three most common types of telemetry data in observability are metrics, logs, and traces. Each suits different questions:

| Signal | Questions it can answer | Example for `Create Todo` |
| --- | --- | --- |
| Metrics | Is the problem growing? How widespread is the impact? | Did p95 latency in Staging rise between 10:08 and 10:13? |
| Logs | What context and errors did an individual event record? | What error category did the database return when saving a Todo failed? |
| Traces | Which components did a request pass through? Where was the time spent? | How long did the BFF, `todo-api`, and the database each take? |

Metrics are numerical series that can be aggregated. They suit tracking trends such as error rates, latency, traffic, and Pod restart counts. They help the team quickly identify the time window and scope of a problem, but are not suited to storing the details of every request.

Logs record the context of individual events, such as error categories, service versions, or operation results. A log that says only "database timeout" is not enough to find the request from that moment. It needs identifying information that can be matched to other telemetry.

Traces connect the processing of a single request across services into a timeline. A request to create a to-do item might enter the BFF first, then call `todo-api`, and finally write to the database. Each unit of work in a trace is a span, so we can see directly which part was slowest or failed.

Looking at just one type of signal can easily lead to a mistaken diagnosis. A metric can show when latency rose in Staging; a trace can reveal that the database span took 1.8 seconds; a log can then supply the error category and the context needed from that moment. We need to be able to move between all three to follow a useful investigation path.

## Decide on shared query criteria for the three signals first

Collecting more data does not necessarily make troubleshooting easier. If a log from `todo-api` records a database timeout, but the trace uses a different service name and the metric has no environment label, a query still cannot confirm whether they relate to the same problem.

The Todo system needs a consistent service identity across all three signals:

| Field | Purpose |
| --- | --- |
| `service.name` | Query metrics, logs, and traces using the same service name, such as `todo-api`. |
| `deployment.environment.name` | Distinguish Staging from other environments so their data does not get mixed together. |
| `service.version` | Compare error rates and latency across deployed versions. |
| `trace_id` | Go from a log entry to the trace for the corresponding request. |

These fields give us reference points for later investigation, rather than metadata added arbitrarily. The service name, environment, and version let us narrow the scope first; `trace_id` takes us from a failed event back to the full call chain.

We should also decide on data minimization at this stage. User email addresses, complete Todo contents, the `Authorization` header, and access tokens should never be sent as telemetry just to make debugging easier. Once data enters a centralized backend, its retention period, query access, and potential exposure in a leak all expand.

Metric labels require particular restraint. `service.name`, environment, normalized route, and status code each have a finite set of values, making them suitable aggregation dimensions. Request IDs, trace IDs, user IDs, and raw URL paths differ on almost every request. They produce high-cardinality time series and increase storage and query costs in the metrics backend. Keep individual identifiers in traces or logs.

## Investigating from an alert to the root cause

Returning to the opening scenario, requests to create to-do items through `todo-api` in Staging have become slow. We can investigate in the following order:

![Start with a latency or error-rate metric, query traces and structured logs in sequence, then check whether the metric trend has recovered](../assets/day-09-metric-trace-log-investigation-flow.png)

Start with the metric to check whether just one request was slow or overall latency is rising. Then query traces using the same time window and service criteria to see whether the time was spent in the BFF, `todo-api`, or the database. With the `trace_id`, we can find the structured log for the same request and check the error category and deployment information.

After a fix or rollback, return to the metric to check the trend. One successful request does not mean the problem has gone away. We can only confirm that the intervention worked when both latency and the error rate are back within the expected range.
